## 2. การตัดสินใจเชิงออกแบบที่ต้องรู้ก่อนเขียนบทถัดไป

### 2.1 `proxy.ts` ไม่เคยทำงานเลยตั้งแต่บทที่ 5 — แก้แล้ว

เจอตอนตรวจก้อนนี้ เป็นบั๊กที่เงียบสนิททั้ง `tsc` และ `build`:

```ts
// ก่อนแก้ — ในสตริง JS "\." คือ "." เฉย ๆ ดังนั้น ".*\..*" กลายเป็น ".*.*"
// ซึ่งชนทุก path ที่ยาวอย่างน้อย 1 ตัวอักษร => negative lookahead ตกทุกครั้ง
matcher: ["/((?!_next/static|_next/image|favicon.ico|.*\..*).*)"],

// หลังแก้
matcher: ["/((?!_next/static|_next/image|favicon.ico|.*\\..*).*)"],
```

ผลก่อนแก้คือ proxy ถูกข้ามทุก request — guard ของหน้าลูกค้าที่เขียนไว้ในบทที่ 5
จึงไม่เคยทำงานจริงเลย (หน้ายังปลอดภัยอยู่ เพราะ `resolveCustomerContext()` ตรวจซ้ำในทุกหน้า
proxy เป็นแค่ชั้นที่ช่วยให้ผู้ใช้ไม่เห็นหน้าเปล่า) docs ของ Next.js 16.2 ที่
`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`
ยืนยันรูปแบบ `\\.` นี้

อีกจุด: `STAFF_SESSION_REQUIRED` ถูกเรียกใช้แต่ยังไม่ได้ประกาศ ทำให้ `tsc --noEmit` พังค้างไว้
ตอนนี้เป็น `/^\/pos(?!\/login(\/|$))(\/|$)/` — ต้องยกเว้น `/pos/login` ไม่งั้น redirect วนไม่จบ

**บทเรียนที่ต้องจำ:** regex ใน `matcher` เขียนอยู่ในสตริง JS จึงต้อง escape สองชั้นเสมอ
และ **`matcher` ที่ผิดจะไม่ทำให้อะไรพัง มันแค่เงียบ** — ต้องทดสอบด้วย curl ทุกครั้งที่แก้

### 2.2 session พนักงานอยู่ใน cookie ที่เซ็น HMAC ไม่ใช่ตารางใน DB

ทุกหน้าของ POS ต้องเช็คสิทธิ์ ถ้าเก็บ session เป็นตารางจะต้อง query เพิ่มทุก request
ราคาที่จ่ายคือ **ยกเลิก session ทันทีไม่ได้ ต้องรอหมดอายุ (8 ชม.)** —
บทที่ 13 ที่ต้องมีปุ่ม "เตะพนักงานคนนี้ออกทุกเครื่อง" ต้องเพิ่มตาราง `StaffSession`
แล้วเช็ค revoke list ทับอีกชั้น

แม้ cookie จะพก `staffId`/`branchId` มาให้แล้ว `getCurrentStaff()` ก็ยัง query `Staff` ทุกครั้ง
เพราะต้องรู้ว่าบัญชีถูกปิดหรือถูกเปลี่ยนตำแหน่งไปแล้วหรือยัง — cookie ที่เซ็นไว้เมื่อเช้า
ไม่ควรมีอำนาจของตำแหน่งที่ถูกถอดไปเมื่อบ่าย

### 2.3 กันเดา PIN สองชั้น และชั้นหนึ่งยังไม่พอสำหรับ production

PIN 4 หลักเดาได้ง่ายมาก จึงต้องคู่กับสองอย่างเสมอ: จำกัดจำนวนครั้งที่กรอกผิด
(5 ครั้ง / ล็อก 5 นาที) และเขียน `AuditLog` ทุกครั้งที่ผิด

**ข้อจำกัดที่ต้องแก้ก่อน deploy:** ตัวนับอยู่ใน `Map` ในหน่วยความจำของ process
ถ้ารันหลาย instance ตัวนับไม่แชร์กัน คนที่ไล่สุ่ม PIN จะได้โควตาใหม่ทุกครั้งที่สลับ instance
บทที่ 13 ต้องย้ายไปเก็บที่ Postgres หรือ Redis (เป็นปัญหาเดียวกับ pub/sub ของ SSE ในบทที่ 8)

หน้าล็อกอินคืนข้อความเดียวกันทั้งกรณี "ไม่มีรหัสพนักงานนี้" และ "PIN ผิด"
เพื่อไม่ให้ใช้หน้าล็อกอินไล่เดาว่ารหัสพนักงานไหนมีอยู่จริง

### 2.4 ด่านตรวจสิทธิ์มีสามชั้น และชั้นที่เชื่อถือได้คือชั้นล่างสุด

| ชั้น | ที่อยู่ | ตรวจอะไร | เชื่อถือได้ไหม |
|---|---|---|---|
| 1 | `proxy.ts` | มี cookie ติดมาไหม (ห้ามแตะ DB) | ไม่ — แค่กันเห็นหน้าเปล่า |
| 2 | หน้า/component | ซ่อนปุ่มที่ตำแหน่งนั้นกดไม่ได้ | ไม่ — เป็นแค่ UX |
| 3 | Server Action + `lib/server/*` | `getCurrentStaff()` + `canAccessScreen()` + กรอง `branchId` ทุก query | **ใช่** |

ทุก action ที่ไม่ใช่ล็อกอินเรียก `requirePosStaff()` เป็นบรรทัดแรกเสมอ เพราะ Server Action
ถูกยิงตรงด้วย POST ได้ และทุก query ใน `lib/server/pos.ts` กรอง `staff.branchId` เสมอ —
พนักงานสาขา A ต้องมองไม่เห็นโต๊ะของสาขา B (สคริปต์ทดสอบมีเคสข้ามสาขา 4 เคส)

### 2.5 ไฟล์ `"use server"` export ได้เฉพาะ async function

`FormState` กับค่าตั้งต้นของฟอร์มถูกย้ายไปที่ `lib/form-state.ts` — ถ้าปล่อยไว้ใน
ไฟล์ `actions.ts` จะไม่พังตอน build แต่จะได้ 500 ทั้งหน้าตอนกดปุ่ม

### 2.6 เปิดโต๊ะจากเครื่อง POS กับจาก QR ต้องเป็นฟังก์ชันเดียวกัน

`openOrJoinTableSession()` ใน `lib/server/table-session.ts` เป็นแกนกลางที่ทั้งสองทางเรียก
ต่างกันแค่ฝั่งพนักงานบันทึก `openedByStaffId` และไม่ต้องเขียน cookie
ถ้าแยกเป็นสองฟังก์ชันจะค่อย ๆ เพี้ยนออกจากกัน แล้วจะเกิดเคส "พนักงานกดเปิดโต๊ะ
แต่ลูกค้าที่สแกน QR ได้คนละรอบ" ซึ่งแปลว่าโต๊ะเดียวได้สองบิล

กติกาที่ตามมา: กดเปิดโต๊ะซ้ำ = เข้าร่วมรอบเดิม ไม่สร้างรอบใหม่ และ `pax`
เพิ่มขึ้นได้อย่างเดียว คนที่กดทีหลังลดจำนวนของคนที่กดก่อนไม่ได้

### 2.7 ปิดรอบโต๊ะทำได้เฉพาะรอบที่ยังไม่มีของเข้าครัว

`closeTableSession()` ยอมให้ปิดเฉพาะรอบที่ไม่มีบิลสถานะอื่นนอกจาก `DRAFT`
(ใช้กับเคส "เปิดโต๊ะผิดใบ" / "ลูกค้าลุกไปก่อนสั่ง") ถ้ามีของเข้าครัวแล้วต้องผ่านการคิดเงิน
ในบทที่ 10 เสมอ — ไม่งั้นตรงนี้จะกลายเป็นช่องล้างบิลทิ้งโดยไม่มีร่องรอย

ตอนปิดรอบ ตะกร้า `DRAFT` ถูกลบทิ้งไปด้วยใน transaction เดียวกับการปิดรอบ
เปลี่ยนสถานะโต๊ะ และเขียน `AuditLog` — ปิดรอบสำเร็จแต่ log หายไม่ได้

### 2.8 ยกเลิกรายการ = จุดที่โกงกันบ่อยที่สุดในเล่ม

กติกาสามข้อที่บังคับพร้อมกัน: จำกัดตามตำแหน่ง (เสิร์ฟกดเองไม่ได้ ต้องเรียกผู้จัดการ),
บังคับกรอกเหตุผลอย่างน้อย 3 ตัวอักษร ไม่มีทางลัด, และเขียน `AuditLog` พร้อม snapshot
ของยอดเงิน/จำนวน/สถานะ ณ ตอนที่กด — ทั้งหมดอยู่ใน `$transaction` เดียวกับการยกเลิก

`Order.subtotal` ถูกคิดใหม่ด้วย `recalculateOrderSubtotal()` ใน transaction เดียวกัน
ไม่ใช่ปล่อยให้ยอดค้างผิดแล้วรอหน้าจอคำนวณเอง

### 3.2 ขับผ่าน HTTP จริงด้วย curl — `proxy.ts` + RBAC

| เส้นทาง | ไม่มี cookie | cookie เจ้าของร้าน (001) | cookie ครัว (004) |
|---|---|---|---|
| `/pos` | 307 → `/pos/login` | 200 | 307 → `/pos/login` |
| `/pos/table/[id]` | 307 → `/pos/login` | 200 | — |
| `/pos/login` | 200 | 307 → `/pos` | — |
| `/t/a1x7qk/cart` | 307 → `/t/a1x7qk` | — | — |
| `/t/a1x7qk` | 200 | — | — |
| `/kds`, `/` | 200 | — | — |

cookie ที่แก้ลายเซ็น (ต่อท้าย 2 ตัวอักษร) → 307 กลับไปหน้าล็อกอิน = HMAC ทำงานถูก
กรณีครัวถูกเด้งออกมาจาก `/pos` ทั้งที่มี cookie ถูกต้อง คือ RBAC ชั้นที่ 3 ทำงาน
(proxy ปล่อยผ่านเพราะมันเช็คได้แค่ว่า "มี cookie ไหม")

## 4. สิ่งที่ยังค้าง / ข้อจำกัดที่รู้ตัว

1. **ไม่มีทางเปลี่ยนสถานะรายการจาก `PLACED` ได้เลยตอนนี้** — เพราะทำบทที่ 9 ก่อนบทที่ 8
   ผลข้างเคียงที่ต้องรู้: ปิดรอบโต๊ะที่สั่งของไปแล้วยังทำไม่ได้ (ต้องรอคิดเงินในบทที่ 10)
   และผังโต๊ะจะขึ้น "ครัวกำลังทำ" ค้างตลอด ใช้ `npm run dev:reset-table <tableCode>` ล้างระหว่าง dev
2. **ย้าย/รวมโต๊ะ และแยกบิล ยังไม่ได้ทำ** — เป็นส่วนที่เหลือของบทที่ 9
   ต้องเป็น transaction เดียวที่ย้ายออร์เดอร์ทั้งชุด ไม่ใช่แค่เปลี่ยน `tableId`
3. **คิดเงินยังไม่มี** — `Order.subtotal` ถูกเติมค่าจริง แต่ `serviceCharge`/`vat`/`grandTotal`
   ยังเป็น 0 ทั้งหมด รอบทที่ 10
4. **rate limit PIN อยู่ใน memory** — ดูหัวข้อ 2.3
5. **ยกเลิก session ทันทีไม่ได้** — ดูหัวข้อ 2.2
6. **หน้า POS ยังไม่ realtime** — ต้องกดโหลดหน้าใหม่เพื่อเห็นของที่ครัวทำเสร็จ
   บทที่ 8 ทำ SSE แล้วให้หน้านี้รับ event เดียวกันด้วย
7. **ในฐาน dev มีรอบโต๊ะ A1 ที่หมดอายุแล้วค้างอยู่ 1 รอบ (บิล `20260821-0001`, `-0002`
   สถานะ `PLACED`)** — เป็นข้อมูลจากการทดสอบด้วยมือของก้อนที่แล้ว ตั้งใจไม่ลบ
   เพราะใช้เป็นข้อมูลตั้งต้นทดสอบ KDS บทที่ 8 ได้เลย

## 5. ขั้นถัดไป — บทที่ 8: จอครัว (KDS) แบบ realtime

ของที่พร้อมรออยู่แล้ว:

- `OrderItem.stationId` ถูก snapshot ตั้งแต่ตอนสั่ง — KDS กรองตามสถานีได้โดยไม่ต้อง join เมนูสด
  (ยืนยันด้วยเคสทดสอบในหัวข้อ 3.1) และรายการที่ `stationId = null` เช่นน้ำเปล่า **ต้องไม่ขึ้นจอครัว**
- `lib/order-status.ts` มีป้ายภาษาไทยและตาราง transition ที่อนุญาตครบแล้ว — ห้ามเขียนป้ายซ้ำ
- `OrderItemStatus` แยกจาก `OrderStatus` อยู่แล้ว KDS ทำงานที่ระดับรายการ

ข้อควรระวังที่ต้องยึด:

- **SSE ผ่าน Route Handler เท่านั้น ห้าม WebSocket ตรง ๆ** (Route Handler อัปเกรด connection ไม่ได้)
- วางเผื่อ pub/sub กลาง (Postgres LISTEN/NOTIFY) ตั้งแต่ต้น เพราะหลาย instance ไม่แชร์ memory —
  เป็นปัญหาเดียวกับตัวนับ PIN ผิดในหัวข้อ 2.3 แก้ทีเดียวได้ทั้งคู่
- ต้องเพิ่ม `"kds"` เข้า `StaffScreen` ใน `lib/rbac.ts` และเพิ่ม guard ของ `/kds` ใน `proxy.ts`
  (ตอนนี้ `/kds` เปิดได้โดยไม่ต้องล็อกอิน)
- ทำเสร็จแล้วกลับมาต่อ `/t/[tableCode]/orders` ของลูกค้ากับผังโต๊ะ `/pos` ให้รับ event เดียวกัน

### คำสั่งที่ใช้บ่อยตอนทำงานต่อ

```
npm run db:up                      เปิด Postgres (Docker Desktop ต้องรันอยู่ก่อน)
npm run dev                        dev server
npm run smoke:pos                  ทดสอบตรรกะฝั่งพนักงาน 58 เคส
npm run smoke:order                ทดสอบตรรกะตะกร้าลูกค้า 21 เคส
npm run dev:staff-cookie 001       ออก cookie พนักงานไว้ทดสอบด้วย curl
npm run dev:session a1x7qk         ออก token ลูกค้าไว้ทดสอบด้วย curl
npm run dev:reset-table a1x7qk     ล้างรอบโต๊ะ+บิลของโต๊ะนั้น
```

**หมายเหตุเครื่อง dev:** Docker Desktop ติดตั้งแบบ per-user ที่
`C:\Users\ADMIN\AppData\Local\Programs\DockerDesktop` ถ้า `docker` สั่งไม่ได้ ให้เปิดโปรแกรมก่อน
แล้วรอจนกว่า `docker info` จะตอบ ค่อยสั่ง `npm run db:up`
