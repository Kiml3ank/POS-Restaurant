# รายงานยอดขายย้อนหลัง + ส่งออก CSV (spec)

> **สถานะ:** spec ที่ตกลงกับผู้ใช้แล้ว รอทำแผน implementation
> **วันที่:** 2026-09-12
> **ที่มา:** spec §18 (Reports) + §19 (Report Export) · เป็นก้อนที่บทที่ 15 กันออกไป
> โดยตั้งใจ ("รายงานยอดขายย้อนหลังเป็นก้อนใหญ่แยกต่างหาก")

## 1. เป้าหมาย

ตอบสี่คำถามของเจ้าของร้าน/ผู้จัดการเกี่ยวกับ **ช่วงเวลาที่เลือกเอง**:

1. ขายได้เท่าไร กี่บิล บิลละเท่าไร ขายดีช่วงไหนของวัน
2. เมนูไหนขายดี เมนูไหนขายไม่ออก
3. พนักงานคนไหนรับเงินไปเท่าไร ให้ส่วนลดไปเท่าไร
4. เงินเข้ามาทางช่องทางไหนบ้าง

แล้ว **เอาออกไปเปิดในสเปรดชีตได้** (CSV)

## 2. การตัดสินใจที่ตกลงไว้แล้ว (ห้ามเปลี่ยนระหว่างทำโดยไม่คุย)

| ข้อ | ที่ตกลง | เหตุผล |
|---|---|---|
| ขอบเขต | **ขาย · เมนู · พนักงาน · ช่องทางจ่าย** เท่านั้น | อีกสามหมวดของ spec ต้องการข้อมูลที่ยังไม่มี (ดูหัวข้อ 3) |
| ส่งออก | **CSV อย่างเดียว** | Excel/PDF ต้องเพิ่ม dependency ทั้งคู่ · CSV เปิดใน Excel ได้อยู่แล้ว |
| ที่มาของยอดเงิน | **`Payment` เท่านั้น** | กฎตั้งแต่บทที่ 11 — ยอดใน `Order` เป็นส่วนแบ่งที่กระจายไว้ ไม่ใช่เงินจริง |
| ที่มาของ "ขายกี่ชิ้น" | **เฉพาะบิลที่จ่ายแล้วในช่วงนั้น** | รายงานย้อนหลังที่แต่ละส่วนบวกไม่ตรงกันคือรายงานที่ไม่มีใครเชื่อ (ดู 4.2) |
| สิทธิ์ | `canViewReports` = **OWNER/MANAGER** | เห็นยอดขายทั้งสาขา — กติกาเดียวกับ `canBrowseReceipts` / `canViewShiftHistory` |
| หน้าจอ | **หน้าเดียว** `/admin/reports` สี่ส่วนเรียงลงมา | ผู้จัดการต้องกวาดตาทีเดียวจบแล้วกดส่งออก ไม่ใช่ไล่เปิดสี่หน้า |
| ทางเข้า | ลิงก์จากหน้า "สรุปวันนี้" | **ไม่เพิ่มโมดูลที่เจ็ด** — แถบล่างที่ 390px เหลือช่องละ ~55px (ท่าเดียวกับประวัติกะ) |
| `costPrice` | **ไม่ทำในก้อนนี้** | แตะจอจัดการเมนู + seed และ spec วางไว้ที่ §4 Product Management ไม่ใช่ §18 |

## 3. สิ่งที่ spec §18 ขอแต่ยังทำไม่ได้ (และเหตุผล)

| หมวดของ spec | ทำไมยังไม่ได้ |
|---|---|
| Inventory (stock · movement · low stock · waste · purchases) | บทที่ 14 ยังไม่มี ไม่มีตารางวัตถุดิบเลย |
| Financial (Revenue − Cost − Expenses − Discounts − Refunds) | ต้องมี **`costPrice`** ที่ `MenuItem` + **โมดูลรายจ่าย** ซึ่งไม่มีในแผนของ e-book เลย |
| Products → Estimated profit | ต้องมี `costPrice` เหมือนกัน |
| Employees → Refunds | **ระบบยังไม่มีการคืนเงิน** |

**กฎเดิมจากบทที่ 15 ใช้ที่นี่ด้วย: ห้ามใส่บรรทัด/คอลัมน์ที่เป็น 0 ตลอดกาล**
ให้เขียนบนจอตรง ๆ ว่ายังไม่มีและเพราะอะไร (ท่าเดียวกับสามอย่างที่หน้าสรุปวันนี้บอก)

## 4. ข้อมูล — ตัวเลขแต่ละตัวมาจากไหน

**ไม่มีตารางใหม่ ไม่มี migration** — อ่านจากของที่มีอยู่ทั้งหมด

### 4.1 ยอดขาย · ช่องทางจ่าย · พนักงาน — จาก `Payment`

```
where: { branchId, paidAt: { gte: from, lt: to } }
```

- **รายได้** = Σ `grandTotal`
- **จำนวนบิล** = จำนวนแถว
- **บิลเฉลี่ย** = รายได้ ÷ จำนวนบิล **หารจำนวนเต็มแล้วปัดลง** (ไม่ใช่ float —
  ค่าเฉลี่ยที่แสดงเป็นเงินต้องเป็นจำนวนเต็มหน่วยย่อยเหมือนทุกยอดในระบบ)
  · **ไม่มีบิลเลย = 0 ไม่ใช่ `NaN`** (ต้องหารเมื่อ `billCount > 0` เท่านั้น)
- **แยกช่องทางจ่าย** = group by `method` (ต้องมีครบทุกค่าของ enum แม้เป็น 0 —
  คนอ่านต้องเห็นว่า "ไม่มี" ไม่ใช่ "หาไม่เจอ" กฎเดียวกับใบสรุปกะ)
- **แยกพนักงาน** = group by `paidByStaffId` (**คนรับเงิน** ไม่ใช่คนกดสั่ง) +
  Σ `discountAmount` ต่อคน · `paidByStaffId` เป็น null ได้ (SetNull ตอนลบพนักงาน)
  → ต้องมีแถว "ไม่ระบุ" ไม่ใช่ทิ้งแถวนั้นหาย

### 4.2 ขายกี่ชิ้น · เมนูขายดี — จาก `OrderItem` ของบิลที่ **จ่ายแล้วในช่วงนั้น**

```
OrderItem
  where order.tableSessionId ∈ (session ที่มี Payment ซึ่ง paidAt อยู่ในช่วง)
    and status notIn (DRAFT, CANCELLED)
```

group by `menuItemId` แล้วสรุป Σ `quantity` และ Σ `lineTotal`
ใช้ **`nameSnapshot`** เป็นชื่อที่แสดง ไม่ join เมนูสด (ร้านเปลี่ยนชื่อเมนูแล้ว
รายงานเดือนที่แล้วต้องยังเรียกชื่อเดิม — กฎเดียวกับใบเสร็จบทที่ 12)

> **ชื่อซ้ำในช่วงเดียวกัน:** เมนู id เดียวอาจมี `nameSnapshot` หลายค่าถ้าร้านเปลี่ยน
> ชื่อกลางช่วง — **ใช้ค่าของรายการที่ใหม่ที่สุดในช่วงนั้น** (ไม่ใช่ค่าแรกที่เจอ
> ซึ่งขึ้นกับลำดับที่ฐานคืนมาแล้วเปลี่ยนไปมาได้) และยังรวมเป็นแถวเดียวตาม id เหมือนเดิม

> **⚠ นี่คือจุดที่ต่างจากหน้า "สรุปวันนี้" โดยตั้งใจ**
> หน้าสรุปวันนี้นับของที่ **ส่งเข้าครัวแล้ว** เพราะของที่ทำไปแล้วมีต้นทุนไปแล้ว
> และช่วงเย็นที่ลูกค้ายังนั่งเต็มร้านจะดูเหมือนขายไม่ออกถ้านับเฉพาะบิลที่ปิด
>
> รายงานย้อนหลังตอบคนละคำถาม: "ช่วงนั้นขายอะไรไปแล้วได้เงินเท่าไร" ถ้านับของที่
> ยังไม่จ่าย **ตารางเมนูกับตัวเลขรายได้จะบวกไม่ตรงกัน** ซึ่งทำให้ทั้งหน้าเชื่อไม่ได้
> → **หน้าจอต้องเขียนบอกตรง ๆ ว่านับเฉพาะบิลที่จ่ายแล้ว**

### 4.3 แยกตามวัน / ตามชั่วโมง — bucket ฝั่ง JS ไม่ใช่ SQL

ดึงแถวในช่วงแล้วจัดกลุ่มด้วย `Branch.timezone` ในโค้ด **ไม่ใช้ `date_trunc` ของ Postgres**

เหตุผล: เขตเวลาของสาขาเป็นข้อมูลในแอป (`Branch.timezone`) การ group ใน SQL ต้อง
ส่งชื่อโซนเข้าไปแล้วหวังว่า tzdata ของ container ตรงกับของ Node — **สองแหล่งความจริง**
ส่วนที่นี่ `branchDayRangeUtc()` คำนวณขอบช่วงอยู่แล้ว ใช้กลไกเดียวกันต่อได้เลย

ราคาที่จ่าย: ต้องดึงแถว Payment ทั้งช่วงมาในหน่วยความจำ →
**จำกัดช่วงไม่เกิน 92 วัน** และบอกบนจอเมื่อผู้ใช้ขอกว้างกว่านั้น
(ร้านเดียว 3 เดือน ≈ ไม่กี่พันแถว ซึ่งอยู่ในวิสัยที่รับได้ · เกินกว่านั้นค่อยย้ายไป SQL)

## 5. ช่วงเวลา

- ตัวเลือกสำเร็จ: **วันนี้ · เมื่อวาน · 7 วันล่าสุด · เดือนนี้**
- กรอกเองได้: `from` / `to` เป็นวันที่ (ไม่ใช่เวลา)
- เก็บใน **URL query** (`?from=YYYY-MM-DD&to=YYYY-MM-DD`) ไม่ใช่ state ในหน้า
  เพราะหน้านี้ต้องส่งลิงก์ให้กันได้ และ **ปุ่มส่งออก CSV ใช้พารามิเตอร์ชุดเดียวกัน**
- แปลงเป็นช่วง UTC ด้วย `branchDayRangeUtc()` ที่มีอยู่แล้ว —
  ช่วงเป็นแบบ **`gte from` / `lt to+1วัน`** (ปลายเปิด) เสมอ
  บิลที่จ่ายตอน 23:59 ของวันสุดท้ายต้องถูกนับ และบิลตอนเที่ยงคืนตรงของวันถัดไปต้องไม่ถูกนับ
- ค่าตั้งต้นเมื่อไม่มี query = **7 วันล่าสุด** (วันนี้อย่างเดียวมีหน้าสรุปวันนี้อยู่แล้ว)

### ลายเซ็นที่ตกลงไว้

```ts
/**
 * ช่วงเป็น "วันของสาขา" เป็นสตริง ไม่ใช่ Date — การแปลงเป็น UTC เกิดฝั่ง server
 * เท่านั้น เพราะ `branchDayRangeUtc()` อยู่ใน `lib/server/branch-time.ts`
 * ที่มี `import "server-only"` · แบบนี้ `lib/report-range.ts` จึงยัง import ได้จากทุกที่
 */
type ReportRange = { fromDay: string; toDay: string };

getSalesReport(branchId: string, range: ReportRange): Promise<{
  revenue: number;
  billCount: number;
  averageBill: number;
  itemsSold: number;
  byDay:      Array<{ day: string; revenue: number; billCount: number }>;
  byHour:     Array<{ hour: number; revenue: number; billCount: number }>;
  byMethod:   Array<{ method: PaymentMethod; total: number; count: number }>;
  byStaff:    Array<{ staffId: string | null; name: string | null; total: number; count: number; discountTotal: number }>;
  byItem:     Array<{ menuItemId: string; name: string; quantity: number; revenue: number }>;
}>
```

`byItem` เรียงมากไปน้อย — "ขายไม่ออก" คือหางของลิสต์เดียวกัน **ไม่ต้องมี query ที่สอง**

## 7. ส่งออก CSV

**Route Handler ไม่ใช่ Server Action** — action คืนไฟล์ให้เบราว์เซอร์ดาวน์โหลดตรง ๆ ไม่ได้

`GET /admin/reports/export?type=<sales|byDay|byHour|products|staff|payments>&from=&to=`

- ตรวจสิทธิ์ซ้ำในไฟล์นี้เอง (`getCurrentStaff("admin")` + `canViewReports`)
  **การซ่อนปุ่มไม่ใช่การกันสิทธิ์** — URL นี้ยิงตรงได้
- `Content-Type: text/csv; charset=utf-8` · `Content-Disposition: attachment; filename="..."`
- **ต้องมี BOM (`﻿`) นำหน้า** ไม่งั้น Excel อ่านภาษาเวียดนามเป็นอักษรขยะ
  (Excel เดา encoding เป็น codepage ของเครื่องถ้าไม่มี BOM)
- **ยอดเงินในไฟล์เป็นจำนวนเต็มหน่วยย่อยดิบ + คอลัมน์ `currency`** ไม่ใช่สตริงที่จัดรูปแล้ว
  — สเปรดชีตต้องบวกเลขคอลัมน์นั้นได้ ส่วนการจัดรูปเป็นเรื่องของหน้าจอ
- หัวคอลัมน์แปลตามภาษาของเครื่อง (route handler อ่าน cookie ได้ จึงเรียก `getT()` ได้)

## 8. จอ

`/admin/reports` — `min-h-0` + `overflow-auto` เอง (กฎเชลล์) เรียงลงมา:

1. ตัวเลือกช่วงเวลา + ปุ่มส่งออก
2. สี่ตัวเลขใหญ่: รายได้ · จำนวนบิล · บิลเฉลี่ย · จำนวนชิ้น
3. ยอดตามวัน (แถบแนวนอนเทียบสัดส่วน ไม่ใช่กราฟไลบรารี) + ยอดตามชั่วโมง
4. เมนูขายดี/ขายไม่ออก · พนักงาน · ช่องทางจ่าย

- **ไม่ใช้ไลบรารีกราฟ** — แถบสัดส่วนวาดด้วย `div` กว้างเป็น % พอ และไม่ต้องเพิ่ม
  dependency ที่ต้องดูแลเรื่องธีม/ภาษา/ขนาดจอเอง
- ทุกจำนวนเงินผ่าน `formatMoney(amount, branch.currency)`
- เขียนบนจอตรง ๆ ว่า **นับเฉพาะบิลที่จ่ายแล้ว** และ **ยังไม่มีต้นทุน/กำไร/สต็อก เพราะอะไร**

## 9. เคสที่ต้องมีเทสต์ (`npm run smoke:reports`)

**ยอดเงิน** (คิดจากราคาใน DB + `calculateBill()` เสมอ ห้ามเขียนตัวเลขไว้เอง)
1. รายได้ = Σ `grandTotal` ของบิลในช่วง · บิลนอกช่วงไม่ถูกนับ
2. บิลเฉลี่ยเป็นจำนวนเต็มและ = รายได้ ÷ จำนวนบิล (ปัดลง)
3. แยกช่องทางจ่ายบวกกลับได้เท่ารายได้รวม
4. แยกพนักงานบวกกลับได้เท่ารายได้รวม · บิลที่ `paidByStaffId = null` ยังถูกนับ

**ขอบช่วง**
5. บิลตอน 23:59 ของวันสุดท้าย **ถูกนับ** · บิลตอน 00:00 ของวันถัดไป **ไม่ถูกนับ**
   (ทดสอบด้วยเวลาตามโซนของสาขา ไม่ใช่ UTC)
6. ขอช่วงเกิน 92 วัน = ถูกปฏิเสธด้วยคีย์ ไม่ใช่ตัดเงียบ ๆ

**เมนู**
7. รายการที่ถูกยกเลิก (`CANCELLED`) ไม่ถูกนับ · ตะกร้า `DRAFT` ไม่ถูกนับ
8. ของในบิลที่ยังไม่จ่าย **ไม่ถูกนับ** (ข้อที่ต่างจากหน้าสรุปวันนี้)
9. ใช้ `nameSnapshot` — เปลี่ยนชื่อเมนูแล้วรายงานเก่าต้องยังเรียกชื่อเดิม

**ขอบเขต/สิทธิ์**
10. ไม่ข้ามสาขา
11. `canViewReports` — แคชเชียร์/ครัว/เสิร์ฟ เปิดไม่ได้

**CSV**
12. ชื่อเมนูที่มี `,` และ `"` ถูก escape ถูกต้อง (สร้างเมนูชื่อพิสดารขึ้นมาทดสอบจริง)
13. ไฟล์ขึ้นต้นด้วย BOM
14. คอลัมน์ยอดเงินเป็นจำนวนเต็มดิบ ไม่ใช่สตริงที่จัดรูปแล้ว
