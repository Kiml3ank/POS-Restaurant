# แผน: ย้ายโต๊ะ / รวมโต๊ะ (งานค้างจากบทที่ 9)

สถานะ: **แผน — ยังไม่ลงมือ** · ตัดสินใจร่วมกับผู้ใช้เมื่อ 2026-08-24

## 1. ขอบเขต

ทำ **ย้ายโต๊ะ** กับ **รวมโต๊ะ** เท่านั้น · **แยกบิลไม่อยู่ในก้อนนี้**

แยกบิลถูกเลื่อนออกไปเพราะมันไม่ใช่งานเดียวกัน: ย้าย/รวมจบที่การเปลี่ยนว่าออร์เดอร์
ผูกกับรอบไหน ซึ่ง `buildBill()` กับ `takePayment()` รองรับอยู่แล้วโดยไม่ต้องแก้
ส่วนแยกบิลต้องทำให้ `Payment` รับ "จ่ายบางส่วน / หลายใบต่อรอบ" ได้ ซึ่งกระทบ
ใบเสร็จ (บทที่ 12) และรายงาน (บทที่ 15) พร้อมกัน — เป็นก้อนถัดไปที่ต้อง brainstorm ใหม่

## 2. รูปร่างข้อมูล

**ไม่มีคอลัมน์ใหม่ที่ `Order`** — คอมเมนต์ใน schema เขียนรอเคสนี้ไว้แล้วว่า
"เก็บ `tableId` ซ้ำไว้ตรง ๆ เพราะการย้าย/รวมโต๊ะเปลี่ยนค่านี้ได้โดย session เดิมไม่เปลี่ยน"
การย้ายจึงเป็นการอัปเดต `Order.tableSessionId` + `Order.tableId` พร้อมกันในทรานแซกชันเดียว

ผลที่ตามมาและเป็นเหตุผลหลักที่เลือกทางนี้: **`buildBill()` · `takePayment()` ·
ใบเสร็จ · KDS ไม่ต้องแก้ตรรกะเลย** ตั๋วครัวเปลี่ยนไปโชว์โต๊ะใหม่เองเพราะอ่านจาก
`Order.tableId` ที่ถูกอัปเดตไปแล้ว

สิ่งที่เพิ่มใน `prisma/schema.prisma`:

- `TableSessionStatus` เพิ่มค่า **`MERGED`**
  แยกจาก `CLOSED` (จบด้วยการจ่ายเงิน) และ `ABANDONED` (พนักงานล้างทิ้ง) เพราะรายงาน
  บทที่ 15 ต้องนับ "จำนวนรอบขาย" ได้ถูก — รอบที่ถูกกลืนไม่ใช่รอบขายที่เกิดขึ้นจริง
- `TableSession.mergedIntoSessionId String?` + self-relation `mergedInto` / `mergedFrom`
  ใช้สองอย่าง: (1) ให้มือถือลูกค้าเดินตามโซ่ไปรอบปลายทาง (2) ตอบย้อนหลังได้ว่า
  ของจากโต๊ะไหนไปรวมที่ไหน โดยไม่ต้องไปขุด AuditLog
- คอลัมน์นี้ **ต้องเป็น null เสมอสำหรับการย้าย** เพราะการย้ายไม่สร้างรอบใหม่
  (รอบเดิมแค่เปลี่ยน `tableId`) จึงไม่มีโซ่ให้เดิน

migration ใหม่หนึ่งใบ: เพิ่มค่า enum + คอลัมน์ + FK (เป็นการเพิ่มล้วน ไม่แปลงชนิด
คอลัมน์เดิม จึงไม่ต้องใช้ `--create-only` แบบตอนแปลง `Branch.currency`)

**⚠ งานที่มากับการเพิ่มค่า enum: ต้องไล่ตรวจทุก query ที่ถาม `TableSession.status` อยู่แล้ว**
โค้ดที่เขียนว่า `status: { not: "OPEN" }` หรือ `in: ["CLOSED", "ABANDONED"]` จะเปลี่ยน
ความหมายทันทีที่มีค่าที่สี่ และ TypeScript **ไม่ฟ้อง** เพราะยังเป็นค่าที่ถูกชนิด
จุดที่ต้องดูอย่างน้อย: `pos.ts` (ผังโต๊ะ/คิว) · `billing.ts` · `payment.ts` ·
`dashboard.ts` (นับรอบขายวันนี้) · `table-session.ts` — ทำเป็นขั้นแรกของการลงมือ
ไม่ใช่ไล่เก็บทีหลัง

## 3. โมดูลใหม่: `lib/server/table-move.ts`

เป็น leaf module (`import "server-only"`) ที่ `pos.ts` **ไม่** import กลับ เพื่อไม่ให้เกิด
import cycle แบบที่บทที่ 12 เจอกับ `receipt-issue.ts` · `pos.ts` อยู่ที่ 541 บรรทัดแล้ว
การยัดเพิ่มทำให้ไฟล์ที่ทำหลายเรื่องอยู่แล้วโตขึ้นอีก

สองฟังก์ชัน **แยกกัน ไม่ใช่ตัวเดียวที่เดาเอาเองว่าเป็นย้ายหรือรวม**:

```
moveTableSession(staff, { sessionId, targetTableId })
mergeTableSessions(staff, { sourceSessionId, targetSessionId })
```

เหตุผลที่ไม่ยุบเป็นตัวเดียว: ฟังก์ชันเดียวที่ดูว่าปลายทางว่างไหมแล้วตัดสินเอง แปลว่า
คนที่ตั้งใจ "ย้าย" ไปโต๊ะที่เผลอกดผิดเป็นโต๊ะมีคน จะได้ผลลัพธ์เป็นการรวมบิลของคนอื่น
เข้าด้วยกันโดยไม่ตั้งใจ — เป็นความเสียหายเรื่องเงินที่กู้คืนอัตโนมัติไม่ได้

### ด่านที่บังคับ (ทั้งหมดอยู่ในทรานแซกชันเดียวกับการย้ายจริง)

| ด่าน | เหตุผล |
|---|---|
| ต้นทางและปลายทางเป็น `DINE_IN` ทั้งคู่ | ซื้อกลับไม่คิดเซอร์วิสชาร์จ (`billRatesForSalePoint`) รวมข้ามช่องทาง = ยอดเปลี่ยนเงียบ ๆ |
| ทั้งสองรอบเป็น `OPEN` และยังไม่มี `Payment` | รอบที่จ่ายแล้วคือประวัติ ห้ามขยับ |
| ทุกอย่างอยู่สาขาเดียวกับ `staff.branchId` | กฎเดิมของทุก query ใน `pos.ts` |
| ย้าย: ปลายทางต้องไม่มีรอบที่เปิดอยู่ | ปฏิเสธพร้อมข้อความบอกให้ไปกด "รวมโต๊ะ" แทน |
| รวม: ต้นทาง ≠ ปลายทาง | กันการรวมโต๊ะเข้ากับตัวเอง |
| **รอบใดรอบหนึ่งติดธงส่วนลดพนักงาน = ปฏิเสธ** | รวมแล้วส่วนลด 10% จะกินอาหารของอีกโต๊ะด้วย — ให้ปลดธงก่อนแล้วติดใหม่หลังรวม เป็นการบังคับให้คนกดเห็นตัวเลขที่เปลี่ยน |

### สิ่งที่ทำในทรานแซกชัน

1. อ่านและตรวจด่านทั้งหมดข้างบน (อ่านสดใน transaction ห้ามเชื่อค่าที่หน้าจอส่งมา)
2. `updateMany` ทุก `Order` ของรอบต้นทาง → `tableSessionId` + `tableId` ใหม่
   **รวมออร์เดอร์ที่เป็น `DRAFT`** (ตะกร้าที่ยังไม่ส่ง) — ไม่ย้ายตาม = ของหายพร้อมโต๊ะ
   ซึ่งเป็นบทเรียนเดียวกับกฎ "ตะกร้า DRAFT ที่มีของ = จ่ายไม่ได้" ในบทที่ 11
3. **ย้าย:** รอบเดิมเปลี่ยน `tableId` · **รวม:** รอบต้นทาง → `MERGED` +
   `mergedIntoSessionId` + `closedAt`, และรอบปลายทาง `pax` บวกกัน
4. โต๊ะต้นทาง → `AVAILABLE` · โต๊ะปลายทาง → `OCCUPIED`
5. `AuditLog` action ใหม่ **`table_session.move`** / **`table_session.merge`**
   เก็บ: ชื่อโต๊ะต้นทาง-ปลายทาง · จำนวนออร์เดอร์ที่ย้าย · **ยอดเงินที่ถูกย้าย** ·
   ยอดของบิลปลายทางก่อนรวม — เพราะคำถามที่ต้องตอบย้อนหลังคือ "เงินก้อนไหนไปรวมกับก้อนไหน"
   ไม่ใช่แค่ "มีการรวมเกิดขึ้น" · เพิ่มป้ายไทยทั้งสอง action ใน `lib/audit-log.ts`
6. **หลัง commit** ค่อย `publishRealtimeEvent()` (กฎบทที่ 8: ห้ามยิงใน `$transaction`)
   ยิงให้ทั้งโต๊ะต้นทางและปลายทาง เพื่อให้จอที่เปิดค้างอยู่และมือถือลูกค้าขยับตาม

## 4. มือถือลูกค้าเดินตามโซ่

`resolveCustomerContext()` ปัจจุบันหา session ด้วย `token + tableId + status OPEN`
ซึ่งหลังรวมโต๊ะจะได้ `null` แล้วลูกค้าถูกเด้งไปหน้าเปิดโต๊ะ — ถ้าเขากดเปิด
**จะได้บิลใบใหม่ที่โต๊ะเดิม แยกจากบิลรวม** เป็นบิลผีที่พนักงานไม่รู้ตัว

แก้เป็น: หา session ด้วย `token` ก่อน (ไม่ผูก `tableId`) แล้ว **ถ้าสถานะเป็น `MERGED`
ให้เดินตาม `mergedIntoSessionId` ต่อไปจนเจอรอบที่ `OPEN`** จำกัดความลึกไว้ (เช่น 5 ชั้น)
กันโซ่วนถ้าข้อมูลเพี้ยน แล้วตรวจเงื่อนไขเดิมทั้งหมดกับรอบปลายทาง (ยัง OPEN · ยังไม่หมดอายุ
· สาขาเดียวกัน)

- หน้าจอลูกค้าต้องขึ้นบรรทัดบอกว่า **"โต๊ะนี้ถูกรวมไปที่ A1 แล้ว"** ไม่ใช่เปลี่ยนชื่อโต๊ะเงียบ ๆ
  (คนที่นั่งอยู่ต้องเข้าใจว่าทำไมมือถือขึ้นอีกโต๊ะ)
- **ข้อแลกที่ยอมรับ:** ลูกค้าที่กลับบ้านไปแล้วแต่ยังถือ cookie เก่า จะสั่งเข้าบิลรวมได้
  จนกว่า `expiresAt` (3 ชม.) จะหมด — เท่ากับความเสี่ยงเดิมของระบบก่อนก้อนนี้ ไม่ได้เพิ่มใหม่
- การ**ย้าย**ไม่ต้องใช้โซ่เลย เพราะรอบเดิมยัง OPEN อยู่ แค่เปลี่ยนโต๊ะ — แต่เงื่อนไข
  `tableId` ที่ถูกถอดออกจาก query ทำให้เคสนี้ทำงานได้ด้วยโดยอัตโนมัติ

## 5. สิทธิ์

`canMoveTableSession(role)` = **ทุกตำแหน่งที่เข้าจอ POS ได้ รวมพนักงานเสิร์ฟ**

เหตุผลเดียวกับ `canSetStaffMeal`: คนที่เห็นลูกค้าย้ายโต๊ะจริงคือเด็กเสิร์ฟ ถ้าต้องเรียก
แคชเชียร์ทุกครั้งงานจะชะงักแล้วคนจะเลี่ยงไปใช้วิธีอื่นที่แย่กว่า (เช่นสั่งของโต๊ะใหม่
ใส่บิลเก่า) ตัวคุมไม่ใช่การจำกัดสิทธิ์ แต่คือ **AuditLog ที่เก็บยอดเงินที่ย้าย**
บวกกับด่าน "ห้ามแตะรอบที่จ่ายแล้ว"

## 6. หน้าจอ

ปุ่ม "ย้ายโต๊ะ" / "รวมโต๊ะ" อยู่ในหน้า `/pos/table/[tableId]` **ในโซนที่เลื่อนได้**
ไม่ใช่โซน `flex-none` (กฎจากบั๊ก "รวมทั้งสิ้นหายจากจอ" — อะไรที่เพิ่มใน `flex-none`
จะไปกินพื้นที่ของโซน `overflow-auto`)

กดแล้วกางฟอร์มที่เซิร์ฟเวอร์เรนเดอร์รายชื่อโต๊ะปลายทางมาให้แล้ว **แยกสองกลุ่มชัดเจน**:

- **โต๊ะว่าง** → ปุ่ม "ย้ายมาที่นี่"
- **โต๊ะที่มีคน** → ปุ่ม "รวมบิลเข้าด้วยกัน" พร้อม **ยอดปัจจุบันของโต๊ะนั้น**
  เพราะคนกดต้องเห็นว่ากำลังจะรวมเงินก้อนไหนเข้ากับก้อนไหนก่อนกดยืนยัน

ทุกอันเป็น `<form>` จริงตามแบบของ `table-actions.tsx` เดิม (กดได้ก่อน JS โหลดเสร็จ)
· ปุ่มรวมต้องมีขั้นยืนยันที่บอกยอดรวมใหม่ ไม่ใช่กดทีเดียวจบ

## 7. เทสต์: `npm run smoke:table-move` (สคริปต์ใหม่)

ใช้โต๊ะที่ไม่ชนกับ smoke ชุดอื่น (A1 = `smoke:order` · B1/B2 = `smoke:pos` · A3 = `smoke:payment`)
และลบข้อมูลที่สร้างเองตอนจบตามลำดับ **ออร์เดอร์ → ใบเสร็จ → การรับเงิน → รอบโต๊ะ**

เคสที่ต้องมีอย่างน้อย:

- ย้ายแล้วยอดบิลเท่าเดิมเป๊ะ (ตัวเลขจริง) และ `Order.tableId` เปลี่ยนครบทุกใบ
- ย้ายแล้วตะกร้า `DRAFT` ตามไปด้วย
- ย้ายไปโต๊ะที่มีรอบเปิด = error (ไม่ใช่กลายเป็นรวมเงียบ ๆ)
- รวมแล้ว `subtotal` ของบิลปลายทาง = ผลบวกของสองบิลเดิม และ **เซอร์วิสชาร์จ/VAT
  ถูกคิดครั้งเดียวบนยอดรวม ไม่ใช่บวกยอดที่คิดแยกกันมาแล้ว** (กฎบทที่ 10)
- รวมแล้วรอบต้นทางเป็น `MERGED` + ชี้ `mergedIntoSessionId` ถูก และโต๊ะต้นทางว่าง
- cookie ของรอบที่ถูกกลืนยังใช้ได้และไปโผล่ที่รอบปลายทาง (เดินโซ่)
- รอบที่ติดธงส่วนลดพนักงาน = ปฏิเสธทั้งย้ายและรวม
- รอบที่จ่ายเงินแล้ว = ปฏิเสธ
- ข้ามช่องทาง (โต๊ะ ↔ เคาน์เตอร์ซื้อกลับ) = ปฏิเสธ
- ข้ามสาขา = ปฏิเสธ
- `AuditLog` ถูกเขียนพร้อมยอดเงินที่ย้าย
- **รวมแล้วรับเงินได้จริงจนจบ** (`takePayment` + ออกใบเสร็จ) — เป็นเคสที่พิสูจน์ว่า
  ชั้นล่างไม่ต้องแก้จริงอย่างที่อ้างไว้ในหัวข้อ 2

ชุดเดิมทั้ง 13 ชุด (705 เคส) ต้องยังผ่านครบ · `npm run audit:screens` วัดหน้า
`/pos/table/[tableId]` ที่กางฟอร์มเลือกโต๊ะแล้วด้วย

## 8. สิ่งที่ตั้งใจไม่ทำในก้อนนี้

- **แยกบิล** — ก้อนถัดไป ต้อง brainstorm ใหม่เพราะกระทบ `Payment`/ใบเสร็จ/รายงาน
- **แยกกลับ (unmerge)** — ไม่มีปุ่ม เพราะหลังรวมแล้วออร์เดอร์อาจถูกแก้/ยกเลิก/เสิร์ฟ
  ไปแล้ว การแยกกลับอัตโนมัติจะเดาผิดได้ · `mergedIntoSessionId` เก็บไว้ให้สืบย้อนหลังได้
  แต่การกู้คืนต้องทำด้วยมือ (ยกเลิกรายการ + เปิดรอบใหม่)
- **ย้ายทีละรายการ** (ย้ายเฉพาะ "ผัดไทยจานนี้" ไปอีกโต๊ะ) — เป็นญาติกับแยกบิล ไม่ใช่ก้อนนี้
- **รวมมากกว่าสองโต๊ะในคลิกเดียว** — กดรวมทีละคู่ซ้ำได้ และโซ่รองรับอยู่แล้ว
