**ส่วนลดในก้อนนี้คือ "ส่วนลดพนักงาน" อย่างเดียว** — พนักงานทุกตำแหน่งกินแล้วได้ลด 10%

## 2. โมเดล — บิลรู้ว่า "ใครกิน" ไม่ใช่แค่ "ลดกี่บาท"

```
Branch       += staffMealDiscountBp  Int @default(1000)   // 10.00% แก้ต่อสาขาได้
TableSession += staffCustomerId · staffMealSetById · staffMealSetAt
Payment      += staffCustomerId · discountBp
```

### 2.1 เก็บ "กติกา" ไม่ใช่ "ผลลัพธ์" — และนี่คือหัวใจของก้อนนี้

`TableSession` เก็บแค่ **ใครกิน** · อัตราอ่านจาก `Branch` สดทุกครั้งที่คิดบิล
· `Payment` snapshot ทั้งอัตราและจำนวนตอนปิดบิล — **วงจรเดียวกับเซอร์วิสชาร์จและ VAT เป๊ะ ๆ**
ไม่มีกติกาที่สาม

ผลที่ตามมาและตั้งใจให้เป็น: **ลูกค้าสั่งเพิ่ม → ส่วนลดขยับตามเอง**
ถ้าเก็บเป็นจำนวนเงินที่คิดไว้ตอนกด ส่วนลด 10% ของบิล ฿1,800 จะยังเป็น ฿180
ตอนบิลขึ้นเป็น ฿3,000 โดยไม่มีใครสังเกต — มีเคสทดสอบตรึงไว้ (`⭐` ใน smoke)

### 2.2 `Payment.discountBp` ต้องมีคู่กับ `discountAmount`

ไม่งั้นใบเสร็จที่พิมพ์ซ้ำปีหน้าพิมพ์คำว่า "10%" ไม่ได้ ต้องเดาย้อนจากตัวเลข
(เหตุผลเดียวกับที่ `vatRateBp` ถูก snapshot ตั้งแต่บทที่ 11)

### 2.3 แยก "คนกิน" ออกจาก "คนกด"

แคชเชียร์คิดเงินให้พ่อครัวเป็นเคสปกติ — `staffCustomerId` กับ `staffMealSetById`
จึงเป็นคนละคอลัมน์ และ AuditLog บันทึกทั้งคู่

## 3. สามชั้นที่กันการโกง (ไม่ใช่การจำกัดสิทธิ์)

**ทุกตำแหน่งกดได้ รวมครัวและเสิร์ฟ** ต่างจากสิทธิ์อื่นเกือบทั้งหมดในระบบ
เพราะทุกคนกินจริง และการบังคับให้ตามผู้จัดการมากดตอนตีหนึ่งไม่ได้แก้อะไร —
มันแค่ย้ายช่องไปอยู่ที่ผู้จัดการ

| ชั้น | กติกา | กันอะไร |
|---|---|---|
| หนึ่งคน หนึ่งบิลที่เปิดอยู่ | เช็คใน transaction เดียวกับที่เขียน | เอาชื่อคนเดียวไปแปะห้าโต๊ะพร้อมกัน |
| ต้อง active ในสาขานี้ | ตรวจฝั่ง server | ใช้ชื่อคนที่ลาออกแล้ว = ชื่อที่ตามตัวไม่ได้ |
| AuditLog ทุกการติด **และปลด** | ใครกด · ใครกิน · ยอดบิล ณ ตอนนั้น · IP | ติดธง → รับเงินตามยอดที่ลด → ปลดธง |

**ชั้นที่สามสำคัญที่สุด** — บันทึกเฉพาะตอนติดจะมองไม่เห็นรูปแบบโกงหลักเลย
และ log เก็บ **ยอดบิล ณ วินาทีนั้น** ด้วย เพราะ log ที่บอกแค่ "ติดธงตอน 20:14"
ตอบไม่ได้ว่าเสียหายเท่าไหร่ ส่วน "ติดธงตอนบิล ฿4,200 = ลด ฿420" ตอบได้ทันที

**ช่องที่ยังเหลือและรู้ตัว:** กติกา "หนึ่งคน หนึ่งบิล" บังคับด้วยการ query ใน transaction
ไม่ใช่ unique constraint (Postgres ต้องใช้ partial unique index บนเงื่อนไข
`status = 'OPEN'` ซึ่ง Prisma ยังประกาศให้ไม่ได้) สองเครื่องที่กดพร้อมกันเป๊ะ ๆ
ยังหลุดได้ — แต่ AuditLog บันทึกทุกครั้ง เคสนี้จึงตรวจเจอย้อนหลังได้เสมอ

## 4. หน้าอ่าน AuditLog — `/admin/audit-logs`

`canReadAuditLog` = OWNER/MANAGER เท่านั้น (log เผยทุกการกระทำของทุกคน รวมยอดเงินทุกบิล)
กรอง: ช่วงวัน (ตาม timezone สาขา) · action · พนักงาน · `entityId` + แบ่งหน้า
· แถวของ action ที่ต้องจับตา (`AUDIT_SENSITIVE_ACTIONS`) ถูกไฮไลต์ด้วย accent

### 4.1 กฎเหล็กของ `lib/audit-log.ts`: **ห้ามซ่อนแถวที่ไม่รู้จัก**

`metadata` เป็น `Json` ที่รูปร่างต่างกันตาม action และจะมี action ใหม่เพิ่มทุกบท
ตัวแปลจึงต้องมี fallback เสมอ:

- action ที่ไม่มีป้ายไทย → **คืนชื่อดิบ** ไม่ใช่ "ไม่ทราบ"
- คีย์ที่ไม่มีป้าย → **แสดงด้วยชื่อคีย์ดิบ** ไม่ใช่ข้าม
- `metadata` เป็น null / array / string → ไม่พัง

เหตุผล: ตารางนี้มีไว้ตอบว่า "เกิดอะไรขึ้น" — **แถวที่หายจากหน้าจอเพราะโค้ดยังไม่รู้จัก
action นั้น แย่กว่าแถวที่อ่านยาก** คนที่กำลังสืบสวนจะสรุปว่าไม่มีเหตุการณ์นั้น ซึ่งผิด
มีเคสทดสอบตรึงทั้งสามข้อ

### 4.2 รายการ action ในกล่องกรองมาจาก `groupBy` ของจริงในฐาน

ไม่ได้ hardcode — บทถัดไปที่เพิ่ม action ใหม่จะโผล่เองโดยไม่ต้องแก้ไฟล์นี้

### 4.3 `ipAddress` — เขียนจริงแล้ว

`lib/server/client-ip.ts` อ่าน `x-forwarded-for` → `x-real-ip` ผ่าน `headers()`
· **เก็บแค่ IP ไม่เก็บ user-agent** (UA ไม่ตอบคำถาม "กดจากในร้านหรือข้างนอก" เพิ่ม
แต่ระบุตัวบุคคลได้ละเอียดขึ้น — เก็บเท่าที่ตอบคำถามได้ ไม่เก็บเผื่อ)
· คืน `null` ได้เสมอและไม่ใช่ error — **ห้ามให้การเขียน log ล้มเหลวเพราะอ่าน IP ไม่ได้**
(สคริปต์/seed ไม่มี request context) แถวที่เขียนจากสคริปต์จึงแสดง "—" ซึ่งถูกแล้ว

**⚠ ก่อน deploy:** `x-forwarded-for` ปลอมได้ถ้าแอปรับ request ตรงจากอินเทอร์เน็ต
ต้องมี proxy ที่เขียนทับค่านี้อยู่ข้างหน้าเสมอ

## 5. บั๊กหน้าจอสามตัวที่ผู้ใช้จับได้ (และเทสต์ผมปล่อยผ่านทั้งสาม)

### 5.1 ⚠ "รวมทั้งสิ้น" หายจากจอ

วางแผงติดธงไว้ในโซน `flex-none` เดียวกับปุ่มรับเงิน → โซนยอดเงินที่เป็น `overflow-auto`
ถูกบีบจาก 336px เหลือ **148px** แล้วยอดรวมหลุดออกนอกจอ

**แก้รอบแรกยังไม่พอ** — ย้ายยอดรวมไปโซนที่ตรึงแล้วยอดรวมเห็นได้จริง แต่โซน
รายละเอียดเหลือบรรทัดเดียว (ผู้ใช้รายงานซ้ำว่า "อ่านรายละเอียดไม่ได้") เพราะแพเนลขวา
ต้องยัด ยอดรวม + วิธีจ่าย + ช่องรับเงิน + ปุ่มลัด + เงินทอน + ปุ่มยืนยัน ~500px

**แก้ที่รากจริง: ย้าย "สรุปยอด" ทั้งก้อนไปอยู่ใต้รายการอาหารในคอลัมน์ซ้าย**
ซึ่งว่างเปล่าเกือบทั้งจอ — และเป็นลำดับที่บิลกระดาษใช้อยู่แล้ว (รายการ → ยอดย่อย → ภาษี)

โครงสุดท้าย:
- **ซ้าย** (เลื่อนได้): ตารางรายการ → ค่าอาหาร/ส่วนลด/เซอร์วิสชาร์จ/VAT → แผงติดธงพนักงาน
- **ขวา**: คำเตือน · **รวมทั้งสิ้น** · แผงรับเงิน — เฉพาะของที่ต้องเห็นตลอดตอนรับเงิน

ที่ 1400×800 ทุกอย่างอยู่ในจอเดียวโดยไม่ต้องเลื่อนเลย

**ปัญหาเดิมมีมาก่อนบทที่ 13** (ที่จอสูง 700px โซนนั้นเหลือ 121px แต่ต้องการ 321px)
การเพิ่มแผงแค่ทำให้เห็นได้ตั้งแต่ 900px

| | ก่อน | หลัง |
|---|---|---|
| 1280×700 | ยอดรวมถูกตัด | เห็นเสมอ |
| 1280×800 | ยอดรวมถูกตัด | เห็นเสมอ |
| 1400×800 | รายละเอียดเหลือบรรทัดเดียว | เห็นครบทั้งหน้า ไม่ต้องเลื่อน |

**บทเรียนของเครื่องมือ (ครั้งที่สองในสองก้อนติด):** สคริปต์วัด overflow ถามว่า
*"เนื้อหาล้นออกนอกหน้าไหม"* ซึ่งตอบว่า "ไม่" ได้เสมอเมื่อ flexbox **บีบ**
โซนที่เลื่อนได้จนแบน — ไม่มีอะไรล้น แต่ตัวเลขสำคัญที่สุดหายไป
และการวัดรอบแรกของผมเทียบ `getBoundingClientRect` กับ viewport เฉย ๆ ซึ่ง
**ตอบ "เห็นได้" แม้ element จะถูก `overflow` ของกล่องแม่ตัดทิ้ง**
→ ตอนนี้เทียบกับกรอบของกล่องที่เลื่อนได้จริง (`clippedByScroller`)

### 5.2 ⚠ แผงควบคุมอ่านเหมือน "สถานะ" ไม่ใช่ "ปุ่ม"

หัวข้อเดิม `ส่วนลดพนักงาน 10%` อยู่ต่อจากแถว ค่าอาหาร / เซอร์วิสชาร์จ / VAT พอดี
ซึ่งทุกแถวเป็นรูปแบบ "ป้าย … จำนวนเงิน" — คนอ่านจึงเข้าใจว่า **บิลนี้ถูกลด 10% ไปแล้ว**
ทั้งที่ยังไม่ได้ติดธงเลย (ผู้ใช้รายงานว่า "ทุกบิลถูกมาร์กเป็นเมนูพนักงาน")

แก้: หัวข้อเป็น **คำถาม** (`บิลนี้พนักงานกินหรือเปล่า`) · เปอร์เซ็นต์ย้ายไปอยู่บน **ปุ่ม**
(`ลด 10%` = บอกว่ากดแล้วจะเกิดอะไร ไม่ใช่บอกว่าเกิดไปแล้ว) · เพิ่ม `rule` คั่นให้ขาด
จากรายการตัวเลข

### 5.3 แผงกว้าง 412px ตรึง → 1/3 ของพื้นที่ทำงาน

`xl:w-1/3 xl:min-w-[412px] xl:max-w-[560px]` ทั้งตะกร้าในหน้าโต๊ะและแพเนลยอดในหน้าคิดเงิน
(สองอันนี้อยู่ตำแหน่งเดียวกันบนจอและพนักงานสลับไปมาตลอด ความกว้างที่ขยับทำให้สายตาเสียจังหวะ)

วัดจริง: 1280→412px (32%) · 1440→412px (29%) · 1920→551px (29%) · 2560→560px (22%)
ไม่ล้นแนวนอนทุกความกว้าง · min ต้องมีเพื่อไม่ให้แคบกว่าเดิม · max ต้องมีเพราะบนจอ 4K
1/3 จริงคือ 1280px ซึ่งกว้างกว่าที่ตะกร้ามีอะไรให้แสดงมาก
