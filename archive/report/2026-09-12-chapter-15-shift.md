## 2. กติกาที่เป็นเรื่องเงิน (จุดที่พังแล้วเสียหายจริง)

### 2.1 อ่านกะที่เปิดอยู่ **ในทรานแซกชันเดียวกับการรับเงิน**

`takePayment()` เรียก `resolveOpenShiftId(tx, branchId)` **ข้างใน `$transaction`**
ก่อนสร้างแถว `Payment` ไม่ใช่อ่านไว้ก่อนแล้วส่งเข้าไป

ถ้าอ่านไว้ก่อน จะมีช่องที่ **ปิดกะแทรกกลาง** แล้วเงินก้อนนั้นถูกผูกกับกะที่ปิดไปแล้ว
— ใบสรุปที่พิมพ์ออกไปจะไม่มีเงินก้อนนั้น ทั้งที่แถวในฐานบอกว่าอยู่ในกะนั้น

`lib/server/shift-current.ts` เป็น **leaf module ที่มีฟังก์ชันเดียว** เพื่อกัน
import cycle (`payment.ts` → `shift-current.ts` เท่านั้น **ห้าม** ชี้กลับไปหา
`shift.ts`) — ท่าเดียวกับ `receipt-issue.ts` ของบทที่ 12

### 2.2 ฐานเป็นคนกันสองกะเปิดพร้อมกัน ไม่ใช่โค้ด

"อ่านว่ายังไม่มีกะเปิด" กับ "สร้างแถวใหม่" เป็นสองคำสั่งที่มีช่องว่างระหว่างกัน
สองเครื่องที่กดพร้อมกันจะผ่านด่านอ่านทั้งคู่ → **partial unique index**
`CREATE UNIQUE INDEX ... ON shifts (branchId) WHERE status = 'OPEN'`
แล้วให้ `openShift()` แปลง `P2002` เป็น `error.shift_already_open`

Prisma จะ log บรรทัด `prisma:error ... Unique constraint failed` ตอนเทสต์เดินผ่าน
เคสนี้ — **นั่นคือด่านทำงาน ไม่ใช่เทสต์พัง**

> partial unique index ประกาศใน `schema.prisma` ไม่ได้ ต้องเขียน SQL เอง

### 2.3 ปิดกะเป็น conditional update และรวมยอดในทรานแซกชันเดียวกัน

`updateMany({ where: { id, branchId, status: "OPEN" }, ... })` เป็นคำสั่งที่ทั้งตรวจ
และเขียนในครั้งเดียว — เครื่องที่สองได้ `count === 0` → **คืนใบเดิม ไม่ใช่ error**
(ท่าเดียวกับกันจ่ายซ้ำของบทที่ 11)

การรวมยอด (`Σ Payment`) อยู่ในทรานแซกชันเดียวกับการปิด ถ้าแยกออกไป บิลที่จ่าย
ระหว่างนั้นจะ **หายจากทั้งสองกะ** (ไม่อยู่ในใบที่ปิดเพราะรวมยอดไปก่อนแล้ว ·
ไม่อยู่ในกะถัดไปเพราะ `shiftId` ชี้กะที่ปิดไปแล้ว)

### 2.4 เงินในลิ้นชักคือ `grandTotal` ไม่ใช่ `receivedAmount`

ลูกค้ายื่นแบงก์ใหญ่ เงินที่ค้างอยู่ในลิ้นชักคือยอดบิล ส่วนที่เหลือทอนออกไปแล้ว
· **QR ไม่นับเข้าลิ้นชัก** แต่ยังขึ้นบรรทัดแยกในใบสรุป
· มีเคสทดสอบที่จ่ายเกินทุกบิลแล้วยืนยันว่ายอดไม่พอง

```
expectedCash   = openingFloat + Σ grandTotal ของ Payment ที่ method = CASH ในกะนี้
cashDifference = countedCash − expectedCash        (บวก = เกิน · ลบ = ขาด)
```

### 2.5 ส่วนต่างที่ไม่มีคำอธิบาย = ปิดไม่ได้

บังคับกรอกหมายเหตุอย่างน้อย 3 ตัวอักษรเมื่อส่วนต่างไม่เป็นศูนย์ **ที่ชั้นธุรกิจ
ไม่ใช่แค่ที่ฟอร์ม** เพราะ action ถูกยิงตรงด้วย POST ได้ · ส่วนต่างที่ไม่มีคำอธิบาย
คือสิ่งที่ตรวจสอบย้อนหลังไม่ได้เลย

### 2.6 X คิดสด · ตัวเลขตอนปิด snapshot — และมีทางอ่านทางเดียว

`getShiftReport()` **รับเฉพาะกะที่ยังเปิดอยู่** กะที่ปิดแล้วอ่านผ่าน `getShift()` เท่านั้น
ไม่งั้นจะมีสองทางที่ให้ตัวเลขของกะเดียวกัน แล้ววันหนึ่งสองทางนั้นจะไม่ตรงกัน
(คิดสดขยับตามอัตราภาษีที่เปลี่ยน ส่วน snapshot ไม่ขยับ)

**ยืนยันด้วยเลขจริง:** ปิดกะแล้วแก้ `vatRateBp` เป็น 14% ยอดในใบสรุปไม่ขยับเลย

### 2.7 ระบบกะไม่ใช่ด่านขวางการขาย

ไม่มีกะเปิดก็รับเงินได้ (`shiftId = null`) — ร้านที่ลืมเปิดกะต้องขายต่อได้
เงินพวกนั้นถูกนับแยกด้วย `getCashOutsideShift()` แล้ว **แสดงบนหน้าเปิดกะ**
พร้อมช่วงเวลา เพื่อให้คนเปิดกะเช้าวันถัดไปรู้ว่าเงินเกินในลิ้นชักมาจากไหน

แถบบน `/pos` เป็น **ลิงก์ ไม่ใช่ modal** และไม่ปิดปุ่มไหนเลย

## 3. ที่ทำต่างจากแผน (และทำไม)

แผนเขียนไว้เมื่อ 2026-08-25 **ก่อนก้อน i18n/VND** จึงมีของที่ขัดกฎที่บังคับใช้ไปแล้ว

### 3.1 คืนคีย์ ไม่ใช่ประโยค (7 จุด)

แผนให้ `lib/server/shift.ts` คืน `{ ok: false, error: "ตำแหน่งของคุณเปิดกะไม่ได้" }`
ซึ่งขัดกฎ **"`lib/server/*` ห้ามแปลภาษา"** โดยตรง → เปลี่ยนเป็น
`{ ok: false, errorKey: "error.cannot_manage_shift" }` ทั้งหมด พร้อมเพิ่มคีย์คู่
vi/en ครบทุกตัว (ขาดข้างเดียว = build error ไม่ใช่คีย์ดิบบนจอ)

ผลพลอยได้: **smoke ตรวจคีย์ ไม่ตรวจประโยค** — เทสต์ชุดนี้จะไม่พังในวันที่มีคน
แก้ถ้อยคำในพจนานุกรม (ซึ่งเป็นสิ่งที่ทำให้เทสต์ 11 เคสพังตอนแปลเป็นอังกฤษรอบก่อน)

ข้อความบนจอทั้งหมด (27 บรรทัดที่แผนเขียนเป็นภาษาไทยตรง ๆ ใน JSX) ย้ายเข้า
พจนานุกรมเป็น 50 คีย์ใหม่

### 3.2 ใช้ตารางป้ายที่มีอยู่แล้ว แทนที่จะพิมพ์คำเอง

- แผนเขียน `method === "CASH" ? "เงินสด" : method === "QR" ? "QR" : "บัตร"` ในใบสรุป
  → ใช้ **`paymentMethodKey()`** ซึ่งคอมเมนต์ของมันเขียนไว้ตั้งแต่บทที่ 11 แล้วว่า
  "รายงานปิดกะบทที่ 15 ต้องเรียกคำเดียวกัน ห้ามพิมพ์ซ้ำเอง"
- แผนเขียน ternary แปลง `kind` → `OrderType` ในตัวสรุปยอด
  → ใช้ **`ORDER_TYPE_FOR_SALE_POINT`** ของ `lib/sale-point.ts`
- แผนใช้ `Intl.DateTimeFormat("th-TH", …)` ตรึงภาษาไทย
  → ใช้ **`intlLocale(locale)`** (ปลอดภัยเพราะทุกจอที่เรียกเป็น server component)

### 3.3 `summarizePayments()` ต้องเป็น generic ไม่งั้นหน้าจอคอมไพล์ไม่ผ่าน

แผนประกาศพารามิเตอร์เป็น `shift: { id: string; openingFloat: number }` ผลคือ
ผลลัพธ์พกแค่สองฟิลด์นั้นออกไป แล้วหน้า X report ที่ต้องแสดง "เปิดกะเมื่อ …"
พังทันที (`TS2339: Property 'openedAt' does not exist`)

→ `function summarizePayments<S extends { id: string; openingFloat: number }>(shift: S, …)`
คืนแถวเต็มที่ผู้เรียกส่งเข้ามา ไม่ใช่ร่างที่ถูกตัดทิ้ง

### 3.4 เทสต์ยอดเงินนอกกะวัด **ส่วนต่าง** ไม่ใช่ค่าสัมบูรณ์

`getCashOutsideShift()` นับทุกแถวที่ `shiftId = null` ของสาขา (ถูกตาม spec)
แต่แปลว่าเลขขึ้นกับของที่ค้างอยู่ในฐานของแต่ละเครื่อง — เขียนเทียบตรง ๆ แล้ว
เทสต์จะเขียวบนเครื่องที่ฐานสะอาดและแดงบนเครื่องที่มีข้อมูล
→ จับ baseline ตอนเริ่มไฟล์แล้วเทียบส่วนต่าง

## 5. ที่ตั้งใจไม่ทำ

- **ไม่มี "ปิดวัน" แยกจากปิดกะ** — `orderNumber` รีเซ็ตเองทุกวันอยู่แล้ว และ
  เลขใบกำกับภาษีห้ามรีเซ็ตตลอดกาล "ปิดวันเพื่อรีเซ็ตตัวนับ" จึงไม่มีความหมายที่นี่
- **ช่องนับเงินเป็นยอดรวมก้อนเดียว** ไม่แยกใบ/เหรียญ — การนับแยกต้องมีชุดใบต่อ
  สกุลเงิน (THB/LAK/VND คนละชุด) ซึ่งไม่คุ้มในก้อนนี้
- **ไม่มีบรรทัด refund ในใบสรุป** — ระบบยังไม่มีการคืนเงิน **ห้ามใส่บรรทัดที่เป็น 0
  ตลอดกาล** ให้เขียนบนจอตรง ๆ ว่ายังไม่มี (ท่าเดียวกับสามอย่างที่หน้าสรุปวันนี้บอก)
- **ไม่มีปุ่มพิมพ์ของตัวเอง** — `receipt-print-button.tsx` นับการพิมพ์ลง AuditLog
  ของ **ใบเสร็จ** ก๊อปมาแก้จะได้ตัวนับที่ชี้ผิดเอกสาร · ใบสรุปกะพิมพ์กี่ครั้งก็ได้
  ให้กด Ctrl+P (CSS 80mm ของบทที่ 12 ทำงานให้อยู่แล้วผ่านคลาส `receipt-doc`)
- **ไม่เพิ่มโมดูลที่เจ็ดในแถบหลังร้าน** — แถบล่างที่ 390px เหลือช่องละ ~55px แล้ว
  ทางเข้าประวัติกะคือลิงก์จากหน้า "สรุปวันนี้" ซึ่งคนที่เห็นเป็นชุดเดียวกับ
  `canViewShiftHistory` พอดี
- **ลิ้นชักหลายใบ/register · pay-in/pay-out · รายงานยอดขายย้อนหลัง** — YAGNI ตาม spec

## 6. ของที่คนถัดไปต้องรู้

- **⚠ `npm run smoke:shift` ลบ `Shift` ของสาขาทุกแถว ไม่ใช่แค่ของตัวเอง**
  จำเป็นเพราะ partial unique index: ถ้ามีกะเปิดค้างอยู่ `openShift()` จะล้มทันที
  — ข้อมูลกะที่ตั้งไว้เล่นในเครื่อง dev จะหายทุกครั้งที่รันชุดนี้
- **`canManageShift` = ชุดเดียวกับ `canTakePayment`** (OWNER/MANAGER/CASHIER)
  โดยตั้งใจ — คนถือลิ้นชักคือคนนับเงิน ถ้าให้เฉพาะผู้จัดการปิดกะ ร้านที่ผู้จัดการ
  กลับก่อนจะเหลือกะที่ไม่มีใครปิดได้ · ตัวคุมคือ AuditLog + หน้าประวัติ
- **`canViewShiftHistory` = OWNER/MANAGER เท่านั้น** (กติกาเดียวกับ `canBrowseReceipts`)
  — ปิดกะของตัวเอง = งานประจำวัน · ลิสต์ทุกกะย้อนหลัง = เห็นส่วนต่างของเพื่อนร่วมงานทุกคน
- **`"shift.changed"` ห้ามใส่ใน `CUSTOMER_BROADCAST_EVENTS`** — คอมเมนต์ที่รายชื่อนั้น
  ยกกะเป็นตัวอย่างไว้ตั้งแต่บทที่ 8 แล้วว่าเป็น event ที่ลูกค้าเดายอดขายได้
- **`breakdown` เป็น Json อ่านอย่างเดียว** ห้ามให้หน้าจอใหม่เอาไปคำนวณต่อ
  ถ้าต้องการตัวเลขใหม่ให้ query จาก `Payment` ตรง ๆ
- **`summarizePayments()` เป็นแกนเดียวของทั้ง X และการปิดกะ** ห้ามคิดยอดซ้ำที่อื่น
