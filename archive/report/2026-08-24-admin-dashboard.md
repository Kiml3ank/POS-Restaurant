# หน้าแรกหลังร้าน — สรุปวันนี้ (spec §1)

**วันที่:** 2026-08-24 · ต่อจาก `report/2026-08-24-settings.md`
**สถานะ:** ✅ เสร็จ · `tsc` · `eslint` · `build` ผ่าน
smoke **สิบสามชุด 705 เคส FAIL 0** (เพิ่ม `dashboard` 31 เคส) · วัดจอ 5/5

เส้นทาง: `/admin` (เดิม redirect ไป `/admin/menu`)

---

## 1. ทำไมเปลี่ยนตอนนี้

`app/(admin)/admin/page.tsx` เดิม redirect ทิ้งพร้อมคอมเมนต์ว่า *"หน้ารวมที่มีปุ่มเดียว
คือหน้าที่ทุกคนต้องกดผ่านโดยไม่ได้อะไร"* — เขียนไว้ตอนมีโมดูลเดียว **ตอนนี้มีหก**
และผู้ใช้ถามเองว่า "admin dashboard อยู่ไหน" ซึ่งเป็นสัญญาณว่าเหตุผลเดิมหมดอายุแล้ว

**สิ่งที่หน้านี้ให้ไม่ใช่ลิงก์** (แถบซ้ายทำหน้าที่นั้นอยู่แล้ว) แต่เป็นคำตอบของสองคำถาม
ที่เจ้าของร้านถามทุกวันและไม่มีที่ไหนในระบบตอบได้: **"วันนี้ขายได้เท่าไหร่"** และ
**"ตอนนี้หน้าร้านค้างอะไรอยู่"**

## 2. ตัวเลขบนหน้า และที่มาของแต่ละตัว

| กลุ่ม | ตัวเลข | มาจาก |
|---|---|---|
| ยอดขายวันนี้ | ยอดรวม · จำนวนบิล · เฉลี่ยต่อบิล | `Payment.paidAt` ในช่วงวันของสาขา |
| | แยกช่องทางรับเงิน (เงินสด/QR) | `Payment.method` |
| | แยกช่องทางขาย (นั่ง/ซื้อกลับ) | `Payment → TableSession → RestaurantTable.kind` |
| | บิลพนักงาน + ส่วนลดรวม | `Payment.staffCustomerId` / `discountAmount` |
| ตอนนี้ที่หน้าร้าน | บิลที่เปิดอยู่ · ยอดที่ยังไม่ได้เก็บ | `TableSession.status = OPEN` |
| | ครัวกำลังทำ · พร้อมเสิร์ฟ (นับเป็น**ชิ้น**) | `OrderItem.status` |
| เมนูขายดีวันนี้ | 5 อันดับ | `OrderItem` ของออร์เดอร์ที่ `placedAt` วันนี้ |
| ที่ต้องจับตา | จำนวนเหตุการณ์ | `AuditLog` ที่อยู่ใน `AUDIT_SENSITIVE_ACTIONS` |

**⚠ ยอดขายมาจาก `Payment` ไม่ใช่ผลรวมของ `Order`** — ยอดใน `Order` เป็น **ส่วนแบ่ง**
ที่กระจายลงไปเพื่อทำรายงานแยกช่องทาง (กฎตั้งแต่บทที่ 11) บวก Order จะได้เลขใกล้เคียง
แต่ไม่ใช่เงินที่อยู่ในลิ้นชักจริง · มีเทสต์ยืนยันว่าสองทางให้เลขตรงกันในวันนี้ **และ
ที่มาของตัวเลขบนจอต้องเป็น Payment เสมอ**

**เมนูขายดีนับของที่ "ส่งเข้าครัวแล้ว" ไม่ใช่ "จ่ายเงินแล้ว"** เพราะของที่ทำไปแล้ว
มีต้นทุนไปแล้วไม่ว่าบิลจะปิดหรือยัง — นับเฉพาะบิลที่ปิดจะทำให้ช่วงเย็นที่ยังมีลูกค้า
นั่งอยู่เต็มร้านดูเหมือนขายไม่ออก (ตัดรายการที่ถูกยกเลิกออก เพราะของถูกทิ้งไม่ใช่ของที่ขายได้)

## 3. สิทธิ์: เด้งไปทำงาน ไม่ใช่ขึ้นว่า "คุณไม่มีสิทธิ์"

`canViewDashboard` = OWNER/MANAGER (ระดับเดียวกับ `canBrowseReceipts` เพราะบอกยอดขาย
ทั้งสาขาในจอเดียว) — **ตำแหน่งอื่นไม่ได้ถูกกันออกจากจอหลังร้าน** แค่ถูก redirect ไป
`/admin/menu` เหมือนพฤติกรรมเดิมทุกประการ ซึ่งเป็นหน้าที่พวกเขาตั้งใจจะไปอยู่แล้ว
(พ่อครัวเข้ามากด "ของหมด") · ยืนยันบนเซิร์ฟเวอร์จริง: ครัวยิง `/admin` ได้ **307 → /admin/menu**

**เมนู "สรุปวันนี้" ไม่ขึ้นเลยสำหรับตำแหน่งที่ดูไม่ได้** — ปุ่มที่กดแล้วเด้งกลับทำให้
คนกดสรุปว่าระบบเสีย (กฎเดียวกับปุ่ม "กลับไปหน้าร้าน" ที่ซ่อนจากครัวอยู่แล้ว)

## 4. หนี้ทางเทคนิคที่เก็บไปด้วย

`dayRangeToUtc()` เคยเป็น **สำเนาสองชุด** ใน `receipt.ts` กับ `audit.ts` พร้อมคอมเมนต์ว่า
*"ยังไม่ยุบ รอผู้ใช้รายที่สามที่จะบอกว่ารูปร่างที่ถูกคืออะไร"* — Dashboard คือรายที่สาม
และสิ่งที่มันต้องการคือ "ตั้งแต่เที่ยงคืนของสาขาถึงตอนนี้" ซึ่งยังเป็นช่วงวันเหมือนเดิม
จึงยุบเป็น **`lib/server/branch-time.ts`** ได้ตามที่คอมเมนต์นั้นวางเงื่อนไขไว้

- `startOfBranchDayUtc()` · `branchDayRangeUtc()` · **`branchTodayRangeUtc()`** (ตัวใหม่)
- **ยังไม่ครอบ "ช่วงกะ" ของบทที่ 15** (ปิดกะตีสองแต่วันยังไม่เปลี่ยน) ตัวนั้นต้องอ้าง
  เวลาเปิด/ปิดกะจริงจากตาราง ไม่ใช่คำนวณจากวันที่ — เขียนกำกับไว้ในไฟล์แล้วว่าอย่ายัดเข้ามา
- `smoke:receipt` (82) และ `smoke:staff-meal` (78) ยังผ่านครบหลังยุบ = ตัวกรองวันไม่เปลี่ยนพฤติกรรม

## 5. สิ่งที่จงใจไม่ใส่ และเหตุผล

- **กำไรขั้นต้น** — ต้องมี `MenuItem.costPrice` ซึ่งยังไม่มี (spec §4)
- **ของใกล้หมด** — ต้องมีสต็อก (บทที่ 14)
- **กราฟย้อนหลังหลายวัน** — บทที่ 15 ที่ต้องคิดเรื่องช่วงกะด้วย

ทั้งสามข้อ **เขียนบอกไว้บนหน้าจอตรง ๆ** ว่ายังไม่มีและเพราะอะไร แทนที่จะวางช่องว่างหรือ
ใส่ตัวเลขปลอมไว้ — ช่องที่ขึ้น "—" ตลอดกาลทำให้คนเลิกดูทั้งหน้า
