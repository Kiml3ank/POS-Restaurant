## 2. เรื่องที่ต้องรู้ก่อนแตะโค้ดนี้

### 2.1 กับดัก `sr-only` ที่ทำให้ "ทั้งหน้าเลื่อนได้" — ⚠ สำคัญที่สุดในก้อนนี้

**อาการ:** เปิด `/admin/menu` แล้วเลื่อนหน้าลงได้ทั้งหน้า แถบหัวจอหลุดหายไป
และมีพื้นที่ว่างเปล่าอยู่ใต้แอป — ทั้งที่เชลล์เป็น `h-dvh overflow-hidden`

**สาเหตุ:** `sr-only` ของ Tailwind คือ `position: absolute` — ถ้าไม่มีบรรพบุรุษที่ถูก
position ไว้ containing block ของมันคือ **initial containing block (viewport)**
มันจึง **ไม่ถูก `overflow: hidden` ของเชลล์ตัด** และไปดันความสูงของทั้ง document
ตามตำแหน่งที่มันอยู่ในลิสต์ที่เลื่อนได้ (ป้ายบอกปุ่ม "เลื่อนขึ้น/เลื่อนลง" ขนาด 1×1px
ที่มองไม่เห็นเลย ทำให้หน้าเลื่อนได้เพิ่มอีก 184px)

**หลักฐานที่ชี้ตัวได้:** บังคับ `height:100px` ให้กล่องที่เลื่อนได้แล้วความสูงเอกสาร
**ไม่เปลี่ยน** · สั่ง `overflow:hidden` ที่ `<main>` ก็ไม่เปลี่ยน · แต่ `display:none`
ที่กล่องนั้นแก้ได้ → แปลว่าเนื้อหาข้างในหลุดออกจากการตัดของทุกบรรพบุรุษ

**ทางแก้:** `position: relative` ที่ `.pos-skin` ใน `app/globals.css` **บรรทัดเดียว
แก้ครบทั้งสามจอ** เพราะทำให้เชลล์กลายเป็น containing block ของลูกที่ absolute ทั้งหมด
(ไม่มีผลต่อหน้าตาเพราะเชลล์ไม่ได้ตั้ง top/left) และใส่ `relative` ที่ปุ่มด้วยอีกชั้น

**ทำไมไม่เจอตอนทำบทก่อน ๆ:** เพราะ `overflow-audit` ที่ใช้มาตลอดวัด **แนวนอน**
อย่างเดียว (`scrollWidth > innerWidth`) — บั๊กนี้เป็นแนวตั้ง
→ ตอนนี้มีสคริปต์วัดแนวตั้งแล้ว (`vscroll.mjs` ใน scratchpad) **ต้องรันทั้งสองแกน**

### 2.2 ต้องมีทางกลับไป POS

ผู้ใช้รายงานว่าเข้ามาหลังร้านแล้วต้องกดปุ่ม back ของเบราว์เซอร์เพื่อกลับหน้าร้าน
— ถูกต้อง เพราะเข้ามาจากแถบโมดูลของ POS แต่ไม่มีทางออกในระบบ
เพิ่ม "‹ กลับไปหน้าร้าน (POS)" ที่ท้ายเมนูข้าง และปุ่ม ‹ ที่แถบล่างของจอแคบ
(แท็บเล็ตที่รันแบบ kiosk อาจไม่มีปุ่ม back ให้กดเลย)

### 2.3 `menu.changed` ต้องถูกอนุญาตให้ถึงลูกค้าเป็นรายชื่อ

SSE กรองให้ลูกค้าเห็นเฉพาะ event ที่ `tableId` ตรงโต๊ะตัวเอง — แปลว่า event ระดับสาขา
(`tableId: null`) **ไม่มีวันถึงมือถือลูกค้า** ซึ่งเป็นสิ่งที่ตอนเขียน spec มองข้ามไป

แก้ด้วยรายชื่อ **opt-in** `CUSTOMER_BROADCAST_EVENTS` (ตอนนี้มีตัวเดียว) ไม่ใช่เปลี่ยนกฎ
เป็น "ปล่อย null ทุกตัว" เพราะวันหนึ่งจะมี event ระดับสาขาที่ลูกค้าไม่ควรเห็น
(เช่น "ปิดกะแล้ว" ของบทที่ 15 ที่บอกได้ว่าร้านทำยอดเท่าไหร่)
— มีเคสทดสอบตรึงรายชื่อนี้ไว้ ถ้าเพิ่มต้องมาแก้เทสต์ด้วยมือ

ทดสอบจริงแล้ว: เปิดสาย SSE ของลูกค้าโต๊ะ A1 ค้างไว้ → กด "ของหมด" จากหลังร้าน
→ ลูกค้าได้รับ `{"type":"menu.changed","tableId":null}` จริง

### 2.4 การลบมีสองแบบ และเลือกให้อัตโนมัติ

| กรณี | ผล |
|---|---|
| เมนูที่ไม่เคยถูกสั่ง | ลบจริงได้ (เมนูพิมพ์ผิดต้องลบทิ้งได้ ไม่งั้นค้างตลอดกาล) |
| เมนูที่เคยถูกสั่ง | ปฏิเสธ + บอกให้ใช้ "ปิดขาย" แทน |
| หมวดที่ยังมีเมนู | ปฏิเสธ + บอกจำนวนเมนูที่ต้องย้ายออกก่อน |
| กลุ่มตัวเลือกที่ยังผูกกับเมนู | ปฏิเสธ + บอกว่าผูกอยู่กี่เมนู |
| ตัวเลือกที่ถูกเอาออกจากฟอร์มกลุ่ม | **ปิดขายอัตโนมัติ ไม่ลบ** (บิลเก่าอ้างถึงอยู่) |

เช็คเองก่อนเสมอ ไม่ปล่อยให้ `onDelete: Restrict` ของ Postgres โยน FK error
ภาษาอังกฤษดิบ ๆ ให้พนักงานอ่าน

### 2.5 `minSelect` ที่มากกว่าจำนวนตัวเลือก = ลูกค้าติดตาย

กฎที่ตรวจฝั่ง server ทุกครั้ง: `maxSelect >= minSelect >= 0` · `maxSelect >= 1` ·
`required → minSelect >= 1` · และ **`minSelect <= จำนวนตัวเลือกในกลุ่ม`**

ข้อสุดท้ายคือข้อที่พังเงียบที่สุด เพราะมันพัง **ที่หน้าลูกค้า** (กดใส่ตะกร้าไม่ผ่าน
ตลอดกาล) ไม่ใช่ที่หน้าที่กดแก้ — ถ้าไม่กันไว้จะไม่มีใครรู้จนกว่าลูกค้าจะบ่น

### 2.6 `sortOrder` เขียนใหม่ทั้งชุด ไม่ใช่สลับค่าสองแถว

`sortOrder` ไม่มี unique constraint ถ้าสองแถวค่าเท่ากันแล้วแค่ "สลับค่า" จะไม่มีอะไร
ขยับเลย แล้วปุ่มจะดูเหมือนเสียโดยไม่มี error — จึงเรียงด้วย `[sortOrder, id]`
สลับตำแหน่งในอาเรย์ แล้วเขียนเลขใหม่ให้ทุกแถวที่เปลี่ยน (ล้างค่าซ้ำทิ้งในตัว)
มีเคสทดสอบที่จงใจตั้งค่าให้ซ้ำกันก่อนแล้วสั่งเลื่อน

### 2.7 แยกไฟล์ `menu-admin.ts` ออกจาก `menu.ts`

`lib/server/menu.ts` เป็นทางอ่านของหน้าลูกค้าที่กรอง `isAvailable` ทุกชั้นตั้งแต่ใน query
ส่วนหลังร้านต้องเห็นของที่ปิดขายอยู่ด้วย ถ้ารวมไฟล์เดียวจะเกิด flag
`includeUnavailable` วิ่งไปทุกฟังก์ชัน แล้ววันหนึ่งจะมีใครลืมส่ง
แล้วเมนูที่ปิดอยู่จะโผล่บนมือถือลูกค้าโดยไม่มีอะไรฟ้อง

### 2.8 AuditLog เก็บราคาก่อน-หลังเสมอ

`menu.<entity>.create|update|availability|reorder|delete` ทุกตัวเขียนในทรานแซกชัน
เดียวกับการแก้ และเก็บค่าก่อน-หลังของราคาเสมอ **แม้ราคาจะไม่เปลี่ยน** เพราะสิ่งที่ต้อง
ตอบให้ได้ย้อนหลังคือ "ราคาช่วงนั้นเท่าไหร่" ไม่ใช่แค่ "ครั้งไหนที่เปลี่ยน" —
การขึ้นราคาแล้วลดกลับใน 10 นาทีจะอ่านได้เป็นสองแถวเรียงกัน (เคสโกงในบทที่ 13)
