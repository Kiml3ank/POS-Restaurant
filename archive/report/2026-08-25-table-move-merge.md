## 1. ทำอะไรไปบ้าง

เส้นทางใหม่ของพนักงาน: บนหน้าโต๊ะ (`/pos/table/[tableId]?view=bills`) มีแผง
**"ย้ายโต๊ะ / รวมบิลกับโต๊ะอื่น"** — กลุ่มบนคือโต๊ะว่าง (ย้าย) กลุ่มล่างคือโต๊ะที่มี
บิลเปิดอยู่ (รวม พร้อมยอดของโต๊ะนั้น)

| Task | ของที่ได้ |
|---|---|
| 1 | `TableSessionStatus.MERGED` + `mergedIntoSessionId` (self-relation, `onDelete: SetNull`) |
| 2 | `moveTableSession()` — ย้ายทั้งรอบใน `$transaction` เดียว |
| 3 | `mergeTableSessions()` — กลืนรอบต้นทาง + ยุบตะกร้าสองใบให้เหลือใบเดียว |
| 4 | `resolveSessionByToken()` — มือถือลูกค้าเดินตามโซ่ merge + แถบบอกบนหน้าเมนู |
| 5 | `getMoveTargets()` + `moveTableAction` / `mergeTableAction` + แผงบนหน้าโต๊ะ |
| 6 | ตรวจครบชุด · วัดจอ · เอกสาร (ไฟล์นี้) |

**ชั้นคิดเงิน / รับเงิน / ใบเสร็จ / KDS ไม่ถูกแก้เลยสักบรรทัด** — ทั้งหมดอ่านจาก
`Order.tableSessionId` / `Order.tableId` ซึ่งการย้ายอัปเดตให้แล้วในทรานแซกชันเดียว
เคสสุดท้ายของ smoke รับเงินบิลที่ผ่านการรวมมาแล้วจนออกใบเสร็จ เพื่อพิสูจน์ข้ออ้างนี้
ด้วยของจริง ไม่ใช่ด้วยการอ่านโค้ด

## 2. กฎที่ต้องรู้ก่อนแตะโค้ดส่วนนี้

- **`lib/server/table-move.ts` เป็น leaf module** — ห้ามมีไฟล์ใน `lib/server/`
  import กลับมาที่นี่ (ท่าเดียวกับ `receipt-issue.ts` ของบทที่ 12)
- **`loadMovableSession()` คือด่าน "รอบนี้ขยับได้ไหม" ที่เดียว** ทั้งย้ายและรวมเรียกตัวนี้
  (รวมเรียกสองครั้ง: ต้นทาง/ปลายทาง) — สาขาเดียวกัน · `OPEN` · ไม่มี `Payment` ·
  ไม่ติดธงส่วนลดพนักงาน · `kind === DINE_IN`
  **ห้ามก๊อปเงื่อนไขไปเขียนซ้ำ** ที่ที่ลืมไปข้อหนึ่งคือประตูหลังที่เปิดค้าง
  (บทเรียนเดียวกับ `loadActiveStaffSession()` ของบทที่ 13b) และที่นี่ประตูหลังแปลว่า
  "ขยับเงินของบิลที่ปิดไปแล้วได้"
- **สองฟังก์ชัน ไม่ใช่ตัวเดียวที่เดาเอง** — ฟังก์ชันเดียวที่ดูว่าปลายทางว่างไหมแล้ว
  ตัดสินใจเองว่าจะย้ายหรือรวม แปลว่าคนที่ตั้งใจ *ย้าย* แล้วเผลอเลือกโต๊ะที่มีคนนั่ง
  จะได้ผลลัพธ์เป็นการ *รวมบิลของคนอื่น* ซึ่ง **แยกกลับไม่ได้**
  (ย้ายผิดแก้ได้ด้วยการย้ายกลับ · รวมผิดแก้ไม่ได้เพราะของอาจถูกเสิร์ฟ/ยกเลิกไปแล้ว)
- **ย้าย `DRAFT` ไปด้วยเสมอ** ตะกร้าที่ค้างอยู่กับรอบที่ถูกปิดคือของที่หายจากสายตาทุกคน ·
  `CANCELLED` ไม่ย้าย มันเป็นประวัติของโต๊ะเดิม
- **`pax` บวกกันตอนรวม** ไม่ใช่ตัวเลขประดับ — เป็นตัวหารของรายงานยอดขายต่อหัวบทที่ 15
  ถ้าปล่อยไว้เท่าเดิม โต๊ะที่ผ่านการรวมจะมียอดต่อหัวสูงเกินจริงทุกใบ
- **ค่า `MERGED` มีอยู่ในระบบแล้ว** — query ที่ถามสถานะรอบต้องคิดถึงมันเสมอ
  `status: "OPEN"` ยังปลอดภัยเหมือนเดิม แต่ `status: { not: "CLOSED" }` ไม่ใช่แล้ว
- **AuditLog เก็บยอดทั้งสองก้อน** (`movedAmount` + `targetAmountBefore`) ถึงจะตอบได้ว่า
  *เงินก้อนไหนรวมกับก้อนไหน* ไม่ใช่แค่ *มีการรวมเกิดขึ้น*

## 3. กับดักที่เจอจริงระหว่างทำ (ไม่ได้อยู่ในแผน)

### 3.1 ตะกร้าที่ไม่มีใครมองเห็น แต่บล็อกการคิดเงินไว้ตลอดกาล

`getCart()` (และทุกหน้าจอที่เรียกมัน) เป็น **`findFirst` บน `status: "DRAFT"`
ของรอบนั้น** พอรวมสองโต๊ะที่ต่างก็มีตะกร้าค้างอยู่ รอบปลายทางจะมีตะกร้าสองใบ
แล้ว **ใบหนึ่งจะไม่มีใครเห็นเลยทั้งจอพนักงานและมือถือลูกค้า** — แต่ยังบล็อกการคิดเงินอยู่
เพราะกฎบทที่ 11 บอกว่า "ตะกร้า `DRAFT` ที่มีของ = จ่ายไม่ได้"

อาการที่หน้าร้าน: แคชเชียร์เห็นตะกร้าว่าง กดรับเงินแล้วขึ้นว่ามีของค้างในตะกร้า
โดยไม่มีทางรู้ว่าของอยู่ที่ไหน

แก้ที่ `foldDraftCarts()` — ย้าย `OrderItem` ของตะกร้าต้นทางเข้าตะกร้าปลายทาง
คิด `subtotal` ใหม่ แล้วลบใบเปล่าทิ้ง (ตะกร้าที่ยังไม่เคยกดส่งไม่ใช่ประวัติ:
ไม่มีเงิน ไม่มีใบเสร็จ ครัวไม่เคยเห็น — ต่างจาก `CANCELLED` ที่เป็นประวัติจริง)
เคสนี้ถูกจับได้เพราะ smoke ไล่ไปจนถึงการรับเงิน ถ้าหยุดที่ "รวมแล้วยอดถูก" จะเขียวผ่าน

### 3.2 `movedOrders` นับ "ใบที่ถูก update" ไม่ใช่ "ใบที่ออกไปจากรอบต้นทาง"

พอตะกร้าถูกยุบ (ของย้าย ใบถูกลบ) จำนวนแถวที่ถูก `updateMany` จะน้อยกว่าจำนวน
ออร์เดอร์ที่หายไปจากรอบต้นทางหนึ่งใบ — ข้อความบนหน้าจอกับ AuditLog จะบอกจำนวน
น้อยกว่าที่ขยับจริง ตอนนี้นับเป็น `moved.count + (folded ? 1 : 0)` และมี
`foldedDraftCart` ใน metadata ให้ตรวจย้อนหลังตรงกัน

### 3.3 หน้าลูกค้า: cookie ผูก `tableId` = บิลผีทันทีที่พนักงานย้ายโต๊ะ

`resolveCustomerContext()` เดิมหา session ด้วย `token` **บวก `tableId`**
ซึ่งถูกต้องตอนที่รอบขายย้ายโต๊ะไม่ได้ พอย้ายได้แล้ว ลูกค้าที่ถือ cookie ใบเดิมจะได้
"ไม่มีรอบ" ทันที แล้วถ้ากดเปิดโต๊ะใหม่ = **บิลใบที่สองที่พนักงานไม่รู้ตัว**

`resolveSessionByToken(branchId, token)` เดินตาม `mergedIntoSessionId` ไปจนถึงรอบที่
ยังเปิดอยู่ (ลึกสุด 5 ชั้น กันโซ่ที่วนกลับมาที่เดิมไม่ให้ค้างทั้ง request)
ราคาที่จ่ายแทน: cookie ใบหนึ่งใช้ได้กับหน้าโต๊ะไหนก็ได้ **ในสาขาเดียวกัน** —
คนที่ถือ cookie ของตัวเองไปเปิดหน้าโต๊ะอื่นจะยังสั่งเข้าบิลของตัวเอง ไม่ใช่บิลคนอื่น
และหน้าจอขึ้นบอกว่าของเข้าบิลไหน

ผลพลอยได้ที่ต้องแก้ตาม: `addToCartAction()` ต้องใช้ `context.session.tableId`
**ไม่ใช่ `context.table.id`** ไม่งั้นออร์เดอร์จะชี้โต๊ะที่สแกนมา ทั้งที่รอบอยู่โต๊ะใหม่
แล้วตั๋วครัวกับใบเสร็จจะเรียกชื่อโต๊ะผิด

### 3.4 เครื่องมือวัดจอพลาดสองทาง — ครั้งที่สี่แล้วที่สคริปต์เขียวทั้งที่ควรแดง

- **ของที่พับอยู่ใน `<details>` ไม่มีความสูง** สคริปต์จึงตอบ "ไม่ล้น" ได้เสมอ
  ทั้งที่ตอนคนกดกางจริงอาจดันจอพัง → เพิ่ม `openDetails: true`
- **ตัวหาข้อความกรองด้วย `children.length === 0`** ซึ่งพลาดสองทาง: ข้อความที่มี
  `<strong>` คั่นกลางจะไม่มีใบไหนถือครบประโยค · และ **`<script>` ของ RSC payload
  เป็นใบและมีข้อความนั้นอยู่** สคริปต์จึงไปวัดแท็ก `script` แล้วรายงานว่า
  "ถูกซ่อนทุกตัว" ทั้งที่ของอยู่บนจอจริง → เปลี่ยนเป็นหา element ที่ลึกที่สุด
  ที่ยังมีข้อความนั้นครบ และข้าม `SCRIPT/STYLE/NOSCRIPT/TEMPLATE`
- เพิ่ม `scrolls: true` สำหรับหน้าจอลูกค้าที่ตั้งใจให้ทั้งหน้าเลื่อนได้
  (ไม่ได้อยู่ในเชลล์ `h-dvh overflow-hidden` ของจอพนักงาน) — **ห้ามใส่ให้หน้าในเชลล์**
  เพราะที่นั่น "ทั้งหน้าเลื่อนได้" คือสัญญาณของบั๊กจริง

## 4. ตัวเลขที่ยืนยันด้วยของจริง

จาก `npm run smoke:table-move` (สาขา THB · VAT ในราคา · เซอร์วิสชาร์จ 10%):

| | ค่าอาหาร | ยอดรวม |
|---|---|---|
| บิลต้นทาง | 12000 | 13200 |
| บิลปลายทาง | 12000 | 13200 |
| **หลังรวม** | **24000** | **26400** |

- `netAmount + vatAmount === grandTotal` ทุกครั้ง (24673 + 1727 = 26400)
- ยอดหลังรวมต่างจากผลบวกของยอดสองใบไม่เกินสองหน่วยย่อย = **คิดครั้งเดียวบนยอดรวม**
  ไม่ใช่บวกยอดที่ปัดเศษมาแล้วสองรอบ (กฎบทที่ 10)
- ตะกร้าสองใบ (2000 + 2000) ยุบเหลือใบเดียว 4000 · ยอดสุดท้ายหลังส่งเข้าครัว 28000
- ย้ายโต๊ะแล้วยอดเท่าเดิมเป๊ะทั้ง `subtotal` และ `grandTotal`

ตรวจกับเซิร์ฟเวอร์จริง (`npm run build` + `npm run start -- -p 3002`):
หน้าโต๊ะ A2 แสดงปุ่มย้าย 3 โต๊ะ + ปุ่มรวมกับ B1 พร้อม `targetSessionId` ที่ถูกต้อง ·
หลังรวมแล้วหน้าโต๊ะปลายทางตอบ 200 และโต๊ะต้นทางกลับเป็นจอเปิดโต๊ะ ·
จอเคาน์เตอร์ซื้อกลับไม่มีแผงนี้ · มือถือลูกค้าของโต๊ะที่ถูกกลืนขึ้นแถบบอกปลายทางจริง

## 5. ยังไม่ได้ทำ

- **แยกบิล** (งานค้างที่เหลืออยู่ข้อเดียวจากบทที่ 9) — ตรงข้ามกับการรวม และยากกว่า
  เพราะต้องตัดสินว่า *รายการไหนไปบิลไหน* ไม่ใช่แค่ขยับทั้งชุด
- **ย้ายรายการเดี่ยว ๆ ข้ามโต๊ะ** (สั่งผิดโต๊ะ) — ตอนนี้ต้องยกเลิกแล้วสั่งใหม่
- ปุ่ม "ยกเลิกการรวม" — ตั้งใจไม่มี เพราะหลังรวมแล้วของอาจถูกเสิร์ฟ/ยกเลิกไปแล้ว
  การแยกอัตโนมัติจึงเป็นการเดาว่าของชิ้นไหนเป็นของใคร
