## 1. สองเรื่องในก้อนเดียว และทำไมต้องมาด้วยกัน

ก้อนนี้ตั้งใจทำบทที่ 10 อย่างเดียว แต่ระหว่างทางมีคำขอเพิ่ม **"อยากใช้ที่ลาวกับ
เวียดนามด้วย"** ซึ่งต้องทำพร้อมกันไม่ใช่ทำทีหลัง เพราะทั้งสองเรื่องแตะเลขก้อนเดียวกัน:

ถ้าทำหน้าคิดเงินให้เสร็จบนสมมติฐาน "เงินคือสตางค์ หาร 100 เสมอ" ก่อน แล้วค่อยมา
เพิ่มสกุลเงินทีหลัง จะต้องรื้อหน้าคิดเงินทั้งหน้าอีกรอบ — และที่แย่กว่าคือ
ระหว่างนั้นจะมีโค้ดที่หาร 100 กระจายอยู่หลายที่ ซึ่งพอลืมแก้จุดใดจุดหนึ่ง
**ราคาจะผิดร้อยเท่าโดยไม่มีอะไรฟ้อง**

## 2. สกุลเงิน — เลขก้อนเดียวกันแปลว่าคนละมูลค่า

### สิ่งที่ต้องเข้าใจก่อนแตะโค้ดเงิน

เลข `6000` ในคอลัมน์ราคา **ไม่ได้แปลว่า 60.00 เสมอไป**:

| สาขา | 6000 หมายถึง | ทศนิยม |
|---|---|---|
| ไทย (THB) | 60.00 บาท | 2 (สตางค์) |
| ลาว (LAK) | 6,000 กีบ | 0 |
| เวียดนาม (VND) | 6.000 ₫ | 0 |

จึงมีกฎใหม่: **ห้ามหารด้วย 100 ที่ไหนก็ตามนอก `lib/money.ts`** และห้ามเขียน "฿"
ลงในหน้าจอตรง ๆ ทุกที่ที่แสดงเงินต้องเรียก `formatMoney(amount, currency)`

### ทำไม LAK กับ VND ไม่มีทศนิยม

- **VND**: ISO 4217 กำหนดหน่วยย่อยเป็น 0 อยู่แล้ว (hào/xu เลิกใช้ไปนานแล้ว)
- **LAK**: ISO 4217 ยังระบุ att ไว้ **แต่ att ไม่มีหมุนเวียนจริงแล้ว** ร้านค้าในลาว
  ตั้งราคาเป็นกีบเต็มจำนวนทั้งหมด ถ้าเก็บทศนิยมไว้ พนักงานจะกรอกราคาผิดร้อยเท่า
  (พิมพ์ 50000 คิดว่า 50,000 กีบ แต่ระบบอ่านเป็น 500 กีบ)

  ถ้าวันหนึ่งต้องใช้ att จริง ให้แก้ `decimals` ของ LAK ที่เดียวในตาราง
  **แล้วต้องแปลงข้อมูลราคาที่มีอยู่ด้วย migration ห้ามแก้เฉย ๆ**

### รูปแบบการแสดงผลไม่ได้ต่างแค่สัญลักษณ์

```
THB  12000   → ฿120.00        สัญลักษณ์นำหน้า · คั่นพันด้วย , · ทศนิยม .
LAK  120000  → ₭120,000       สัญลักษณ์นำหน้า · ไม่มีทศนิยม
VND  120000  → 120.000 ₫      สัญลักษณ์ต่อท้าย · คั่นพันด้วย . (ไม่ใช่ ,)
```

เวียดนามคั่นหลักพันด้วย **จุด** — "6.000 ₫" คือหกพันดอง ไม่ใช่หกดอง
ถ้าใช้รูปแบบไทยไปแสดงในเวียดนาม ลูกค้าจะอ่านราคาผิดพันเท่า

`formatAmount()` ประกอบสตริงเองด้วยจำนวนเต็มล้วน **ไม่ใช้ `Intl.NumberFormat`**
เพราะ Intl ผูกกับ locale ของเครื่องที่รัน ซึ่ง server กับ browser ของลูกค้าอาจ
ไม่ตรงกัน แล้วจะเกิด hydration mismatch ที่โผล่เป็น "ราคากะพริบเปลี่ยนเลข"

### `Branch.currency` เปลี่ยนจาก String เป็น enum

```prisma
enum Currency { THB LAK VND }
```

เพราะการเพิ่มสกุลเงินไม่ใช่แค่เปลี่ยนสัญลักษณ์ — จำนวนทศนิยมไม่เท่ากัน
ถ้าปล่อยเป็น String แล้วมีใครพิมพ์ `"thb"` หรือ `"USD"` ลงไป ระบบจะแสดงราคาผิด
โดยไม่มีอะไรฟ้อง

ตารางใน `lib/money.ts` ประกาศเป็น `Record<Currency, CurrencyConfig>` จึง
**บังคับด้วย tsc** ว่าเพิ่มสมาชิกใน enum แล้วต้องมาเพิ่มรูปแบบการแสดงผลด้วย

#### migration เขียนเอง ไม่ให้ generator เขียนให้ ⚠

`prisma migrate dev` เลือกวิธี **DROP คอลัมน์เดิมแล้วสร้างใหม่** ซึ่งทำให้ค่าที่มี
อยู่หายทั้งตาราง (บนเครื่อง dev มีสาขาเดียวจึงไม่รู้สึก แต่บน production คือ
**ทุกสาขาที่ขายเป็นกีบ/ดอง กลายเป็นบาทพร้อมกัน**)

จึงเขียน SQL เองเป็น cast ในที่:

```sql
ALTER TABLE "branches"
  ALTER COLUMN "currency" DROP DEFAULT,
  ALTER COLUMN "currency" TYPE "Currency" USING ("currency"::"Currency"),
  ALTER COLUMN "currency" SET DEFAULT 'THB';
```

ถ้ามีแถวไหนเป็นค่าที่ไม่ใช่สมาชิกของ enum คำสั่งนี้จะ error แล้ว rollback ทั้งก้อน
— ซึ่งเป็นสิ่งที่ต้องการ ดีกว่าเงียบ ๆ แล้วข้อมูลเพี้ยน
(ใช้ `prisma migrate deploy` apply เพราะ `migrate dev` เป็นคำสั่ง interactive)

## 3. `calculateBill()` — ที่เดียวในระบบที่คิดยอดสุดท้าย

### ลำดับ: เซอร์วิสชาร์จ → VAT

เซอร์วิสชาร์จคือ "ค่าบริการ" ที่ร้านเรียกเก็บ = รายได้ของร้าน จึงเป็นฐานภาษีด้วย
ถ้าสลับลำดับเป็น VAT → เซอร์วิสชาร์จ **ยอด VAT ที่ต้องนำส่งจะขาดทุกบิล**
(ในตัวอย่างง่าย ๆ ยอดสุดท้ายอาจบังเอิญเท่ากันเพราะเป็นการคูณต่อกัน แต่ตัวเลข
VAT ที่ต้องขึ้นใบกำกับภาษีต่างกัน: 77 กับ 70)

### สองโหมดที่ให้ตัวเลขคนละชุด

**`pricesIncludeVat = false`** (ราคายังไม่รวม VAT) — บวกเพิ่ม
```
1,000 → +100 (เซอร์วิส 10%) = 1,100 → +77 (VAT 7%) = 1,177
```

**`pricesIncludeVat = true`** (ราคารวม VAT แล้ว) — **ถอดออกมาแสดง ไม่ใช่บวกเพิ่ม**
```
1,000 → +100 (เซอร์วิส 10%) = 1,100 ← ยอดที่ลูกค้าจ่าย
VAT ที่ถอดได้ = 1,100 × 7 ÷ 107 = 71.96
มูลค่าสินค้า = 1,100 − 71.96 = 1,028.04
```

ห้ามใช้ `ยอดรวม × 7%` ตรง ๆ ในโหมดนี้ — จะได้ 77 ซึ่งเป็นการคิด VAT ของยอดที่มี
VAT อยู่แล้ว เกินความจริงและทำให้ยอดนำส่งภาษีผิดทุกบิล (มีเคสทดสอบจับเรื่องนี้)

### การปัดเศษด้วยจำนวนเต็มล้วน

```ts
const product = amount * bp;
const remainder = product % 10000;
const quotient = (product - remainder) / 10000;  // หารลงตัวเป๊ะ
return remainder * 2 >= 10000 ? quotient + 1 : quotient;
```

ตั้งใจไม่ใช้ `Math.round(amount * bp / 10000)` เพราะนั่นคือหารแบบ float แล้วปัด
ซึ่งเป็นจุดที่เงินเพี้ยนทีละสตางค์แบบหาสาเหตุไม่เจอ

ปัด **ครึ่งขึ้น** ตามที่ร้านอาหารไทยใช้กันทั่วไป **แต่กฎหมายไม่ได้บังคับ** —
ถ้าผู้สอบบัญชีให้ปัดลงหรือปัดแบบธนาคาร แก้ที่ฟังก์ชันเดียวแล้วทั้งระบบเปลี่ยนตาม

### รับประกันสองข้อเสมอ

1. `netAmount + vatAmount === grandTotal` (ไม่มีสตางค์หายระหว่างทาง)
2. ทุกค่าที่คืนออกไปเป็นจำนวนเต็ม

ในโหมดรวม VAT ได้ข้อ 1 มาฟรีเพราะ `netAmount` คำนวณจาก `grandTotal − vatAmount`
ไม่ได้คิดใหม่แยก

## 4. หนึ่งบิล = หนึ่ง "รอบโต๊ะ" ไม่ใช่หนึ่ง Order

ลูกค้าโต๊ะเดียวสั่งเป็นรอบได้หลายใบ แต่ตอนคิดเงินคือใบเดียว `getTableBill()` จึง
รวม subtotal ของทุกออร์เดอร์ที่ยังมีชีวิตในรอบนั้น **แล้วค่อยคิดเซอร์วิสชาร์จ
กับ VAT ครั้งเดียวจากยอดรวม**

เหตุผลไม่ใช่ความสวยงาม — คิดทีละใบแล้วบวกจะปัดเศษหลายรอบ:

```
สามใบ ใบละ 33.33 → เซอร์วิส 10% = 3.33 × 3 = 9.99
รวมก่อนคิด 99.99 → เซอร์วิส 10%          = 10.00
```

ต่างกันหนึ่งสตางค์ต่อบิล ซึ่งพอสิ้นเดือนคือยอดที่กระทบงบจริงและอธิบายไม่ได้
(มีเคสทดสอบยืนยันว่าสองวิธีให้คนละค่า)

**รายการไม่ถูกยุบรวมกันแม้เป็นเมนูเดียวกัน** ถ้ามาจากคนละรอบ — ลูกค้าที่จำได้ว่า
สั่งกะเพราสองรอบ แล้วเห็นบิลเขียน "กะเพรา 3" จะเริ่มไม่แน่ใจว่าโดนคิดเกินหรือเปล่า

## 5. ขอบเขต: บทนี้ "คิด" กับ "แสดง" เท่านั้น

หน้า `/pos/table/[tableId]/bill` เป็นหน้าอ่านอย่างเดียว **ยังไม่มีปุ่มรับเงิน**
และตั้งใจไม่ใส่ปุ่มปลอมที่กดแล้วไม่เกิดอะไร — พนักงานที่กดปุ่มแล้วเงียบจะกดซ้ำ
แล้วเชื่อว่าระบบพัง

ที่ยังไม่ทำและเป็นของบทถัดไป:

| งาน | บท |
|---|---|
| รับเงิน (PromptPay QR / บัตร / เงินสด) | 11 |
| ปิดบิล SERVED → PAID + เขียนยอดลง `Order` | 11 |
| snapshot อัตราลง `serviceChargeBp` / `vatRateBp` / `pricesIncludeVat` ของ `Order` | 11 |
| เลขที่ใบกำกับภาษีที่ต้องเดินต่อเนื่อง + ใบเสร็จ | 12 |
| ปุ่มส่วนลด (สูตรรองรับแล้ว แต่ยังไม่มี UI) | 13 |

**อัตราที่ใช้ตอนนี้มาจาก `Branch` (ค่าปัจจุบัน) ไม่ใช่ snapshot** เพราะบิลยังไม่ปิด
ยอดที่แสดงคือ "ถ้าคิดเงินตอนนี้จะเป็นเท่าไหร่" — ตอนปิดบิลจริงในบทที่ 11
ต้องคัดลอกอัตราลง `Order` แล้วใบเสร็จย้อนหลังอ่านจากตรงนั้นเท่านั้น

### ส่วนลดยังไม่มีปุ่ม — โดยตั้งใจ

`discountAmount` รองรับในสูตรแล้ว (และมีเคสทดสอบว่าหักก่อนคิดเซอร์วิสชาร์จ +
ไม่ยอมให้บิลติดลบ) แต่ยังไม่มี UI เพราะส่วนลดคือช่องโกงอันดับต้น ๆ ของหน้าร้าน
การเปิดปุ่มต้องมาพร้อมสามอย่างเสมอ: จำกัดตามตำแหน่ง · บังคับกรอกเหตุผล ·
เขียน `AuditLog` — ชุดเดียวกับที่ `cancelOrderItemByStaff()` ทำอยู่แล้ว

## 6. หน้าจอ

ทางเข้า: ปุ่ม **"คิดเงิน"** สีแดงเต็มใบบนแถบแท็บของหน้าโต๊ะ โผล่เฉพาะตอนมีบิล
ที่ส่งเข้าครัวแล้วจริง ไม่ใช่ปุ่มที่อยู่ตลอดแล้วกดไปเจอหน้าเปล่า

**ทำไมแยกเป็นหน้าใหม่ ทั้งที่ CLAUDE.md ห้ามแยกเมนูกับตะกร้า:** กฎข้อนั้นคุมจังหวะ
"รับออร์เดอร์" ซึ่งพนักงานคุยกับลูกค้าไปกดไป จอเปลี่ยนไม่ได้ · การคิดเงินเป็นจังหวะ
คนละแบบ: หยุดคุย ยืนอ่านตัวเลขด้วยกันกับลูกค้า จอควรมีแต่ตัวเลขบิล ไม่มีเมนูให้กดพลาด

จอนี้ต่อ SSE ด้วย เพราะยอดเปลี่ยนได้ระหว่างที่ยืนอ่านอยู่ ถ้าลูกค้ากดสั่งเพิ่มจากมือถือ

เตือน **"ยังมีของที่ยังไม่ได้เสิร์ฟ N ชิ้น"** เมื่อมีของค้าง — ไม่ได้ห้ามคิดเงิน
(ลูกค้าขอจ่ายก่อนได้ และบางร้านเก็บเงินก่อนเสมอ) แต่พนักงานต้องเห็นก่อนกด ไม่ใช่รู้ทีหลัง

### responsive

- จอกว้าง (`xl`+): สองแพเนลเลื่อนแยกกัน ยอดรวมปักขวา 412px อยู่กับที่ตลอด
- จอแคบ: เลื่อนเป็นหน้าเดียว + ตัดคอลัมน์ "ราคา/หน่วย" ไปไว้ใต้ชื่อเมนูแทน

รอบแรกที่ทำแบ่งเป็นสองกล่องเลื่อนแยกกันทั้งสองขนาด ผลคือที่ 390×800 ตารางรายการ
เหลือพื้นที่ประมาณหนึ่งบรรทัดครึ่ง และชื่อเมนูแตกเป็นสามบรรทัด — เห็นจาก screenshot
ที่เก็บระหว่าง audit ไม่ใช่จากการเดา

## 7. การทดสอบ

```bash
npm run smoke:bill    # 43 เคส
```

แบ่งเป็น: ลำดับ/สองโหมด VAT 11 · ปัดเศษ 5 · ส่วนลด 4 · เคสขอบ 2 ·
สกุลเงิน 14 · ต่อกับ DB จริง 7

เคสที่ต้องไม่พังเด็ดขาด:

- **`netAmount + vatAmount === grandTotal`** ทั้งสองโหมด
- **ถอด VAT ได้น้อยกว่าการคูณ 7% ตรง ๆ** (จับวิธีคิดที่ผิด)
- **คิดทีละใบแล้วบวก ≠ รวมก่อนคิด** (เหตุผลที่ `getTableBill()` รวมก่อน)
- **เลข 50000 เท่ากันแต่คนละสกุล = คนละมูลค่า** (`฿500.00` vs `₭50,000`) —
  ถ้าวันหนึ่งมีใครไป hardcode หาร 100 ไว้ เคสนี้จะพัง
- **VND: สัญลักษณ์ท้าย + คั่นพันด้วยจุด** (`120.000 ₫`)
- ส่วนลดเกินค่าอาหารถูกจำกัด บิลไม่ติดลบ

## 8. ⚠ ก่อน deploy ใช้จริง

**เนื้อหาภาษีในบทนี้ไม่ใช่คำแนะนำทางกฎหมาย** ลำดับการคิด อัตรา และวิธีปัดเศษ
เป็นแบบที่ร้านอาหารไทยใช้กันทั่วไป แต่ต้องให้ผู้สอบบัญชี/สรรพากรตรวจก่อนใช้จริง
โดยเฉพาะ:

- **วิธีปัดเศษ** ที่กฎหมายไม่ได้บังคับตายตัว ร้านต่างเจ้าอาจปัดต่างกัน
- **อัตรา VAT ของลาวและเวียดนาม** ต่างจากไทยและเปลี่ยนบ่อยกว่า
  (เวียดนามมีช่วงลด VAT จาก 10% เหลือ 8% เป็นช่วง ๆ) — ตั้งได้ที่ `Branch.vatRateBp`
