## 2. session เก็บใน DB แล้ว — cookie เหลือหน้าที่แค่ "ชี้แถว"

**`StaffSession`** (migration `20260824113710_staff_session_and_login_throttle`)

- cookie เก็บ `jti` = id ของแถว · ลายเซ็น HMAC ยังทำหน้าที่เดิม (กันปลอม/เดา id ของคนอื่น)
  แต่ **คำตอบว่า "ยังใช้ได้ไหม" มาจาก DB ทุก request**
- **cookie เก่าที่ไม่มี `jti` ถือว่าใช้ไม่ได้ทันที** ทุกคนต้องใส่ PIN ใหม่หนึ่งครั้ง
  — ตั้งใจไม่ทำ fallback เพราะ fallback แปลว่ายังมีทางเข้าที่ยกเลิกไม่ได้ค้างอยู่
  ซึ่งเป็นสิ่งเดียวที่ทั้งบทนี้พยายามปิด
- ราคาที่จ่าย: query เพิ่มต่อ request — **แต่เดิมก็ query `Staff` ทุก request อยู่แล้ว**
  (เพื่อดูว่าบัญชียัง active) ตอนนี้รวมเป็น query เดียวที่ join มาให้เลย
- แถวไม่ถูกลบตอนล็อกจอ ตั้ง `revokedAt` แทน → **"ประวัติการเข้าใช้งาน" เป็นผลพลอยได้
  ไม่ใช่ตารางที่สองที่ต้องเขียนซ้ำ** (spec §26 Login history)
- **`loadActiveStaffSession()` เป็นที่เดียวที่รวมเงื่อนไข "ยังใช้ได้ไหม" ครบชุด**
  (ยังไม่ revoke · ยังไม่หมดอายุ · เป็นของจอนี้ · บัญชียัง active)
  **ห้ามกระจายเงื่อนไขพวกนี้ไปเขียนซ้ำที่อื่น** ที่ที่ลืมไปข้อหนึ่งคือประตูหลังที่เปิดค้าง

**ทำไมแยกเป็นสามไฟล์:** `staff-session.ts` เรียก `cookies()` ของ next/headers จึงรัน
นอก request ของ Next ไม่ได้ = ทดสอบไม่ได้เลย → ตรรกะทั้งหมดย้ายไป
`staff-session-store.ts` กับ `staff-login-throttle.ts` ที่ไม่แตะ cookie
(ท่าเดียวกับ `receipt-issue.ts` ในบทที่ 12) แล้ว smoke เรียกตรงได้

## 3. ตัวนับ PIN ผิดย้ายลง Postgres

`StaffLoginThrottle` — ผิดครบ 5 ครั้ง = ล็อก 5 นาที · **หน้าต่างเวลา 30 นาที**
(ผิดสองครั้งเมื่อเดือนที่แล้วต้องไม่ทำให้เหลือโควตาสามครั้งไปตลอดกาล)

- `recordFailedLogin()` อยู่ใน `$transaction` เพราะต้องอ่านค่าเดิมมาตัดสินว่า
  "หน้าต่างหมดแล้วเริ่มใหม่" หรือ "นับต่อ" — สองคำขอพร้อมกันจะนับได้แค่ครั้งเดียวถ้าไม่ทำ
- **ตรวจล็อกก่อนตรวจ PIN เสมอ** ไม่งั้นคนที่เดา PIN ถูกในครั้งที่ 6 จะเข้าได้ทั้งที่ควรถูกล็อก
- **ผูกกับ (สาขา, รหัสที่พิมพ์มา)** — รหัสที่ไม่มีอยู่จริงไม่มีสาขาให้ผูก จึงไม่ถูกนับ
  และนั่นถูกแล้ว: การไล่สุ่ม *รหัสพนักงาน* ต้องกันที่ rate limit ระดับ IP ชั้น proxy
  ซึ่งเป็นคนละงาน · เขียนข้อจำกัดนี้ไว้ในหัวไฟล์แล้ว
- เพิ่ม action **`staff.login`** (สำเร็จ) นอกจาก `staff.login_failed` เดิม —
  ก่อนหน้านี้ log มีแต่ครั้งที่ผิด ซึ่งตอบคำถามสำคัญที่สุดของการสืบสวนไม่ได้เลย:
  *"ตอนที่บิลนั้นถูกยกเลิก ใครล็อกอินอยู่บ้าง"*

## 4. หน้าจัดการพนักงาน (`/admin/staff`)

- **`canManageStaff` = OWNER/MANAGER** — ต่างจากหน้าอื่นของจอหลังร้านที่ทุกตำแหน่งเข้าได้
  เพราะหน้านี้เผยรายชื่อทั้งสาขาพร้อมเวลาเข้าใช้งานล่าสุด ซึ่งใช้วางแผนโกงได้พอ ๆ กับใช้จับโกง
- **`canAssignRole()` — แก้ได้เฉพาะตำแหน่งที่ต่ำกว่าตัวเอง**
  ถ้าผู้จัดการตั้งบัญชี OWNER ได้ สิทธิ์ทั้งระบบไม่มีความหมายเลย เพราะข้ามได้ในสองคลิก
  (สร้างบัญชีใหม่แล้วใส่ PIN ที่ตัวเองรู้) — ตารางลำดับชั้นอยู่ใน `lib/rbac.ts` ที่เดียว
- **ห้ามแก้บัญชีตัวเองจากหน้านี้** เพราะกรณีที่อันตรายจริง (ลดตำแหน่ง/ปิดบัญชีตัวเอง)
  แก้กลับเองไม่ได้เลยหลังกด · ปุ่ม "เตะออกทุกเครื่อง" ยกเว้นให้ตัวเองกดได้
  เพราะเป็นสิ่งที่คนกดตั้งใจจริงเมื่อรู้ตัวว่าลืมล็อกจอไว้ที่เครื่องอื่น
- **รีเซ็ต PIN / ปิดบัญชี = เตะทุกเครื่องทันที** และหน้าจอบอก **จำนวนเครื่องที่หลุด**
  ไม่ใช่แค่คำว่า "สำเร็จ" — ถ้าเลขไม่ใช่ศูนย์แปลว่ามีเครื่องเปิดค้างอยู่จริง
  ซึ่งอาจเป็นเครื่องที่กำลังตามหาอยู่พอดี
- **ไม่มีปุ่มลบพนักงาน** โดยตั้งใจ — คนที่เคยเปิดโต๊ะ/รับเงิน/ถูกอ้างใน AuditLog
  ต้องอ้างถึงได้ตลอดไป (หลักการเดียวกับเมนูที่เคยถูกสั่ง)
- **ห้ามเก็บ PIN หรือ hash ลง AuditLog เด็ดขาด** — log อ่านได้โดยคนที่ไม่ใช่เจ้าของบัญชี
  (มีเคสตรึงไว้ว่า metadata ต้องไม่มีทั้งเลข PIN และสตริง `scrypt$`)
- "ประวัติการเข้า" อยู่หน้าเดียวกับปุ่มรีเซ็ต PIN เพราะถูกใช้ในนาทีเดียวกันเสมอ:
  สงสัย → ดูว่ามีเครื่องไหนค้าง → เตะออก → รีเซ็ต PIN ถ้ายังไม่มั่นใจ

## 5. เรื่องที่ตัดสินใจให้ตรงกับความจริง ไม่ใช่ให้ดูดี

**ด่าน "ต้องเหลือเจ้าของร้านอย่างน้อยหนึ่งคน" ยังเรียกไม่ถึงในโค้ดปัจจุบัน** เพราะด่าน
"ห้ามแก้บัญชีตัวเอง" ปฏิเสธไปก่อนเสมอ (คนที่แก้ได้คือ OWNER อีกคน ซึ่งตัวเขาเองก็นับ
เป็นเจ้าของร้านที่ใช้งานได้อยู่แล้ว) — เก็บโค้ดไว้เป็นตาข่ายรองรับพร้อมคอมเมนต์
**ห้ามลบเพราะ "ไม่มีเทสต์ครอบ"** และแก้ชื่อเทสต์ให้บอกตรง ๆ ว่าด่านไหนเป็นคนปฏิเสธ
ไม่งั้นเทสต์จะยังเขียวอยู่ในวันที่ด่านแรกถูกถอดออก ซึ่งเป็นวันที่มันควรแดงที่สุด

## 6. ผลกระทบต่อเครื่องมือ dev

`npm run dev:staff-cookie <รหัส> [pos|kds|admin]` — **token ใบเดียวใช้ได้จอเดียวแล้ว**
(เดิมใบเดียวใช้ได้ทั้งสามจอ) เพราะ session ผูกกับจอตั้งแต่ตอนสร้าง · สคริปต์สร้าง
**แถว session จริง** ไม่ใช่ปลอม token และประกอบ token ด้วย `createStaffToken()`
ตัวเดียวกับระบบจริง — ห้ามเขียนสูตร token ซ้ำในสคริปต์อีก

ยืนยันบน dev server จริง: cookie ของจอ POS ยิงเข้า `/kds` ได้ **307 (เด้งไปล็อกอิน)**
ส่วนของถูกจอได้ 200 ทั้งคู่

## 7. ยังไม่ได้ทำ

- **rate limit ระดับ IP** ที่ชั้น proxy (กันไล่สุ่ม *รหัสพนักงาน*) — คนละงานกับตัวนับนี้
- หน้า "อุปกรณ์ที่ล็อกอินอยู่ทั้งสาขา" รวมทุกคนในหน้าเดียว (ตอนนี้ดูรายคน + เห็นตัวเลขรวมบนลิสต์)
- ยังไม่ได้วัด responsive/overflow ของสองหน้าใหม่ด้วย `npm run audit:screens`
- Settings (spec §22 §24) = ก้อนถัดไปตามแผนใน `docs/admin/spec-vs-current.md`

## 8. เพิ่มเติมระหว่างทาง — เลขที่บิลที่คนอ่าน (`lib/order-number.ts`)

ผู้ใช้ทักว่า "เลขบิลควรเริ่มจาก 1 และรีเซ็ตทุกวัน" — **ตรวจแล้วฐานข้อมูลทำถูกอยู่แล้ว**
(`20260824-0001` … `-0004` และ prefix เปลี่ยนเองทุกวันตาม timezone ของสาขา)
ที่ผิดคือ **การแสดงผล**: ทุกจอพิมพ์ค่าดิบออกไปเป็น `#20260824-0001` ซึ่งอ่านไม่ออก
ว่าเป็นบิลที่เท่าไหร่ และตัวที่ต่างกันจริง (สี่หลักท้าย) จมอยู่ท้ายเลข 13 หลัก

- **เก็บเหมือนเดิม แปลตอนแสดงผล** — เลขวันคือสิ่งที่ทำให้ `@@unique([branchId, orderNumber])`
  กันเลขซ้ำข้ามวันได้ และทำให้รายงานกรองตามวันจากคอลัมน์เดียว ถ้าเปลี่ยนไปเก็บ `1..N`
  ล้วน ๆ ต้องเพิ่มคอลัมน์วันแยกแล้วแก้ทุก query ที่อ้างเลขนี้ — ไม่คุ้มกับปัญหาที่แก้
- **`dailyOrderNumber()` เป็นทางเดียวที่จอใช้แสดงเลขบิล** ครบทั้งห้าจุด: หน้าติดตาม
  ออร์เดอร์ของลูกค้า · ตั๋วครัว · การ์ดบิลบนจอสั่งอาหาร · หน้าคิดเงิน (สองที่) · ใบเสร็จ
- **ค่าที่ไม่ตรงรูปแบบคืนกลับไปทั้งก้อน** ไม่ใช่คืนค่าว่าง — เหตุผลเดียวกับ
  `auditActionLabel()`: แถวที่หายจากจอเพราะโค้ดไม่รู้จักรูปแบบ แย่กว่าแถวที่อ่านยาก
- ตรึงด้วย 10 เคสใน `smoke:order` (order 21 → 31) รวมเคส "คนละวันใช้เลขเดียวกันได้"
  ซึ่งเป็นข้อพิสูจน์ว่าการรีเซ็ตรายวันเป็นพฤติกรรมที่ตั้งใจ ไม่ใช่ผลข้างเคียง

**⚠ อย่าสับสนกับเลขที่ใบกำกับภาษี** — `Receipt.number` (`HQ-00000244`) ต้องเดินต่อเนื่อง
ตลอดกาลและห้ามรีเซ็ต ส่วนเลขบิลรีเซ็ตทุกวันโดยตั้งใจ สองตัวนี้อยู่คนละตารางคนละกติกา

**วัดบนเซิร์ฟเวอร์จริง:** จอครัวขึ้น `#1 #2 #3 #4` · การ์ดบิลของโต๊ะ A2 ขึ้น `#2`
· ใบเสร็จบรรทัด "อ้างอิงบิล" ขึ้น `#3` · ไม่มีเลข `20260824-…` หลงเหลือบนจอไหนเลย
