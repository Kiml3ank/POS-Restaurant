## 2. การตัดสินใจที่สำคัญที่สุด: **event เป็นสัญญาณ ไม่ใช่ข้อมูล**

`RealtimeEvent` มีแค่ `{ v, type, branchId, tableId, at }` — **ไม่มีชื่อเมนู
ไม่มีราคา ไม่มีสถานะ** ฝั่ง client ได้ยินแล้วสั่ง `router.refresh()`
แล้ว React Server Component ไปดึงของใหม่ผ่านด่านสิทธิ์เดิม

เหตุผลที่ไม่ push ข้อมูลจริงลงไปในสาย:

- ถ้า push ข้อมูล เราจะมีทางเข้าถึงข้อมูล **สองทาง** (ทาง RSC ที่ตรวจสิทธิ์แล้ว
  กับทาง SSE ที่ต้องมาตรวจซ้ำเอง) แล้ววันหนึ่งสองทางนั้นจะกรองไม่เหมือนกัน
  → ลูกค้าโต๊ะ A เห็นของโต๊ะ B โดยไม่มีใครรู้
- หน้าจอทั้งสี่ไม่ต้องมี client state เลยสักตัว จึงไม่มีเคส "ข้อมูลบนจอไม่ตรงกับ
  ใน DB เพราะ merge patch ผิด" ซึ่งเป็นบั๊กที่หาสาเหตุยากที่สุดของระบบ realtime

ราคาที่จ่าย: 1 event = 1 รอบ render ฝั่ง server ซึ่งแพงกว่า push JSON ก้อนเล็ก
แต่ปริมาณของหนึ่งสาขาคือหลักสิบ event ต่อนาที ไม่ใช่หลักพัน

## 3. pub/sub — ทำไมต้องมี และทำไมต้อง local-first

SSE แก้แค่ "ส่งจาก server ตัวนี้ไปหา browser" ปัญหาที่ยากกว่าคือ:

```
instance A ── ลูกค้ากดส่งออร์เดอร์ ──▶ เขียน DB เสร็จ
instance B ── จอครัวถือสาย SSE ค้าง ──▶ ไม่มีใครบอกมันเลย
```

บน Vercel/หลาย container เรื่องนี้เกิดแน่นอน จึงวาง "ที่นัดพบกลาง" ไว้ตั้งแต่ต้น

**สอง driver เลือกด้วย env `REALTIME_DRIVER`** (ค่าเริ่มต้น `memory`)

| driver | ใช้เมื่อ |
|---|---|
| `memory` | `next dev` และ deploy แบบ instance เดียว |
| `postgres` | **ต้องเปิดก่อน deploy หลาย instance** — ใช้ `LISTEN/NOTIFY` |

**กฎ local-first:** ทั้งสอง driver emit เข้า EventEmitter ในเครื่องตัวเอง**ก่อนเสมอ**
แล้ว driver postgres ค่อยยิง NOTIFY ออกไปให้ instance อื่นเพิ่ม ตอนรับ NOTIFY
กลับมาถ้าเป็นของที่ตัวเองยิง (`originId` ตรงกัน) จะทิ้ง

ถ้าปล่อยให้ event ของตัวเองต้องวิ่งอ้อมผ่าน Postgres ก่อนเสมอ วันที่สาย LISTEN หลุด
จอครัวที่เสียบอยู่กับ instance เดียวกับที่รับออร์เดอร์จะไม่เห็นออร์เดอร์ของตัวเองด้วย
— ครัวหยุดทำงานเพราะปัญหาที่ไม่เกี่ยวกับครัวเลย

รายละเอียดอื่นที่อยู่ในโค้ดแล้ว: reconnect แบบถอยห่าง (1→2→5→10→30 วินาที),
`prisma.$executeRaw` ยิง NOTIFY (ไม่ต้องเปิด connection ที่สอง), สาย LISTEN
ใช้ `pg` ตรง ๆ เพราะ pool คืน connection แล้ว NOTIFY จะตกหล่นเงียบ ๆ

**`publishRealtimeEvent()` ต้องเรียกหลัง commit เสมอ ห้ามเรียกใน `$transaction`**
ถ้า rollback ทีหลัง เราจะบอกครัวไปแล้วว่ามีออร์เดอร์ ทั้งที่ใน DB ไม่มีอะไรเลย

## 4. กฎของจอครัว

1. **กรองด้วย `OrderItem.stationId` ที่ snapshot ไว้ ห้าม join เมนูสด** —
   ไม่งั้นวันที่ย้าย "ผัดกะเพรา" จากครัวร้อนไปครัวทอด ออร์เดอร์ที่กำลังผัดอยู่
   จะหายจากจอกลางคันแล้วโผล่อีกสถานี
2. **`stationId = null` ต้องไม่ขึ้นจอครัว** (น้ำเปล่า ขนมซอง)
3. ครัวเดินได้แค่ `PLACED → IN_PROGRESS → READY` — **ไม่มีปุ่มถอยหลัง**
   กดพลาดต้องให้ผู้จัดการ "ยกเลิกพร้อมเหตุผล" เพื่อให้มีร่องรอยใน `AuditLog`
4. `to` ไม่รับมาจากหน้าจอ — หน้าจอส่งมาแค่ "กดปุ่มถัดไปของรายการนี้" แล้ว server
   อ่านสถานะสดจาก DB เอง (สองจอที่ถือ HTML เก่าคนละเวอร์ชันจะได้ไม่ดันสถานะย้อน)
5. `where` ผูก `status: from` เสมอ = ชั้นกันสองจอกดพร้อมกันที่เชื่อถือได้จริง
   (Postgres ให้คำสั่งที่สองรอ row lock แล้วเช็คเงื่อนไขใหม่ ได้ `count = 0`)
6. บิลที่ครัวทำเสร็จครบแล้ว **ยังอยู่บนจอ** แต่จาง — ครัวต้องเห็นว่ามีของกอง
   รออยู่ที่ช่องรับอาหารกี่ใบ

### สถานะบิล = สถานะของรายการที่ "ช้าที่สุด"

`rollUpOrderStatus()` — คำถามที่บิลต้องตอบคือ "โต๊ะนี้รออะไรอยู่หรือเปล่า"
ไม่ใช่ "มีอะไรเสร็จแล้วบ้าง" · รายการที่ยกเลิกไม่นับ · ยกเลิกหมดใบ = `CANCELLED`

`syncOrderStatusFromItems()` เป็น**ที่เดียวในระบบ**ที่ทำเรื่องนี้ และถูกเรียกจาก
สามทาง: ครัวกดปุ่ม, พนักงานกดเสิร์ฟ, ผู้จัดการยกเลิกรายการ — **ต้องอยู่ใน
transaction เดียวกับที่แก้ `OrderItem` เสมอ**

ตัวนี้ยอมให้ข้ามขั้นได้ (ต่างจาก `canTransitionOrder` ที่เดินทีละก้าว) เพราะเคสจริง:
บิล `[PLACED, SERVED]` แล้วยกเลิกตัว PLACED ทิ้ง → บิลต้องกระโดดไป `SERVED` ทันที
เพราะไม่เหลืออะไรให้ครัวทำแล้ว **แต่ห้ามถอยหลังทุกกรณี** และบิลที่ `PAID` แล้วแข็งตัว

## 5. บั๊กที่เจอระหว่างทาง (ทั้งสองตัวมีอยู่ก่อนบทที่ 8 แล้ว)

### 5.1 บิลที่มีน้ำเปล่าปนอยู่ จะคิดเงินไม่ได้ตลอดกาล

รายการที่ `stationId = null` ไม่ขึ้นจอครัว → ไม่มีใครกดเปลี่ยนสถานะให้ได้ →
ค้างที่ `PLACED` → สถานะบิล (ที่คือรายการช้าที่สุด) ไม่มีวันถึง `SERVED` →
**คิดเงินไม่ได้ในบทที่ 10** เพราะเงื่อนไขปิดบิลคือ `SERVED → PAID`

แก้ที่ `placeOrder()`: ของที่ไม่ผูกสถานีข้ามไป `READY` ตั้งแต่วินาทีที่กดส่ง
— ถูกตามความจริงด้วย ขวดน้ำในตู้เย็นพร้อมเสิร์ฟตั้งแต่ตอนสั่ง สิ่งที่ยังไม่เกิด
คือมีคนไปหยิบมาวาง ซึ่งคือขั้น `SERVED`

ผลพลอยได้: ต้องมีปุ่ม "เสิร์ฟแล้ว" บนหน้า `/pos/table/[tableId]?view=bills` ด้วย
เพราะจอครัวไม่แสดงของพวกนี้ (`posServeItemAction`)

> **`smoke:order` และ `smoke:pos` มีเคสที่ต้องแก้ตามเรื่องนี้** — ไม่ใช่ regression
> แต่เป็นการอัปเดต assertion ให้ตรงพฤติกรรมใหม่ที่ถูกกว่าเดิม (แก้แล้ว 4 เคส)

### 5.2 เปิด POS กับ KDS บนเบราว์เซอร์เดียวกัน แล้วสองจอเตะกันเอง ⚠

**อาการที่ผู้ใช้เจอ:** POS ส่งออร์เดอร์ → จอครัวรีเฟรช → ถูกเด้งไปหน้าล็อกอิน
และกลับกัน ครัวกด "เสร็จ" → POS ถูกเด้งไปล็อกอิน

**สาเหตุ:** cookie session ของพนักงานมี**ใบเดียว**ทั้งระบบ (`pos_staff_session`)

```
1. แท็บ /pos ล็อกอินเป็นแคชเชียร์   → cookie = แคชเชียร์
2. แท็บ /kds ล็อกอินเป็นครัว        → cookie ใบเดิม "ถูกเขียนทับ" = ครัว
3. ครัวกดปุ่ม → SSE → แท็บ POS refresh
4. แท็บ POS อ่าน cookie ได้ "ครัว" ซึ่งไม่มีสิทธิ์เข้า POS → เด้งไปใส่ PIN
```

แล้วแคชเชียร์ล็อกอินใหม่ ไปเขียนทับ cookie ของครัวต่อ วนไม่จบ

**บั๊กนี้มีมาตั้งแต่บทที่ 9 แล้ว** แต่มองไม่เห็นเพราะหน้าจอไม่เคยรีเฟรชเอง
บทที่ 8 ทำให้มัน refresh อัตโนมัติ อาการเลยโผล่ทันที

**แก้:** แยก cookie ต่อหน้าจอ — `pos_staff_session` / `kds_staff_session`
ทุกฟังก์ชันใน `lib/server/staff-session.ts` รับ `screen: StaffScreen` แล้ว
`Record<StaffScreen, string>` ใน `lib/staff-session-cookie.ts` จะบังคับให้
เพิ่ม cookie ของ `"admin"` ตอนบทที่ 13 โดยอัตโนมัติ (tsc พัง ถ้าลืม)

ที่หน้าร้านจริงสองจอเป็นคนละเครื่องจึงไม่เจอ — แต่ตอนผู้จัดการเปิดจอครัวดูบน
แท็บเล็ตเครื่องเดียวกับที่คิดเงิน มันคือเครื่องเดียวกัน การให้แต่ละจอถือ session
ของตัวเองจึงถูกกว่าทั้งสองกรณี ไม่ใช่แค่ทางแก้สำหรับ dev

ราคาที่จ่าย: ต้องใส่ PIN สองครั้งถ้าเปิดทั้งสองจอบนเครื่องเดียว — ซึ่งถูกแล้ว
เพราะอาจเป็นคนละคนกด และ `AuditLog` ต้องแยกออกจากกันให้ได้

## 6. RBAC — "เห็นจอ" กับ "กดปุ่มบนจอ" ไม่ใช่สิทธิ์เดียวกัน

| | OWNER | MANAGER | CASHIER | SERVER | KITCHEN |
|---|:-:|:-:|:-:|:-:|:-:|
| เข้า `/pos` | ✅ | ✅ | ✅ | ✅ | — |
| เข้า `/kds` | ✅ | ✅ | — | ✅ | ✅ |
| ปุ่มครัว (รับ/เสร็จ) | ✅ | ✅ | — | — | ✅ |
| ปุ่ม "เสิร์ฟแล้ว" | ✅ | ✅ | ✅ | ✅ | — |
| ยกเลิกรายการ | ✅ | ✅ | ✅ | — | — |

- **เสิร์ฟเข้าจอครัวได้** เพราะจอครัวคือที่ที่เห็นว่าของโต๊ะไหนพร้อมยก
  แต่กดแทนครัวว่า "ทำเสร็จแล้ว" ไม่ได้ ไม่งั้นเวลาที่เก็บไว้วัดครัวในบทที่ 15
  จะไม่ใช่เวลาที่ครัวทำจริง
- **ครัวกด "เสิร์ฟแล้ว" ไม่ได้** เพราะครัวไม่ใช่คนยกไปวางบนโต๊ะ ถ้าให้กดได้
  ตัวเลข "พร้อมเสิร์ฟค้างอยู่กี่จาน" บนผังโต๊ะจะเป็นศูนย์ตลอดเวลา
- **แคชเชียร์เข้าจอครัวไม่ได้แต่กดเสิร์ฟได้** — แยกหน้าที่ระหว่างคนถือเงินกับ
  คนตัดสินว่าอาหารเสร็จ (หลักเดียวกับที่บทที่ 13 จะใช้ทั้งบท)

แถบข้าง `pos-sidebar.tsx` ซ่อนลิงก์ "จอครัว" ให้ตำแหน่งที่เข้าไม่ได้ (แสดงจาง
พร้อมคำว่า "ไม่มีสิทธิ์") — แคชเชียร์ที่กดแล้วไปเจอหน้า PIN ที่ตัวเองใส่เท่าไหร่
ก็ไม่ผ่าน แย่กว่าไม่มีปุ่มให้กดตั้งแต่แรก

## 7. การทดสอบ

### smoke test

```bash
npm run smoke:kds                              # 55 เคส (driver memory)
REALTIME_DRIVER=postgres npm run smoke:kds     # 56 เคส (+ เส้นทาง LISTEN/NOTIFY)
```

เคสที่ครอบ: RBAC 9, roll-up 6, กรองตามสถานี 7, ครัวเดินสถานะ 8, บั๊มทั้งใบ 5,
เสิร์ฟ 7, ยกเลิกแล้ว roll-up 5, ท่อ realtime 3-4

เคสสำคัญที่ต้องไม่พัง:
- น้ำเปล่าไม่ขึ้นจอครัวเลย (สั่ง 3 รายการ เห็นบนจอ 2)
- บิลกระโดด `PLACED → READY` เมื่อยกเลิกรายการสุดท้ายที่ครัวต้องทำ
- บั๊มซ้ำได้ `changed = 0` **โดยไม่ error** (อีกจอกดไปก่อนแล้ว = ผลลัพธ์ที่ต้องการอยู่ดี)
- รับ event จาก instance อื่นผ่าน `LISTEN/NOTIFY` ได้จริง

### ทดสอบ SSE ผ่าน HTTP จริง

```bash
STAFF=$(npm run --silent dev:staff-cookie 004)

# 1. ไม่มี cookie → ต้อง 401 (ห้าม redirect — EventSource ตาม redirect ไปหน้า HTML แล้วพัง)
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000/api/realtime

# 2. header ต้องมี text/event-stream + no-transform + x-accel-buffering: no
curl -s -D - -o /dev/null --max-time 2 -H "Cookie: kds_staff_session=$STAFF" \
  http://localhost:3000/api/realtime

# 3. เนื้อสาย
curl -s -N --max-time 3 -H "Cookie: kds_staff_session=$STAFF" http://localhost:3000/api/realtime
```

ผลที่ยืนยันแล้ว:

| เคส | ผล |
|---|---|
| ไม่มี cookie | `401` |
| `?table=` ที่ยังไม่เปิดรอบโต๊ะ | `401` |
| พนักงานที่ล็อกอินแล้ว | `200` + `retry: 3000` + `event: pos-ready` |
| POS(002) + KDS(004) cookie อยู่ในเบราว์เซอร์เดียวกัน | `/pos` 200 · `/kds` 200 (ไม่เตะกัน) |
| ครัวถือ cookie ของ POS | `/pos` → 307 `/pos/login` |
| แคชเชียร์ถือ cookie ของจอครัว | `/kds` → 307 `/kds/login` |

**ทดสอบ cross-process จริง** (สร้าง production build รันที่ :3001 ด้วย
`REALTIME_DRIVER=postgres` แล้วยิง event จากอีก process):

```bash
npm run build
REALTIME_DRIVER=postgres PORT=3001 npm run start &
curl -s -N --max-time 10 -H "Cookie: kds_staff_session=$STAFF" \
  http://localhost:3001/api/realtime &
REALTIME_DRIVER=postgres npm run dev:emit order.placed
```

สาย SSE ได้รับ `event: pos-change` พร้อม `at` ตรงกับที่ยิงไปเป๊ะ ๆ
และเมื่อทดสอบฝั่งลูกค้าด้วย `?table=a1x7qk` **ได้รับเฉพาะ event ของโต๊ะ A1**
ไม่ได้รับของโต๊ะ B1 และไม่ได้รับ event ระดับสาขาที่ไม่ผูกโต๊ะ

## 9. UI ของจอครัว

`app/globals.css` เพิ่มบล็อก `.pos-skin.kds-skin` = **โหมดกลับสีของ design system เดิม**
ใช้คู่กันเสมอ: `class="pos-skin kds-skin"` ที่ `app/(kds)/layout.tsx` จุดเดียว

ทำได้เพราะทุกกฎใน design system เขียนเป็น `var(--color-*)` ไว้หมดแล้ว
การนิยาม token ชุดใหม่ทับบน element เดียวกันจึงกลับสีทั้งระบบให้ฟรี
**ไม่ต้องก๊อป `.btn` / `.ink-grid` / `.tag` / `.alert` ไปเขียนซ้ำอีกชุด**
(specificity `.pos-skin.kds-skin` สูงกว่า `.pos-skin` จึงชนะโดยไม่ต้อง `!important`)

ทำไมจอครัวต้องมืดทั้งที่ทั้งระบบเป็นกระดาษขาว:
- จอครัวเปิดค้างทั้งวันในระยะ 1-3 เมตร พื้นขาวเต็มจอคือแสงจ้ายิงใส่คนทำงาน 8 ชม.
- ครัวมีไอน้ำมันเกาะจอ ตัวอักษรสว่างบนพื้นมืดยังอ่านออกเมื่อจอเลอะ

เส้นหมึก 2px ยังอยู่ครบ แค่กลับเป็นเส้นสว่างบนพื้นมืด · ฐานฟอนต์ 16px (ไม่ใช่ 14px)
เพราะอ่านจากไกลกว่าจอ POS หนึ่งช่วงแขน

**สิ่งที่ตัดออกจากจอครัวทั้งหมด: ราคา ยอดรวม ชื่อพนักงาน** — ครัวไม่ได้ตัดสินใจ
อะไรจากตัวเลขพวกนั้น จอต้องตอบแค่ 3 คำถาม: ใบไหนมาก่อน · ใบไหนรอนานไป · ต้องทำอะไรกี่ที่

`<Elapsed>` เดินนาฬิกาเองฝั่ง client (ทุก 15 วินาที) เพราะเวลาที่ผ่านไปเปลี่ยน
ตลอดโดยไม่มี event เกิดขึ้น — ถ้าให้มาจาก server มันจะค้างที่ "2 นาที" จนกว่า
จะมีคนกดอะไรสักอย่าง

## 10. หน้าล็อกจอ (แก้ตามที่ผู้ใช้ขอ)

- **ช่อง PIN ใหญ่ขึ้น** `h-16` → `h-20`, ตัวอักษร 30px → 36px
- **พิมพ์ด้วยคีย์บอร์ดได้แล้ว** — วาง `<input>` จริงทับช่อง PIN แบบโปร่งใส
  (`opacity-0` + ช่องที่เห็นเป็น `pointer-events-none`) จึงได้ทั้งสามทางเข้า
  ด้วย state ตัวเดียว: พิมพ์คีย์บอร์ด · แตะช่อง (มือถือเด้งแป้นตัวเลข) · กดแป้นบนจอ
  **ห้ามใช้ `hidden`/`display:none`** เพราะ focus ไม่ได้ แล้วแป้นมือถือจะไม่ขึ้น
- Enter ที่ช่องรหัสพนักงาน = ไปต่อที่ PIN (ไม่ใช่ส่งฟอร์ม) · Enter ตอน PIN ไม่ครบ
  ถูกบล็อก (ปุ่ม disabled กันการคลิก ไม่ได้กันการ submit ด้วย Enter)
- **โชว์ชื่อคนล่าสุดที่ใช้เครื่องนี้** ผ่าน cookie `pos_last_staff` / `kds_last_staff`

  ตั้งใจ**ไม่** query รายชื่อพนักงานจาก DB เพราะหน้าล็อกอินยังไม่รู้ว่าเครื่องนี้
  อยู่สาขาไหน จะกลายเป็นการโชว์ชื่อพนักงานสาขาอื่นให้คนแปลกหน้าดู · cookie ตอบ
  คำถามที่ถูกกว่าด้วย: ไม่ใช่ "ใครล็อกอินล่าสุดในร้าน" แต่คือ "ใครใช้เครื่องนี้ก่อนฉัน"

  **เก็บเฉพาะชื่อกับตำแหน่ง ไม่เก็บรหัสพนักงาน** เพราะรหัสคือครึ่งหนึ่งของสิ่งที่
  ต้องใช้ล็อกอิน ถ้าโชว์คู่กันจะเหลือแค่ต้องเดา PIN 4 หลัก · ค่านี้ไม่ได้เซ็นลายเซ็น
  เพราะไม่มีอำนาจอะไรเลย — **ห้ามเอาไปใช้ตัดสินใจเรื่องสิทธิ์**

## 11. ยังไม่ได้ทำ / ต้องทำก่อน deploy

| เรื่อง | รายละเอียด |
|---|---|
| **ตั้ง `REALTIME_DRIVER=postgres`** | ถ้า deploy หลาย instance ไม่ตั้ง = จอครัวไม่เห็นออร์เดอร์ที่เข้าคนละ instance |
| ตัวนับ PIN ผิดยังอยู่ใน memory | ปัญหาเดิมจากบทที่ 9 ต้องย้ายไป Postgres/Redis |
| ยกเลิก session ทันทีไม่ได้ | ต้องเพิ่มตาราง `StaffSession` ในบทที่ 13 |
| ย้าย/รวมโต๊ะ, แยกบิล | ค้างจากบทที่ 9 |
| **responsive** | POS ต้องการจอ ≥1100px · เป็นก้อนถัดไปที่ตกลงกันไว้ |
| `images.remotePatterns` ยังกว้าง | ต้องแคบก่อน deploy (บทที่ 16) |

`STREAM_LIFETIME_MS = 5 นาที` — สายปิดตัวเองแล้วให้เบราว์เซอร์ต่อใหม่ ไม่ใช่เพราะ
อยากปิด แต่เพราะทุก platform มีเพดานอายุ request ของตัวเอง การปิดเองก่อนแบบสุภาพ
คู่กับ `retry:` ทำให้การต่อใหม่เป็นเรื่องปกติที่ควบคุมได้ ไม่ใช่อุบัติเหตุ
