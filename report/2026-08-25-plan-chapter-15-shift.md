# บทที่ 15 — กะ / ปิดกะ / ใบสรุปกะ (spec)

> **สถานะ:** spec ที่ตกลงกันแล้ว รอทำแผน implementation
> **ขอบเขตที่ตกลง:** ทำ **เรื่องกะอย่างเดียว** — รายงานยอดขายย้อนหลัง (รายวัน/รายชั่วโมง ·
> เมนูขายดี · รายพนักงาน · export CSV) เป็นก้อนถัดไป ไม่อยู่ในนี้

## 1. เป้าหมาย

ตอบคำถามเดียวให้ได้แม่นยำ: **"เงินสดในลิ้นชักตอนนี้ควรมีเท่าไร และที่นับได้จริงต่างจากนั้นเท่าไร"**
พร้อมหลักฐานว่าใครเปิดกะ ใครปิด และส่วนต่างเกิดในกะของใคร

ของที่ได้:
- เปิดกะพร้อมเงินทอนตั้งต้น
- **X report** — สรุปสดระหว่างกะ (ดูกี่ครั้งก็ได้ ไม่บันทึกอะไร)
- **ปิดกะ** — นับเงินสดจริงเทียบกับที่ระบบคาดไว้ บันทึกส่วนต่าง
- **ใบสรุปกะ (Z)** — เอกสารของกะที่ปิดแล้ว พิมพ์ 80mm ได้ ตัวเลขไม่ขยับตลอดกาล
- หน้าประวัติกะย้อนหลังของผู้จัดการ (spec §14 "Managers should be able to review cash discrepancies")

## 2. การตัดสินใจที่ตกลงไว้แล้ว (ห้ามเปลี่ยนระหว่างทำโดยไม่คุย)

| ข้อ | ที่ตกลง | เหตุผล |
|---|---|---|
| ขอบเขต | กะอย่างเดียว | รายงานย้อนหลังเป็นก้อนใหญ่แยกต่างหาก |
| หนึ่งกะ = | **หนึ่งสาขา** ณ เวลาหนึ่ง | ร้านมีลิ้นชักเดียว · ตรงกับ `Shift` ที่ไม่มีคอลัมน์ register |
| ไม่มีกะเปิดแล้วรับเงิน | **ขายได้** · `shiftId = null` · นับแยกแล้วแสดงให้เห็น | ระบบกะเป็นเครื่องมือนับเงิน **ไม่ใช่ด่านขวางการขาย** (คอมเมนต์ใน schema เขียนไว้ตั้งแต่บทที่ 11) |
| ใครเปิด/ปิด | OWNER/MANAGER/CASHIER ที่จอ POS | คนถือลิ้นชักคือคนนับเงิน |
| ใครดูย้อนหลัง | OWNER/MANAGER ที่จอหลังร้าน | ประวัติกะ = เห็นยอดขายทั้งสาขา (กติกาเดียวกับ `canBrowseReceipts`) |
| ปิดวัน / Z report | **ไม่มี "ปิดวัน" แยก** · Z = ใบสรุปกะ | `orderNumber` รีเซ็ตเองทุกวันอยู่แล้ว · เลขใบกำกับภาษีห้ามรีเซ็ตตลอดกาล — "ปิดวันเพื่อรีเซ็ตตัวนับ" จึงไม่มีความหมายที่นี่ · ร้านที่มีกะเดียวต่อวัน ปิดกะ = ปิดวันอยู่แล้ว |
| ช่องนับเงิน | ยอดรวมก้อนเดียว | `countedCash` เป็น `Int` เดียวอยู่แล้ว · การนับแยกใบ/เหรียญต้องมีชุดใบต่อสกุลเงิน (THB/LAK/VND คนละชุด) ซึ่งไม่คุ้มในก้อนนี้ |

**ไม่ทำในก้อนนี้ (YAGNI):** ลิ้นชักหลายใบ/register · pay-in/pay-out (เบิกเงินซื้อของระหว่างกะ) ·
refund (ยังไม่มีทั้งระบบ) · ปิดวันเป็น entity · รายงานยอดขายย้อนหลัง

## 3. ข้อมูล

**ไม่มี migration ใหม่** — `Shift` และ `Payment.shiftId` ลง DB ไปแล้ว (`71d1654`)

คอลัมน์ที่จะเริ่มมีคนเขียนค่า:

```
Shift
  status          OPEN | CLOSED
  openedAt · openedByStaffId · openingFloat      ← เขียนตอนเปิดกะ
  closedAt · closedByStaffId                     ← เขียนตอนปิดกะ
  countedCash · expectedCash · cashDifference    ← snapshot ตอนปิด
  salesTotal · billCount · breakdown (Json)      ← snapshot ตอนปิด
  note                                           ← หมายเหตุตอนปิด
Payment.shiftId                                  ← เขียนตอนรับเงิน (nullable)
```

### 3.1 สูตรเงินสดที่ควรมีในลิ้นชัก

```
expectedCash = openingFloat + Σ grandTotal ของ Payment ที่ method = CASH ในกะนี้
cashDifference = countedCash − expectedCash      (บวก = เกิน · ลบ = ขาด)
```

- ใช้ **`grandTotal` ไม่ใช่ `receivedAmount`** — เงินทอนออกจากลิ้นชักไปแล้ว
- **QR ไม่นับ** (ไม่ได้เข้าลิ้นชัก) แต่ยังต้องขึ้นในใบสรุปแยกบรรทัด
- **ไม่มีบรรทัด refund** — spec §14 มี แต่ระบบยังไม่มีการคืนเงิน · **ห้ามใส่บรรทัดว่างที่เป็น 0 ตลอดกาล**
  ให้เขียนบนจอตรง ๆ ว่ายังไม่มีการคืนเงินในระบบ (ท่าเดียวกับสามอย่างที่หน้าสรุปวันนี้บอกว่าจงใจไม่ใส่)
- ทุกยอดเป็น `Int` หน่วยย่อยของสกุลเงินสาขา · แสดงผลผ่าน `formatMoney(amount, branch.currency)` เท่านั้น

### 3.2 `breakdown` (Json, อ่านอย่างเดียว)

รูปร่างที่จะเขียน — เป็น snapshot ไม่มีใครอ่านกลับมาคำนวณต่อ:

```jsonc
{
  "byMethod":    { "CASH": { "count": 12, "total": 348000 }, "QR": { "count": 5, "total": 96000 } },
  "bySalePoint": { "DINE_IN": { "count": 14, "total": 402000 }, "COUNTER": { "count": 3, "total": 42000 } },
  "discountTotal": 12000,
  "staffMealCount": 2
}
```

เก็บเป็น Json เพราะรูปร่างจะเปลี่ยนตามช่องทางที่ร้านเปิดใช้ · **ห้ามให้หน้าจอใหม่ ๆ เอา Json นี้
ไปคำนวณต่อ** ถ้าต้องการตัวเลขใหม่ให้ query จาก `Payment` ตรง ๆ

## 4. กติกาที่เป็นเรื่องเงิน (จุดที่พังแล้วเสียหายจริง)

### 4.1 อ่านกะที่เปิดอยู่ **ในทรานแซกชันเดียวกับการรับเงิน**

`takePayment()` ต้องเรียก `resolveOpenShiftId(tx, branchId)` **ข้างใน `$transaction`**
ก่อนสร้างแถว `Payment` — ไม่ใช่อ่านไว้ก่อนแล้วส่งเข้าไป

เหตุผลเดียวกับที่บทที่ 13a อ่านธง "พนักงานกิน" ในทรานแซกชัน: ถ้าอ่านไว้ก่อน จะมีช่องที่
**ปิดกะแทรกกลาง** แล้วเงินก้อนนั้นถูกผูกกับกะที่ปิดไปแล้ว — ใบสรุปที่พิมพ์ออกไปจะไม่มีเงินก้อนนั้น
ทั้งที่แถวในฐานบอกว่าอยู่ในกะนั้น

### 4.2 ปิดกะเป็น conditional update และคิดยอดในทรานแซกชันเดียวกัน

```ts
const claimed = await tx.shift.updateMany({
  where: { id: shiftId, branchId, status: "OPEN" },
  data: { status: "CLOSED", ... },
});
if (claimed.count === 0) { /* ปิดไปแล้ว → คืนใบเดิม ไม่ใช่ error */ }
```

เป็น **คำสั่งแรก** ในทรานแซกชัน ท่าเดียวกับการกันจ่ายซ้ำของบทที่ 11 —
สองเครื่องที่กดปิดพร้อมกันต้องได้ใบสรุปใบเดียว ไม่ใช่สองใบที่ตัวเลขต่างกัน

การรวมยอด (`Σ Payment`) ต้องอยู่ในทรานแซกชันเดียวกับการปิด ไม่งั้นบิลที่จ่ายระหว่างที่กำลังปิดกะ
จะ **หายไปจากทั้งสองกะ** (ไม่อยู่ในใบที่ปิด เพราะรวมยอดไปก่อนแล้ว · ไม่อยู่ในกะถัดไป เพราะ
`shiftId` ชี้กะที่ปิดไปแล้ว)

### 4.3 X คิดสด · ตัวเลขตอนปิด snapshot

`getShiftReport()` (X) query สดทุกครั้ง ไม่บันทึกอะไรเลย — ดูกี่ครั้งก็ได้ ไม่ทิ้งร่องรอย
**และรับเฉพาะกะที่ยังเปิดอยู่** (กะที่ปิดแล้วต้องอ่านผ่าน `getShift()` เท่านั้น ไม่งั้นจะมีสองทาง
ที่ให้ตัวเลขของกะเดียวกัน แล้ววันหนึ่งสองทางนั้นจะไม่ตรงกัน)
ส่วนตัวเลขตอนปิดเขียนลงแถว `Shift` แล้ว **หน้าใบสรุปอ่านจากแถวนั้นอย่างเดียว ห้าม query สดซ้ำ**
(เหตุผลเดียวกับ `Receipt` ของบทที่ 12: เปิดใบสรุปกะเมื่อวานดูปีหน้าต้องได้ตัวเลขเดิมเป๊ะ
แม้อัตรา VAT/ชื่อร้านจะเปลี่ยนไปแล้ว — มีเทสต์ตรึง)

### 4.4 เงินสดนอกกะ

บิลที่รับตอนไม่มีกะเปิด (`shiftId = null`) ต้อง **มองเห็นได้** ไม่ใช่หายเงียบ:
หน้าเปิดกะแสดง "มีเงินสดที่รับนอกกะ ฿X จาก N บิล (เวลา … ถึง …)" เพื่อให้คนเปิดกะรู้ว่า
เงินส่วนเกินในลิ้นชักมาจากไหน · ยอดนี้ **ไม่ถูกนับเข้ากะไหนทั้งสิ้น**

## 7. เคสที่ต้องมีเทสต์ (`npm run smoke:shift`)

**ยอดเงิน**
1. `expectedCash` = เงินทอนตั้งต้น + เฉพาะบิลเงินสด (บิล QR ในกะเดียวกันต้องไม่ถูกนับ)
2. `cashDifference` บวก/ลบ/ศูนย์ ถูกทั้งสามกรณี
3. ใช้ `grandTotal` ไม่ใช่ `receivedAmount` — บิลที่รับเงินมาเกินแล้วทอน ต้องไม่ทำให้ยอดเพี้ยน
4. `salesTotal` / `billCount` / `breakdown` ตรงกับบิลที่ปิดในกะจริง
5. บิลที่รับ **นอกกะ** ไม่ถูกนับเข้ากะ และหน้าเปิดกะรายงานยอดนั้นได้

**การชนกัน**
6. กดปิดกะพร้อมกันสองครั้ง → ได้ใบเดียว · ครั้งที่สองคืน `alreadyClosed: true` ไม่ใช่ error
7. เปิดกะซ้อนขณะมีกะเปิดอยู่ = error
8. ปิดกะที่ปิดไปแล้ว = คืนใบเดิม
9. รับเงินหลังปิดกะ → `shiftId = null` (ไม่ตกไปอยู่ในกะที่ปิดแล้ว)

**snapshot**
10. แก้ VAT/เซอร์วิสชาร์จในหน้าตั้งค่าหลังปิดกะ → ตัวเลขในใบสรุปกะไม่ขยับ (ยืนยันด้วยเลขจริง)

**สิทธิ์/ขอบเขต**
11. ครัว/พนักงานเสิร์ฟเปิดหรือปิดกะไม่ได้
12. ปิดกะข้ามสาขาไม่ได้ · `getShift` ของสาขาอื่นคืน null
13. `canViewShiftHistory` — แคชเชียร์เปิด `/admin/shifts` ไม่ได้ แต่เปิดใบสรุปของกะที่ตัวเองปิดได้

**AuditLog**
14. `shift.open` / `shift.close` เขียนครบ และ `shift.close` เก็บส่วนต่างที่ถูกต้อง

**หน้าจอ**
15. `audit:screens` สามหน้าใหม่ × 5 ขนาด (มีข้อมูลจริงก่อนวัด · กาง `<details>` ด้วย `openDetails`)
16. ตรวจ HTML ที่ออกจาก `npm run build` + `npm run start -- -p 3002` จริง —
    **อ่านของที่เซิร์ฟเวอร์ส่งออกมา ไม่ใช่เชื่อว่าโค้ดถูก** (บทเรียนจากก้อน KDS ที่จอหลุดสามจุดทั้งที่เทสต์เขียว)
