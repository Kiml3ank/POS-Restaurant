ตอบสี่คำถามที่ **ผูกกับจุดขาย ไม่ได้ผูกกับบิล** (ตัดสินได้ตั้งแต่ก่อนบิลมีของอยู่ในนั้น):

| ฟังก์ชัน | จริงเฉพาะ | ผลถ้าทำผิด |
|---|---|---|
| `showsInTableMap()` | `DINE_IN` | เคาน์เตอร์โผล่ในผังโต๊ะเป็นช่องที่ไม่มีความหมาย |

| `needsQueueNumber()` | ไม่ใช่ `DINE_IN` | ไม่มีอะไรให้เรียกลูกค้ามารับของ |
| `chargesServiceCharge()` | `DINE_IN` | **ลูกค้าซื้อกลับโดนเก็บเงินเกินทุกใบ** |

## 4. ของเดิมที่ถูกแก้

- **`table-session.ts`** — `openOrJoinTableSession()` แตกเป็นสองทาง: โต๊ะนั่ง
  เข้าร่วมรอบเดิมเหมือนเดิมทุกประการ · จุดขายอื่นสร้างรอบใหม่เสมอ + ออกเลขคิว ·
  และ **ไม่แตะ `RestaurantTable.status`** เพราะเคาน์เตอร์มีบิลเปิดหลายใบ
  คำว่า "ไม่ว่าง" ตอบอะไรไม่ได้ ตั้งแล้วจะค้างตลอดกาลเพราะไม่มีใครรู้ว่าเมื่อไหร่ควรปลด
- **`resolveCustomerContext()` + `openTableSession()`** — ปฏิเสธจุดขายที่ไม่ใช่โต๊ะนั่ง
  **ทั้งสองที่** (ตัวหลังคือเส้นทางที่เขียนจริง และถูกยิงตรงด้วย POST ได้)
  คืน `null` เฉย ๆ ไม่บอกว่า "มีอยู่แต่เข้าไม่ได้" เพื่อไม่ยืนยันว่า code นั้นมีจริง
- **`cart.ts`** — `Order.type` เลิกฮาร์ดโค้ด `"DINE_IN"` แล้ว อ่านจาก `kind` ของจุดขาย
  **enum `OrderType` เพิ่งมีคนเขียนค่าจริงเป็นครั้งแรกตั้งแต่บทที่ 7**
- **`billing.ts` / `payment.ts`** — ทั้งคู่ผ่าน `billRatesForSalePoint()` ตัวเดียวกัน
- **`pos.ts`** — `getPosTables()` กรอง `kind: "DINE_IN"`

### เลขคิวใช้ `max+1` ไม่ใช่ `DocumentCounter` — โดยตั้งใจ

เลขที่ใบกำกับภาษี **ห้าม** ใช้ `max+1` เพราะถ้าชนกัน สิ่งที่ล้มเหลวคือ
**การรับเงินทั้งที่ลูกค้าจ่ายแล้ว** ซึ่งรับไม่ได้ (บทที่ 12)

เลขคิวคนละสถานการณ์: ถ้าชนกัน สิ่งที่ล้มเหลวคือ "การเปิดบิลใหม่" ซึ่งยังไม่มีเงิน
เกี่ยวข้อง กดใหม่ก็จบ · ความเสียหายจริงข้อเดียวคือลูกค้าสองคนได้ "คิว 12" พร้อมกัน
แล้วมีคนมารับผิดคน — ซึ่งกันด้วย `@@unique([branchId, queueDay, queueNumber])`
ราคาที่ไม่ต้องจ่าย: ไม่ต้องให้การเปิดบิลของทั้งสาขาเข้าคิวกันที่แถวเดียว

## 5. ⚠ บั๊กเรื่องเงินที่เจอระหว่างทาง — สมมติฐาน "หนึ่งจุดขาย = หนึ่งบิลที่เปิดอยู่"

ทั้ง `getTableBill()` และ `takePayment()` หา session ด้วย
`findFirst({ where: { tableId, status: "OPEN" }, orderBy: { openedAt: "desc" } })`
ซึ่ง **ถูกต้องเสมอสำหรับโต๊ะนั่ง** และไม่มีใครสังเกตมาตั้งแต่บทที่ 10 เพราะโต๊ะหนึ่งโต๊ะ
มีรอบเปิดได้ทีละรอบ — พอเคาน์เตอร์เปิดหลายบิลพร้อมกันได้ สมมติฐานนี้พังทันที

1. **`getTableBill()`** คืนบิลของคนที่มาทีหลังเสมอ → คนแรกที่ยืนรอจ่ายเงินเห็นบิลว่าง
   (เคสนี้ทำให้เทสต์แดงจริง ไม่ได้เดาเอา)
2. **`takePayment()`** — ร้ายกว่ามาก: แคชเชียร์กดรับเงินจากคิว 12 แล้ว
   **ไปปิดบิลของคิว 14 แทน** ซึ่งย้อนคืนยากเพราะรอบที่ปิดไปแล้วออกใบเสร็จและ
   เดินเลขเอกสารไปเรียบร้อย

**ที่แก้:**

- เพิ่ม `getSessionBill(branchId, sessionId)` และแยกแกนกลาง `buildBill()` ออกมา
  ให้สองทางเข้าลงมาจบที่เดียว (ไม่ใช่สองฟังก์ชันที่คิดเองคนละที่ ซึ่งวันหนึ่งจะมี
  ที่หนึ่งลืมกรองรายการที่ถูกยกเลิก)
- `takePayment()` รับ `sessionId` ได้ และ **ปฏิเสธเมื่อมีบิลเปิดมากกว่าหนึ่งใบ
  แต่ไม่ระบุมา** — เลือก "ไม่เดา" แทน "หยิบล่าสุด" · โต๊ะนั่งไม่ต้องส่งอะไรเพิ่ม
  หน้าจอเดิมของบทที่ 11 จึงไม่ต้องแก้เลย

**บทเรียน:** ก้อนนี้ไม่ได้เพิ่มบั๊ก แต่ทำให้บั๊กที่หลับอยู่ตื่น — สมมติฐานที่ไม่เคยถูก
เขียนเป็นตัวหนังสือ (`หนึ่งจุดขาย = หนึ่งบิลที่เปิดอยู่`) ฝังอยู่ในรูปแบบ query
ไม่ใช่ใน comment จึงหาไม่เจอด้วยการอ่าน ต้องให้เทสต์ชนเอง
