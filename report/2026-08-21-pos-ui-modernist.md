| เรื่อง | ค่า |

## 3. การตัดสินใจที่ต้องรู้ก่อนแก้ UI ต่อ

### 3.1 กับดักฟอนต์ไทย — จุดที่กินเวลาที่สุดของก้อนนี้

Archivo ไม่มีกลีฟไทยเลย จึงตั้ง font stack เป็น `Archivo, "Noto Sans Thai"`
แล้วให้เบราว์เซอร์ไล่หาฟอนต์ **ทีละกลีฟ** — ตัวเลข/อังกฤษได้ Archivo ตัวไทยตกไป Noto

ปัญหาที่เจอตอนตรวจ CSS ที่ emit ออกมาจริง:

```
--font-archivo: "Archivo", "Archivo Fallback";
@font-face { font-family: Archivo Fallback; src: local(Arial); size-adjust: 98.7% }
```

Next แทรก `Archivo Fallback` = **Arial** ต่อท้ายให้เองเพื่อลด layout shift
และ **Arial มีกลีฟไทย** ตัวไทยจึงไปหยุดที่ Arial ตลอด ไม่มีวันตกถึง Noto Sans Thai
(แถมโดน `size-adjust: 98.7%` ที่คำนวณจาก metric ของ Archivo ไปด้วย)

`adjustFontFallback: false` ที่เอกสาร Next ระบุไว้ **ไม่ได้ผล** — ตรวจแล้วว่า
`@font-face` ตัวนั้นยังถูก emit ทั้งใน dev และใน `npm run build` ตัว loader ของ
`next/font/google` รองรับ option นี้จริง (`validate-google-font-function-call.js`)
แต่ build ผ่าน **Turbopack** ซึ่งไม่ทำตาม

ทางแก้ที่ใช้จริงอยู่ที่ `app/globals.css` — เขียนชื่อ `"Archivo"` ตรง ๆ แทน
`var(--font-archivo)` เพื่อข้ามตัว Fallback ทิ้ง ส่วน Noto ใช้ var ได้ตามปกติ
เพราะ fallback ของมันอยู่ถูกตำแหน่งแล้ว ผลลัพธ์ที่ resolve ออกมา:

```
1. "Archivo"                  ← ตัวเลข/อังกฤษ
2. "Noto Sans Thai"           ← ตัวไทย
3. "Noto Sans Thai Fallback"
4. system-ui
5. sans-serif
```

**ถ้าจะแตะฟอนต์อีกในอนาคต ต้องตรวจ `@font-face` ที่ออกมาจริงเสมอ อย่าเชื่อ option**

### 3.2 token ผูกกับ `.pos-skin` ไม่ใช่ `:root`

ขอบเขตของก้อนนี้คือหน้าพนักงานเท่านั้น ถ้าวาง token ไว้ที่ `:root` หน้าลูกค้า
KDS และหลังร้านจะเปลี่ยนตามไปด้วยทันทีโดยไม่มีใครสั่ง — คลาส `pos-skin`
แปะอยู่ที่ `app/(pos)/layout.tsx` **จุดเดียว** ถ้าจะขยายไปหน้าอื่นให้แปะที่
layout ของ route group นั้น อย่าย้าย token ขึ้น `:root`

ชื่อตัวแปรตั้งให้ตรงกับไฟล์ต้นทางเป๊ะ ๆ (`--color-text`, `--space-4`, …)
เพื่อให้ก๊อป snippet จาก `Cafe POS.dc.html` มาวางแล้วใช้ได้เลยโดยไม่ต้องแปลชื่อ

### 3.3 `ItemOptionsForm` แยกแค่หน้าตา ไม่แยกตรรกะ

ไฟล์นี้ใช้ร่วมกันระหว่างหน้าลูกค้ากับ POS จึงเพิ่ม prop `skin?: "default" | "pos"`
ค่าเริ่มต้นเป็นของเดิม (ยืนยันแล้วว่าหน้าลูกค้าไม่เปลี่ยนเลย — หัวข้อ 4)

ที่ต่างกันคือ **การจัดวาง** ล้วน ๆ: ฝั่งลูกค้าเป็นรายการแนวตั้งกดด้วยนิ้วโป้งมือเดียว
ฝั่ง POS เป็นแถบ segmented บนกริดเส้นหมึกที่กวาดตาทีเดียวเห็นครบ — สองจอนี้ใช้งาน
คนละท่าจริง ๆ ส่วนกฎ `required`/`minSelect`/`maxSelect` และการคิดราคาเป็นโค้ด
ชุดเดียวกันเป๊ะทั้งสองลุค ไม่มี branch

### 3.4 สื่อสถานะโต๊ะด้วยความเข้ม ไม่ใช่หลายสี

ผังโต๊ะเดิมใช้ 3 สี (เขียว = มีของพร้อมเสิร์ฟ / เหลือง = เปิดอยู่ / ขาว = ว่าง)
แต่ Modernist มี accent สีเดียว จึงเปลี่ยนเป็น **ลำดับความเข้ม**: โต๊ะที่ต้อง
รีบไปยกของได้พื้น `accent-100` + ป้าย accent ทึบ ที่เหลือเป็นกระดาษเปล่า
ตาจับ "ใบที่ต่างจากพวก" ได้เร็วกว่าจับเฉดสีอยู่แล้ว และไม่พึ่งการแยกสีเขียว/เหลือง
ซึ่งเป็นคู่ที่ตาบอดสีแดง-เขียวแยกยากที่สุด

### 3.5 หน้าเมนูเปลี่ยนจาก "ไล่เลื่อนทีละหมวด" เป็นแท็บหมวด

ตาม design ทำผ่าน `?cat=` ใน URL ไม่ใช่ client state — ยังเป็น Server Component
ล้วนและกดได้ก่อน JS โหลดเสร็จเหมือนส่วนอื่นของหน้านี้ หมวดที่ไม่มีเมนูเปิดขาย
จะถูกกรองทิ้งไม่ให้เป็นแท็บว่าง

**ที่ design มีแต่ยังไม่ได้ทำ:** ช่องค้นหาเมนู — ถ้าทำผ่าน URL จะต้องยิง server
ทุกตัวอักษรที่พิมพ์ ถ้าทำฝั่ง client ต้องดึงเมนูทั้งสาขาลงมาก่อน ทั้งสองทาง
ต้องคิดมากกว่าที่ก้อนนี้ควรรับ จึงเว้นไว้

### 3.6 สองจุดที่ตั้งใจไม่ทำตาม design

1. **ไม่เอาลิสต์รายชื่อพนักงานให้กดเลือกที่หน้าล็อกอิน** — จอนี้อยู่ในที่ที่ลูกค้า
   มองเห็น การโชว์รายชื่อทั้งกะคือการแจกครึ่งหนึ่งของข้อมูลที่ต้องใช้ล็อกอินให้ฟรี
   และขัดกับที่ `loginStaff()` ตั้งใจตอบข้อความเดียวกันทั้งกรณีรหัสผิดและ PIN ผิด
   (รายงานก้อนที่แล้ว หัวข้อ 2.3) — คงเป็นช่องกรอกรหัสพนักงานเหมือนเดิม เอาแค่รูปลักษณ์
2. **หัวเรื่องใหญ่ยังเป็น "POINT OF SALE" ตัวโรมัน** — เป็น wordmark ไม่ใช่ข้อความ
   ที่ต้องอ่าน และ `line-height: 0.92` ที่ design ใช้ตรงนี้ **ตัดหัว-หางสระไทยขาด**
   ถ้าเอาตัวไทยมาวาง ข้อความไทยทุกจุดที่เหลือใช้ line-height ปกติทั้งหมด

ข้อความ ค่าเงิน `฿` (ผ่าน `formatBaht`) และแบรนด์ยังเป็นของโปรเจกต์ทั้งหมด
ไม่ได้เอา copy / `$` / ชื่อ "Meridian Coffee" จาก design มาด้วย

### 3.7 ช่อง PIN 6 ช่องอ่านผิดเป็น "ต้องกรอก 6 หลัก" — แก้แล้วหลังทดสอบด้วยตา

รอบแรกวาดช่อง PIN ทั้ง 6 ช่องเป็นกล่องขอบ 2px เหมือนกันหมด (`MAX_PIN_LENGTH = 6`)
คนที่มาเห็นครั้งแรกอ่านออกมาเป็น **"ต้องกรอกให้ครบ 6 หลัก"** แล้วค้างรอว่าจะกรอกอะไร
อีกสองตัว ทั้งที่ PIN ของ seed ยาว 4 หลักและระบบตั้งใจรับ 4-6 หลักมาแต่แรก

เป็นปัญหาที่เกิดจากการเปลี่ยนรูปทรงล้วน ๆ — ของเดิมเป็นจุดกลมเล็ก ๆ ที่อ่านว่า
"ได้ถึง 6" ส่วนกล่องขอบหนาเรียงกันอ่านว่า "ช่องที่ต้องเติมให้เต็ม" **การเปลี่ยน
รูปทรงเปลี่ยนความหมายของ UI ไปด้วย ไม่ใช่แค่ความสวย**

แก้สามจุด: สองช่องท้ายใช้เส้นขอบจาง (`--color-neutral-400`) เพื่อบอกว่าไม่บังคับ,
เพิ่มป้ายบอกสถานะข้างคำว่า PIN (`อย่างน้อย 4 หลัก` → `4 หลัก · กดเริ่มกะได้เลย`),
และแก้ hint ฝั่งซ้ายให้บอกชัดว่า PIN ของ dev ยาว 4 หลัก
ตรรกะไม่เปลี่ยน — ปุ่มเปิดใช้งานที่ 4 หลักเหมือนเดิม แค่เดิมไม่มีอะไรบอกผู้ใช้

รอบเดียวกันขยายขนาดฟอร์มทั้งชุดตาม feedback ว่า "เล็กไป": คอลัมน์ขวา 520 → 620px,
ช่อง PIN สูง 52 → 64px, ปุ่มแป้น `py-4` → `py-6`, ปุ่มเริ่มกะสูง 56 → 64px
และจัดฟอร์มให้อยู่กึ่งกลางแนวตั้งแทนการชิดบน

### 3.8 รอบแรกทำ design ไม่ครบสองจุด — แก้แล้วหลังผู้ใช้ทัก

รอบแรกส่งงานโดย**ขาดสองอย่างที่เป็นแกนของ design** แล้วไม่ได้บอกให้ชัดในบทสรุป
(เขียนไว้แค่ในรายงาน) ผู้ใช้ทักถูกทั้งสองข้อ:

**ก. ไม่มีแถบข้าง** — design มีแถบซ้าย 268px พร้อมโมดูลเรียงเลข 01-06
ที่ข้ามไปตอนแรกเพราะโมดูลส่วนใหญ่ยังไม่มีในโปรเจกต์ ตอนนี้ทำแล้วที่
`pos-sidebar.tsx` โดย **โมดูลที่ยังไม่มีแสดงเป็นข้อความจาง ๆ พร้อมเลขบท ไม่ใช่ลิงก์**
— ตั้งใจไม่ใส่ลิงก์ที่กดแล้วไปเจอหน้าเปล่า และตั้งใจไม่ซ่อน เพราะแถบนี้ทำหน้าที่
เป็นแผนที่บอกคนที่มาเห็นครั้งแรกว่าระบบจะมีอะไรบ้าง ถ้าบทไหนทำเสร็จให้เติม `href`
แล้วมันจะกดได้เอง เป็น client component ตัวเดียวของ layout เพราะต้องใช้ `usePathname`
ไฮไลต์โมดูลปัจจุบัน (ข้อมูลที่ต้องใช้มีแค่ตำแหน่งพนักงาน จึงรับเป็น prop ไม่แตะ DB)

**ข. เมนูกับตะกร้าไม่ได้อยู่จอเดียวกัน** — อันนี้คือใจความหลักของ design เลย

ที่ต้องพูดกับลูกค้าไปกดไปและต้องเห็นตะกร้าโตขึ้นทันทีที่กด

```
└─────────────────────────────────────┴─────────────────┘
```

- บิลที่ส่งเข้าครัวแล้วย้ายไปเป็นแท็บ `?view=bills` ของแพเนลซ้าย (พร้อมป้ายนับจำนวน)
  ปุ่มปิดรอบโต๊ะอยู่ท้ายแท็บนั้น — เป็นปุ่มอันตรายที่ควรอยู่นอกทางเดินหลัก
  แต่ยังห่างแค่คลิกเดียว
- `/pos/table/[id]/menu` กลายเป็น redirect (คงไว้เพราะเครื่องหน้าร้านมักถูก bookmark
  และหน้าเลือกตัวเลือกยังอยู่ใต้เส้นทางนี้)
- `posAddToCartAction` เปลี่ยนปลายทาง redirect มาที่จอนี้ — ใส่ของเสร็จแล้วเห็นมัน
  โผล่ในตะกร้าทางขวาทันทีโดยไม่เปลี่ยนหน้า
- layout ของ `(pos)` เปลี่ยนจาก `min-h-dvh` เป็น `h-dvh overflow-hidden` เพื่อให้
  **แต่ละแพเนลเลื่อนของตัวเองแยกกัน** ตะกร้ากับยอดรวมจึงอยู่กับที่เสมอ ไม่เลื่อนหนี
  (หน้าล็อกอินยังเป็น `min-h-dvh` เพราะจอเตี้ยต้องเลื่อนลงไปหาแป้น PIN ได้)

### 4.2 ขับผ่าน HTTP จริง

| หน้า | ผล |

| `/pos/table/.../menu/[itemId]` | 200 |

**คลาสเก่าหลงเหลือ:** ค้นหา `rounded-*`, `bg-white`, `border-neutral-300`,
`bg-emerald-600`, `text-red-700` ใน HTML ของหน้าโต๊ะ — **เจอ 0 ตัว**

`accent-neutral-900` 8) — เท่ากับก่อนแก้

## 5. ข้อมูลทดสอบที่ทิ้งไว้ให้ + สิ่งที่ยังค้าง

**ทิ้งไว้ให้ดู UI:** เปิดรอบโต๊ะ **A2** ไว้แล้ว มีบิลที่ส่งเข้าครัว 1 ใบ
(ชาเย็น ×2 + น้ำเปล่า) และตะกร้าที่ยังไม่ส่งอีก 1 รายการ (กะเพราพิเศษ + ไข่ดาว
พร้อมหมายเหตุ) — เปิด `npm run dev` แล้วไปที่ `/pos/login` ใส่ `001` / `1234`
แล้วกดเข้าโต๊ะ A2 จะเห็นทั้งแผงตะกร้า ปุ่ม stepper และการ์ดบิลครบ

ล้างทิ้งเมื่อไม่ต้องการแล้วด้วย `npm run dev:reset-table a2m4vd`
(รอบนี้หมดอายุเองใน 3 ชั่วโมงอยู่แล้ว)

**ยังค้าง:**

1. **ยังไม่มีใครเห็นด้วยตา** — ดูกล่องเตือนบนสุดของรายงาน
2. **ช่องค้นหาเมนู** ที่ design มี — เหตุผลที่เว้นไว้อยู่ในหัวข้อ 3.5
3. **จอ Report / Products / Inventory / Employees** ใน design ยังไม่ได้ทำ
   (ตรงกับบทที่ 13-15)
4. **หน้าลูกค้า / KDS / หลังร้าน ยังเป็นลุคเดิม** ตามขอบเขตที่ตกลงกันไว้
   ถ้าจะทาต่อ ให้แปะ `pos-skin` ที่ layout ของ route group นั้น — แต่ design
   ต้นทางเป็นจอ 1440×900 ต้องออกแบบใหม่พอสมควรก่อนเอาไปใช้กับมือถือลูกค้า
5. **`.pos-skin *{border-radius:0}` เป็นไม้ตาย** — ล้างมุมมนทับทุกอย่างในซับทรี
   ถ้าวันหนึ่งอยากได้มุมมนที่ไหนในหน้า POS ต้องลบกฎนี้ก่อนแล้วไล่เก็บ `rounded-*`
   ที่หลงเหลือแทน
