## 1. ⚠ ขอบเขต: นี่คือโหมดสาธิต ไม่ใช่การรับเงินจริง

ตามที่ตกลงไว้ในแผน:

- ❌ ไม่ต่อกับ payment gateway จริง ไม่มี webhook ไม่มีการยืนยันยอดจากธนาคาร
- ❌ ไม่ได้สร้าง PromptPay payload ตามมาตรฐาน EMVCo (tag 29) — **ยกเลิกข้อนี้ตามที่ผู้ใช้สั่ง**
- ✅ แคชเชียร์กดเลือกเงินสด/QR เองแล้วกดยืนยัน = บิลปิด
- ✅ QR เป็นกล่อง placeholder ที่ **ตั้งใจวาดให้ดูออกว่าปลอม** (ไม่มีสี่เหลี่ยม finder
  ตามมุมแบบ QR จริง) พร้อมป้าย "โหมดสาธิต · สแกนไม่ได้จริง" — ของปลอมที่ดูออกว่าปลอม
  ปลอดภัยกว่าของปลอมที่เนียนจนมีคนยกมือถือขึ้นมาสแกนแล้วสงสัยว่าเครื่องเสีย

**สิ่งที่ยังทำเต็มรูป** เพราะบทที่ 12/13/15 ต่อยอดจากมันโดยตรง:
ปิดบิลใน `$transaction` เดียว · snapshot อัตรา+สกุลเงิน · `AuditLog` · จำนวนเต็มล้วน ·
RBAC ฝั่ง server · กันจ่ายซ้ำ · กระจายยอดลงทุกบิลแบบผลรวมตรงเป๊ะ

**จุดที่ต้องแก้วันที่ต่อของจริง:** `takePayment()` ต้องแตกเป็นสองขั้น
(“ตั้งรายการรอชำระ” → “ยืนยันเมื่อธนาคาร callback กลับมา”) — แก้ที่ฟังก์ชันนั้น
ไม่ใช่ที่หน้าจอ · และวิธีรับเงินต้องผูกกับประเทศของสาขา ไม่ใช่ hardcode PromptPay
(ลาว = LAO QR ของ BCEL One · เวียดนาม = VietQR ของ NAPAS — EMVCo เหมือนกันแต่คนละ tag)

## 3. การตัดสินใจที่ต้องรู้ก่อนเขียนบทถัดไป

### 3.1 `Payment` เป็นตารางแยก และเป็น "ยอดจริง" ที่ลูกค้าจ่าย

บิลคิดที่ระดับ **รอบโต๊ะ** (รวม subtotal ทุกใบก่อน แล้วคิดเซอร์วิสชาร์จ/VAT ครั้งเดียว)
แต่คอลัมน์ยอดเงินอยู่ที่ระดับ `Order` ซึ่งมีได้หลายใบต่อรอบ

**กฎที่ห้ามลืมในบทที่ 12/15:**
`Payment.grandTotal` คือยอดที่ลูกค้าจ่ายจริง · ยอดใน `Order` เป็น **ส่วนแบ่ง**
ที่กระจายลงไปเพื่อทำรายงานแยกช่องทาง (`channel`) และแยกพนักงาน (`placedByStaffId`)
ใบเสร็จต้องอ้าง `Payment` ไม่ใช่ผลบวกของ `Order`

### 3.2 กระจายยอดด้วย largest remainder — และ `grandTotal` ต้อง "ประกอบ" ไม่ใช่ "แบ่ง"

`distributeByWeight(total, weights)` แบ่ง discount / serviceCharge / VAT
ตามสัดส่วน `subtotal` ของแต่ละบิล โดยผลรวมเท่าเดิมเป๊ะเสมอ

**จุดที่ต่างจากแผนเดิมเล็กน้อยและสำคัญ:** `Order.grandTotal` ไม่ได้แบ่งด้วย
largest remainder อีกชุดหนึ่ง แต่ **ประกอบจากชิ้นส่วนของแถวตัวเอง** ด้วยสูตร
เดียวกับ `calculateBill()`:

```
pricesIncludeVat = true  → grandTotal = subtotal − discount + serviceCharge
pricesIncludeVat = false → grandTotal = subtotal − discount + serviceCharge + vat
```

ถ้าแบ่ง `grandTotal` แยกต่างหาก ผลรวมจะตรงก็จริง **แต่บางแถวจะบวกเองไม่ลงตัว**
(เพี้ยนได้ 1 หน่วยจากการปัดคนละรอบ) แล้วคนที่มาอ่านแถวนั้นทีหลังจะสรุปว่าข้อมูลเสีย
วิธีนี้ได้ทั้งผลรวมที่ตรงและแถวที่อ่านแล้วบวกได้ — มีเคสทดสอบคุมทั้งสองข้อ

### 3.3 กันจ่ายซ้ำด้วยการ "ปิดรอบโต๊ะแบบมีเงื่อนไข"

คำสั่งแรกใน transaction คือ:

```ts
updateMany({ where: { id, status: "OPEN" }, data: { status: "CLOSED", closedAt } })
```

หนึ่งรอบโต๊ะ = หนึ่งบิล การปิดรอบจึงเป็น **ตั๋วใบเดียว** ของการรับเงินครั้งนี้
สองเครื่องที่กดพร้อมกัน เครื่องที่สองจะรอ row lock แล้ว Postgres (READ COMMITTED)
ประเมิน `WHERE` ซ้ำหลังปลดล็อก → ได้ `count = 0` → คืน Payment ใบเดิม
**ไม่ใช่ error และไม่ใช่ใบที่สอง** (ท่าเดียวกับ conditional update ใน `placeOrder()`)

มีเคสทดสอบยิงสองครั้งพร้อมกันด้วย `Promise.all` แล้วยืนยันว่าได้ `Payment` ใบเดียว

**การกดซ้ำแบบเรียงกัน** (กดสองที/กด back แล้วกดใหม่) ก็ต้องไม่ขึ้น error —
ถ้าโต๊ะนั้นเพิ่งมีการรับเงินภายใน **60 วินาที** จะพากลับไปที่ใบเดิม
เลยกรอบนั้นแล้วถึงจะเป็น error (กันเคสเปิด URL ค้างไว้ครึ่งวันแล้วกด)

### 3.4 ห้ามเชื่อยอดที่ client ส่งมา — แต่ใช้มันเป็น optimistic check ได้

หน้าจอส่งมาแค่ **"วิธีจ่าย" กับ "รับเงินสดมาเท่าไหร่"**
ยอดจริงคิดใหม่ฝั่ง server **ในtransaction** ด้วย `calculateBill()` เสมอ

เพิ่มเติมจากแผน: หน้าจอแนบ `expectedTotal` (ยอดที่แคชเชียร์เห็นตอนกด) มาด้วย
ถ้าไม่ตรงกับยอดที่คิดสด ๆ ใน transaction → **ไม่ยอมปิดบิล** แล้วบอกให้อ่านยอดใหม่
เหตุผล: ลูกค้าที่โต๊ะกดสั่งเพิ่มจากมือถือได้ตลอดเวลา (บทที่ 8 ทำให้จอ refresh เอง
แต่ระหว่างที่นิ้วกำลังกดปุ่มอยู่ก็ยังชนกันได้) — **ปิดบิลด้วยยอดที่ลูกค้าไม่เคยเห็น
คือสิ่งที่ห้ามเกิดที่สุดในหน้านี้**

### 3.5 ตะกร้าที่ยังไม่ส่งเข้าครัว = จ่ายไม่ได้ (ต่างจากของที่ยังไม่เสิร์ฟ)

- **ของที่ยังไม่ได้เสิร์ฟ → เตือน ไม่ห้าม** (ลูกค้าขอจ่ายก่อนรับของได้ ตามแผน)
- **ตะกร้า `DRAFT` ที่มีของ → ห้ามจ่าย** เพราะมันไม่ได้อยู่ในยอดบิลเลย
  เคสจริง: พนักงานกดเลือกเมนูให้ลูกค้าไว้แล้วลืมกด "ส่งเข้าครัว" แล้วเดินมาคิดเงิน —
  ถ้าปล่อยให้ปิดได้ ของนั้นจะหายไปพร้อมรอบโต๊ะโดยไม่มีใครรู้ว่าลูกค้าสั่งไว้

ตะกร้า **เปล่า** ที่ค้างอยู่ถูกลบทิ้งในtransaction เดียวกัน (ไม่มีของจริงผูกอยู่)

### 3.6 ของที่ยังไม่ได้ทำ ยังอยู่บนจอครัวต่อไปแม้บิลจะ PAID แล้ว

`lib/server/kds.ts` กรองด้วย **สถานะของรายการ** ไม่ใช่สถานะของบิล จึงไม่ต้องแก้อะไร
และมันถูกตามความจริง: ลูกค้าจ่ายก่อนแล้วนั่งรอของได้ ครัวต้องยังเห็นงานอยู่
`serveOrderItem()` ก็ยังกดได้บนบิลที่ PAID แล้ว (`syncOrderStatusFromItems()`
ไม่แตะบิลที่ PAID อยู่แล้ว สถานะบิลจึงไม่ถอยกลับ)

### 3.7 `AuditLog` action `"payment.take"`

เขียนใน transaction เดียวกับการรับเงิน (รับเงินสำเร็จแต่ log หายไม่ได้)
metadata มี: วิธีจ่าย · สกุลเงิน · ยอดทุกช่อง · เงินรับมา/เงินทอน · จำนวนบิล ·
โต๊ะ · รอบโต๊ะ · และ **`demoMode: true`** เพื่อให้ย้อนหลังแล้วอ่านออกว่าแถวนี้
มาจากโหมดสาธิต ไม่ใช่การยืนยันจากธนาคาร

## 4. กับดักที่เจอระหว่างทาง (อ่านก่อนแตะโค้ดใกล้เคียง)

### 4.1 ⚠ ทุกสคริปต์ที่ล้างโต๊ะต้องลบ `Payment` ด้วย ไม่งั้นพังทั้งหมด

`Order → Payment` เป็น `Restrict` และ `Payment → TableSession` ก็ `Restrict`
ลำดับการลบจึงต้องเป็น **ออร์เดอร์ → การรับเงิน → รอบโต๊ะ** เท่านั้น

โต๊ะที่เคยปิดบิลแล้วจะรีเซ็ตไม่ได้เลยถ้าลืมบรรทัดนี้ — แก้ไปแล้วทั้ง 4 ที่:
`scripts/dev-reset-table.ts`, `smoke-bill.ts`, `smoke-kds.ts`, `smoke-pos-staff.ts`
(นี่คือเหตุผลที่ `smoke:payment` ใช้โต๊ะ A3 ร่วมกับ `smoke:kds` ได้อย่างปลอดภัย)

### 4.2 ต้อง `throw` เพื่อ rollback ไม่ใช่ `return`

เงื่อนไขหลายข้อ (บิลว่าง, ตะกร้าค้าง, เงินไม่พอ, ยอดเปลี่ยน) ตรวจได้**หลังจาก**
ที่เราปิดรอบโต๊ะไปแล้ว (คำสั่งแรกใน transaction) — ถ้า `return` เฉย ๆ
**รอบโต๊ะจะถูกปิดทิ้งโดยไม่ได้รับเงิน** จึงต้องมี `class PaymentAbort extends Error`
แล้ว throw ให้ Prisma rollback ทุกอย่างกลับไปเหมือนไม่มีอะไรเกิดขึ้น
(มีเคสทดสอบยืนยันว่ารอบโต๊ะยังเป็น `OPEN` หลังถูกปฏิเสธ)

### 4.3 `19.99 * 100 === 1998.9999999999998`

ช่อง "รับเงินมา" ให้พนักงานพิมพ์เป็นหน่วยใหญ่ตามที่เขียนบนแบงก์
การแปลงเป็นหน่วยย่อยจึง **ห้ามคูณ 100 แบบ float** — `parseMoneyInput()`
แยกสตริงที่จุดทศนิยมแล้วประกอบเป็นจำนวนเต็มตรง ๆ (อยู่ใน `lib/money.ts` ที่เดียว
ตามกฎ "ห้ามหาร/คูณ 100 นอกไฟล์นี้") และรู้จักตัวคั่นหลักพันของแต่ละสกุลด้วย

### 4.4 กับดัก specificity เดิม — เกือบโดนอีกรอบ

เขียน `<div className="ink-row grid grid-cols-2">` ไว้ตอนแรกสำหรับปุ่มเลือกวิธีจ่าย
`.pos-skin .ink-row` ประกาศ `display:flex` ด้วย specificity 0-2-0 ซึ่ง **ชนะ `grid`
ของ Tailwind (0-1-0)** — แก้เป็นให้ลูกใช้ `flex-1` แทน
(กับดักเดียวกับ §3.1 ของ `report/2026-08-22-responsive-screens.md`)

### 4.5 `Intl` ใช้ได้เฉพาะที่ที่ render ฝั่ง server อย่างเดียว

หน้าสรุปแสดง "เวลาที่รับเงิน" ด้วย `Intl.DateTimeFormat("th-TH", { timeZone })`
ซึ่งขัดกับกฎใน `lib/money.ts` ที่ห้ามใช้ Intl — ต่างกันตรงที่อันนั้นเป็นค่าที่
client component ก็ต้อง render (จึงเกิด hydration mismatch ได้) ส่วนอันนี้อยู่ใน
async server component ล้วน ไม่มีการ render ซ้ำฝั่ง client
และการระบุ `timeZone` ของสาขาตรง ๆ ทำให้ผลไม่ขึ้นกับ timezone ของเครื่องที่รัน

## 5. หน้าจอ

`/pos/table/[tableId]/bill` เป็น **หน้าเดียว สองโหมด**:

| URL | โหมด |
|---|---|
| `.../bill` | บิลที่ยังไม่ปิด — อ่านยอด + ส่วนรับเงิน |
| `.../bill?paid=<paymentId>` | สรุปการรับเงิน (อ่านจาก snapshot ล้วน ไม่แตะ `Branch`) |

ต้องเป็นหน้าเดียวกันเพราะพอปิดบิลแล้ว **รอบโต๊ะถูกปิดไปด้วย** หน้าคิดเงินปกติจะ
ไม่มีอะไรให้แสดงอีกเลย ถ้าไม่มีโหมดที่สอง แคชเชียร์จะกดยืนยันแล้วเจอหน้า
"โต๊ะนี้ยังไม่ได้เปิด" ซึ่งอ่านแล้วเหมือนระบบพัง ทั้งที่เพิ่งรับเงินสำเร็จ
— และจะไม่มีที่ให้ดูเงินทอนด้วย

ส่วนรับเงิน:
- ปุ่มเลือก **เงินสด / QR** (`.is-active` ของ design system เดิม)
- เงินสด: ช่องกรอกใหญ่ + **ปุ่มลัดยอดกลม ๆ ที่คิดจากจำนวนหลักของยอดจริง**
  ไม่ได้ hardcode ค่าแบงก์ของประเทศใดประเทศหนึ่ง (พันบาทกับแสนดองคนละสเกล)
  + เงินทอนโชว์สด ๆ ระหว่างพิมพ์
- QR: กล่อง placeholder + ยอด + ป้ายโหมดสาธิต
- ปุ่มยืนยันปิดตัวเองด้วย `useFormStatus` และ disable เมื่อเงินสดยังไม่พอ
- ตำแหน่งที่ไม่มีสิทธิ์เห็นข้อความแทนปุ่ม (**ตัวกันจริงอยู่ฝั่ง server อีกชั้น**)

**หน้าหลังจ่าย = "ใบบิล" ใบเดียว ไม่ใช่สองแพเนล** (แก้ตามที่ผู้ใช้ติเมื่อ 2026-08-22)

รอบแรกทำหน้าหลังจ่ายเป็นเลย์เอาต์เดียวกับหน้าคิดเงิน (ซ้ายรายการ · ขวาสรุปยอด)
แล้วผู้ใช้ติว่ามัน "อ่านเป็นสรุปของออร์เดอร์ ไม่ใช่บิล" — ถูกต้อง เพราะสองหน้านี้
เป็นคนละชนิดของสิ่ง:

| หน้า | ชนิด | เลย์เอาต์ |
|---|---|---|
| `/bill` (ก่อนจ่าย) | **เครื่องมือ** — ฝั่งขวาคือแป้นรับเงินที่ต้องกด | สองแพเนล |
| `/bill?paid=` (หลังจ่าย) | **เอกสาร** — ไม่เหลืออะไรให้กดแล้ว | คอลัมน์เดียวแบบใบเสร็จ |

สิ่งที่เปลี่ยน: รายการกับยอดรวมไหลต่อกันในกระดาษใบเดียว (กว้างสุด 560px จัดกลาง) ·
เพิ่ม **จำนวน × ราคาต่อหน่วย** ใต้ชื่อทุกบรรทัด · **เลขบิลย้ายไปอยู่หัวเอกสาร
ครั้งเดียว** ไม่ซ้ำทุกบรรทัดอีก (รอบโต๊ะที่มีหลายออร์เดอร์ลิสต์เลขทั้งหมดที่หัว) ·
เพิ่มบรรทัด "ชำระโดย" ให้เอกสารบอกตัวเองได้ว่าจ่ายด้วยอะไรโดยไม่ต้องอ่านแถบหัวจอ

**หน้าคิดเงินยังแปะเลขบิลทุกบรรทัดเหมือนเดิมโดยตั้งใจ** — ตอนนั้นลูกค้ากำลังไล่เทียบ
ว่า "รอบที่สั่งตอนแรก" กับ "ที่สั่งเพิ่มทีหลัง" ตรงไหม พอจ่ายจบแล้วข้อมูลนั้นกลายเป็นสิ่งรบกวน

**RBAC:** `canTakePayment` = OWNER / MANAGER / CASHIER (ชุดเดียวกับ `canCancelOrderItem`)
พนักงานเสิร์ฟกดไม่ได้ — คนถือเงินกับคนเสิร์ฟต้องแยกกัน

**แถบข้าง:** โมดูล 03 เปลี่ยนจาก "บทที่ 10-11" เป็น "เลือกจากผังโต๊ะ"
(ทำเสร็จแล้วแต่ไม่มีหน้าเดี่ยว เพราะบิลผูกกับรอบโต๊ะเสมอ) ผ่าน field `hint` ตัวใหม่

## 6. วิธีทดสอบที่ใช้

```bash
npm run smoke:payment    # 67 เคส (ได้ 67 เท่ากันทั้ง driver memory และ postgres)
npm run smoke:order && npm run smoke:pos && npm run smoke:kds && npm run smoke:bill
REALTIME_DRIVER=postgres npm run smoke:kds       # 56 เคส (รวมเส้นทาง LISTEN/NOTIFY)
npx tsc --noEmit && npx eslint && npm run build
```

⚠ สคริปต์ที่ `subscribeToBranch()` **ต้องเรียก `stopRealtime()` ตอนจบเสมอ**
ไม่งั้นตอน `REALTIME_DRIVER=postgres` มันถือ connection ที่ LISTEN ค้างไว้
แล้ว process ไม่จบ — สคริปต์จะค้างเงียบ ๆ ทั้งที่เทสต์ผ่านหมดแล้ว (โดนมาแล้วหนึ่งครั้ง)

`smoke:payment` ครอบ: `distributeByWeight` (รวม invariant ที่ลองหลายสิบชุด) ·
`parseMoneyInput` · RBAC ทั้ง 5 ตำแหน่ง · บิลว่าง · ตะกร้าค้าง · เงินไม่พอ ·
ยอดเปลี่ยนระหว่างกด · เงินทอน · กดซ้ำทันที/กดซ้ำหลังหมดเวลา · **กดพร้อมกันสองเครื่อง** ·
ผลรวมของ Order เท่ากับ Payment เป๊ะ · snapshot ครบ · session/โต๊ะ/AuditLog ·
event realtime · QR · CARD ที่ยังไม่เปิดใช้ · และ **สาขาสกุลเงิน VND**
(สลับสาขาชั่วคราวแล้วคืนค่าเดิมใน `finally` เสมอ)

ทดสอบผ่าน HTTP จริงด้วย cookie พนักงาน: หน้าบิล 200 + เห็นปุ่มรับเงิน (แคชเชียร์) ·
เห็นข้อความ "ไม่มีสิทธิ์รับเงิน" (พนักงานเสิร์ฟ) · หน้าสรุปหลังจ่าย 200 พร้อม
ยอด/เงินทอน/เวลา/ชื่อคนรับเงินถูกต้อง

**การล้นแนวนอน** วัดด้วย headless Chrome ผ่าน CDP (สคริปต์อยู่ใน scratchpad
ไม่ได้ commit) ที่ 390 / 768 / 1024 / 1440px × 3 สถานะจอ (โหมดเงินสด · โหมด QR
ที่ต้องคลิกสลับก่อน · หน้าสรุปหลังจ่าย) = **12 เคส ล้น 0px ทุกเคส**

## 7. ยังไม่ได้ทำ / ต้องทำต่อ

- **บทที่ 12** — ใบเสร็จ / ใบกำกับภาษีอย่างย่อ: เลขที่ต้องเดินต่อเนื่อง
  แขวนไว้ที่ `Payment` ได้เลย (ตารางออกแบบเผื่อไว้แล้ว)
  · **เนื้อหาภาษีต้องให้ผู้สอบบัญชี/สรรพากรตรวจก่อนใช้จริง**
- **ปุ่มส่วนลด** — สูตรใน `calculateBill()` และคอลัมน์ใน `Payment`/`Order` พร้อมแล้ว
  แต่ยังไม่มีปุ่ม เพราะส่วนลดคือช่องโกงอันดับต้น ๆ ต้องมาพร้อม
  จำกัดตามตำแหน่ง + บังคับเหตุผล + `AuditLog` (บทที่ 13)
- **`PaymentMethod.CARD`** มีใน enum แต่ปิดไว้ — ต้องมีเครื่อง EDC/gateway จริงถึงจะมีความหมาย
- **แยกบิล / ย้าย-รวมโต๊ะ** ยังไม่ได้ทำ (ค้างจากบทที่ 9) — `Payment` ออกแบบไว้ให้
  หลาย `Order` ชี้มาใบเดียวได้แล้ว แต่การ "แยกจ่ายคนละครึ่ง" ต้องมี Payment หลายใบ
  ต่อรอบโต๊ะ ซึ่ง schema รองรับอยู่แล้ว (ไม่ได้ทำ unique ที่ `tableSessionId`)
  สิ่งที่ต้องเพิ่มคือตรรกะเลือกว่าบรรทัดไหนอยู่ใบไหน
- งานค้างเดิมก่อน deploy: `REALTIME_DRIVER=postgres` · ตัวนับ PIN ผิดที่ยังอยู่ใน
  memory · ตาราง `StaffSession` สำหรับ revoke · `images.remotePatterns` ที่ยังกว้าง
