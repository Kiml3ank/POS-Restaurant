## 1. ⚠ สิ่งที่เจอตอนเริ่ม — บั๊กเดียวกันซ่อนอยู่ทั่วชั้น action

ก้อนที่แล้วแก้ "หนึ่งจุดขาย = หนึ่งบิลที่เปิดอยู่" ไปสองจุด (`getTableBill`,
`takePayment`) พอจะทำหน้าจอจริงถึงพบว่า **สมมติฐานเดียวกันอยู่ในทุก action**:

```
resolveOpenSession(branchId, tableId) → getPosTable() → "รอบล่าสุดของโต๊ะ"
```

ทุกฟังก์ชันที่แก้ของในบิล — ใส่ตะกร้า · เพิ่ม/ลดจำนวน · ส่งเข้าครัว ·
ติด/ปลดธงส่วนลดพนักงาน — หาบิลด้วยวิธีนี้ทั้งหมด ผลถ้าปล่อยไว้:
**พนักงานกดเพิ่มของให้คิว 12 แล้วของไปโผล่ในบิลของคิว 14** โดยหน้าจอดูปกติทุกอย่าง

จึงไม่ใช่ "เพิ่ม route ใหม่" แต่ต้องให้ชั้น action เลิกเดาก่อน

**วิธีแก้ — ท่าเดียวกับที่ใช้กับ `takePayment()` ในก้อนที่แล้ว ไม่สร้างกติกาที่สอง:**

- ฟอร์มแนบ `sessionId` มาได้ · `resolveOpenTarget()` ตรวจว่าเป็นรอบที่เปิดอยู่
  ในสาขานั้นจริงก่อนใช้เสมอ (เชื่อค่าจากฟอร์มไม่ได้)
- ไม่แนบมา + จุดขายมีบิลเปิดมากกว่าหนึ่ง = **ปฏิเสธ ไม่เดา**
- โต๊ะนั่งไม่ต้องส่งอะไรเพิ่ม → **หน้าจอเดิมของบทที่ 9-13 ไม่ต้องแก้เลยสักบรรทัด**
- `setStaffMeal()` / `clearStaffMeal()` รับ `sessionId` เพิ่มด้วยเหตุผลเดียวกัน
  (eslint จับได้ว่า `clearStaffMeal` รับพารามิเตอร์แล้วลืมใช้ — เป็นบั๊กจริง ไม่ใช่ lint noise)

**`salePointBase()` คำนวณเส้นทาง redirect จาก `kind` ของจุดขาย ไม่ใช่รับ base
มาจากฟอร์ม** เพราะ base ที่ฟอร์มส่งมาผิดได้ (ก๊อปฟอร์มไปวางแล้วลืมแก้)
แล้วพนักงานจะถูกพากลับไปผิดบิล ซึ่งอ่านออกมาเหมือน "จอค้าง" มากกว่าเหมือนบั๊ก

## 2. จอที่ใช้ร่วมกัน ไม่ใช่จอชุดที่สอง

สองจอใหญ่ถูกแยกออกจาก page มาเป็น component ที่ **สองเส้นทางใช้โค้ดชุดเดียวกันจริง ๆ**
(ท่าเดียวกับ `components/receipt-document.tsx` ในบทที่ 12):

| component | ใช้โดย | ต่างกันแค่ |
|---|---|---|
| `_components/sale-point-screen.tsx` | `/pos/table/[tableId]` · `/pos/counter/[sessionId]` | `base`, `backHref`, `heading`, `subtitle`, `sessionId` |
| `_components/bill-screen.tsx` | `.../bill` ทั้งสองฝั่ง | `base`, `heading`, `sessionId` |

page ทั้งสองฝั่งเหลือแค่ "หาบิล → ส่งให้จอกลาง" (~60 บรรทัด)
ถ้าแยกเป็นสองไฟล์ วันหนึ่งจะมีที่หนึ่งที่ลืมแก้ แล้วซื้อกลับกับนั่งที่ร้าน
จะเริ่มทำงานไม่เหมือนกันโดยไม่มีใครตั้งใจ

### เส้นทางใหม่

```
/pos/counter                          แถบคิว + ปุ่มเปิดบิลใหม่
/pos/counter/[sessionId]              สั่งอาหาร (เมนู+ตะกร้าจอเดียว เหมือนหน้าโต๊ะ)
/pos/counter/[sessionId]/menu/[itemId]  เลือกตัวเลือก
/pos/counter/[sessionId]/bill         คิดเงิน / รับเงิน / สรุปหลังจ่าย
```

**ชี้ด้วย `sessionId` ไม่ใช่ `tableId`** เพราะ `/pos/counter/<เคาน์เตอร์>`
ตอบไม่ได้ว่าหมายถึงบิลใบไหน

## 3. ทางเข้า — ปัญหา "มองไม่เห็นจากหน้าจอไหนเลย" ปิดแล้ว

จุดขายที่ไม่ใช่โต๊ะนั่งถูกกรองออกจากผังโต๊ะตั้งแต่ก้อนที่แล้ว จึงต้องมีทางเข้าใหม่:

- **แถบซื้อกลับบน `/pos`** — วางไว้**เหนือ**ผังโต๊ะ เพราะลูกค้าซื้อกลับยืนรออยู่จริง
  ต่างจากโต๊ะที่นั่งรอได้ · ได้พื้น accent เต็มใบเมื่อมีของพร้อมให้ลูกค้ารับ
- **`/pos/counter`** — การ์ดเรียงตามเลขคิวจากน้อยไปมาก (คนที่รอนานที่สุดอยู่บนสุด)
  ไม่ใช่เรียงตามเวลาเปิดล่าสุดแบบผังโต๊ะ
- **แถบข้างไม่ได้เพิ่มโมดูลที่ 07** — design "Cafe POS" วางไว้หกโมดูล และสำหรับ
  พนักงานมันคืองานเดียวกัน ("รับออร์เดอร์") แค่คนละช่องทาง จึงให้โมดูล 01
  ครอบ `/pos/counter` ด้วย

**"ต้องรีบ" ที่เคาน์เตอร์ = ของเสร็จแล้วแต่ลูกค้ายังไม่ได้รับ** ซึ่งต่างจากผังโต๊ะ
ที่แปลว่า "ต้องไปยกเสิร์ฟ" — ที่เคาน์เตอร์ไม่มีใครยกไปให้ ลูกค้ายืนรออยู่ตรงนั้น

## 4. ภาษาบนหน้าจอ

`BillScreen` เดิมเขียน "โต๊ะ" ตายตัวหลายจุด ทำให้บิลซื้อกลับขึ้นว่า
"โต๊ะ เคาน์เตอร์ซื้อกลับ" ซึ่งอ่านแล้วสะดุดทุกครั้ง — แก้เป็น:

- หัวจอมาจาก prop (`คิดเงิน · ซื้อกลับ คิว 1`)
- หน้าสรุปหลังจ่ายเลือกคำจาก `kind` ของจุดขาย (`รับเงินแล้ว · ซื้อกลับ คิว 1`)
  จึงต้องเพิ่ม `kind` + `queueNumber` เข้า query ของ `getPayment()`
- ปุ่มกลับที่ใช้ร่วมกันเปลี่ยนเป็นคำกลาง ("ย้อนกลับ")
- **ปุ่มกลับของหน้าสรุปฝั่งซื้อกลับพาไปแถบคิว ไม่ใช่บิลใบเดิม** เพราะบิลปิดแล้ว
  รอบขายหายไปด้วย URL เดิมจะ 404

`OpenSalePointForm` ไม่ถามจำนวนคนต่างจาก `OpenTableForm` โดยตั้งใจ — ลูกค้าซื้อกลับ
ไม่ได้นั่ง "จำนวนคนต่อโต๊ะ" ไม่มีความหมายและไม่ควรไปปนในยอดขายต่อหัวของบทที่ 15
และเป็นปุ่มเดียวจบไม่มีฟอร์ม เพราะจังหวะที่กดคือตอนลูกค้ายืนรอบอกออร์เดอร์อยู่ —
อะไรที่ต้องกรอกก่อนเริ่มรับออร์เดอร์ได้จะกลายเป็นของที่พนักงานกรอกมั่ว ๆ ให้ผ่านไป

## 6. ยังไม่ได้ทำ

- **KDS ยังไม่ขึ้น "ซื้อกลับ · คิว 12"** (ข้อ 4 ของแผน) — ตั๋วของบิลซื้อกลับตอนนี้
  ขึ้นชื่อจุดขายว่า "เคาน์เตอร์ซื้อกลับ" ซึ่งครัวอ่านแล้วไม่รู้ว่าของใคร
  **นี่คือก้อนถัดไป และควรทำก่อนเปิดใช้จริง**
- `TableSession.customerName` มีคอลัมน์ + แสดงผลแล้ว แต่**ยังไม่มีฟอร์มให้กรอก**
- ไรเดอร์ทั้งหมด (ข้อ 5 ของแผน) — `/pos/delivery`, `PaymentMethod.PLATFORM`,
  `platform`/`platformOrderCode` (ต้อง migration เพิ่ม)
- ยังไม่ได้วัด responsive/overflow ของหน้าใหม่สองหน้าด้วยสคริปต์ headless
  (ใช้คลาสและโครงเดียวกับผังโต๊ะที่วัดผ่านแล้ว แต่ยังไม่ได้ยืนยันเอง —
