## 2. สองระดับสิทธิ์ ไม่ใช่ระดับเดียว

| สิทธิ์ | ใครทำได้ | ทำไม |

ห้าตัวหลัง **เปลี่ยนยอดที่ลูกค้าต้องจ่าย** และเป็นช่องโกงที่เนียนที่สุดของระบบนี้:
ลดเซอร์วิสชาร์จเป็น 0 ตอนดึก เก็บเงินลูกค้าเท่าเดิม แล้วตั้งกลับตอนเช้า —
`settings.tax_update` จึงเข้า `AUDIT_SENSITIVE_ACTIONS` (ตระกูลเดียวกับการแก้ราคาเมนู)

**แผงที่กดไม่ได้ยังแสดงค่าปัจจุบันให้เห็น** ไม่ใช่ซ่อนทั้งแผง — ผู้จัดการต้องตอบลูกค้า
ได้ว่าร้านคิด VAT กี่เปอร์เซ็นต์ แค่แก้เองไม่ได้ (ยืนยันบนเซิร์ฟเวอร์จริงแล้ว)

## 3. กฎเรื่องเงินที่บังคับไว้

- **แก้อัตราแล้วบิลที่ปิดไปแล้วต้องไม่ขยับแม้แต่บาทเดียว** — ทั้งระบบพึ่ง snapshot
  ใน `Payment`/`Receipt` มาตั้งแต่บทที่ 11-12 · เทสต์ขึ้น VAT เป็น 10% + เซอร์วิสชาร์จ
  เป็น 20% หลังปิดบิลแล้วยืนยันว่ายอดเดิม ฿132.00 ไม่ขยับ ส่วนบิลใบใหม่ของชุดเดียวกัน
  เป็น ฿144.00 ทันที — **นี่คือข้อพิสูจน์ว่า snapshot ทำงานจริง ไม่ใช่แค่ตั้งใจให้ทำ**
- **เปลี่ยนสกุลเงินไม่ได้ถ้าสาขานี้เคยรับเงินแล้ว** — ยอดทุกคอลัมน์เก็บเป็น "จำนวน
  หน่วยย่อยของสกุลเงินสาขา" เลข 6000 ที่เคยแปลว่า ฿60.00 จะกลายเป็น ₭6,000 ทันที
  ที่สลับ = ประวัติการเงินทั้งร้านถูกตีความใหม่โดยไม่มีใครสั่ง · หน้าจอปิดช่องให้ด้วย
  แต่ตัวที่กันจริงอยู่ฝั่ง server
- **อัตราเป็น basis point จำนวนเต็ม 0-10000 เท่านั้น** · ช่องกรอกเป็น "เปอร์เซ็นต์"
  เพราะเจ้าของร้านคิดเป็น 7% ไม่ใช่ 700 bp — ตัวแปลง `percentToBp()` **แยกสตริง
  ที่จุดทศนิยมเอง ไม่คูณ 100 แบบ float** (เหตุผลเดียวกับ `parseMoneyInput()`)
- **timezone ต้องเป็นค่าที่ Node รู้จักจริง** (`Intl.DateTimeFormat` throw = ปฏิเสธ)
  — ค่าผิดแปลว่าเลขบิลกับรายงานตัดวันผิดทั้งระบบ
- เลขประจำตัวผู้เสียภาษี: ตัดขีด/ช่องว่างออกก่อนเก็บ · ว่างได้ แต่ถ้ากรอกต้องครบ 13 หลัก
- ข้อมูลกิจการอยู่คนละตารางกับข้อมูลสาขา จึงเขียนใน `$transaction` เดียว — ครึ่งเดียว
  สำเร็จแปลว่าใบเสร็จพิมพ์ข้อมูลผสมสองยุคออกมา

## 4. ข้อความท้ายใบเสร็จ — ของใหม่ที่ต้อง migration

เดิม "ขอบคุณที่ใช้บริการ" ฮาร์ดโค้ดอยู่ใน `receipt-document.tsx`

- เพิ่ม `Branch.receiptFooter` (ตั้งเอง) + **`Receipt.sellerFooter` (snapshot ณ วันที่ออกใบ)**
  — ร้านเปลี่ยนข้อความแล้วใบเก่าต้องพิมพ์ซ้ำได้เหมือนเดิมเป๊ะ เหตุผลเดียวกับ
  `sellerName`/`sellerAddress` ที่อยู่ในกลุ่มเดียวกัน (มีเทสต์ตรึงทั้งสองทิศ)
- `null` = ใช้ข้อความเริ่มต้นของระบบ ไม่ใช่ "ไม่มีอะไรเลย" — ใบที่จบห้วน ๆ ดูเหมือน
  พิมพ์ไม่ครบมากกว่าดูเหมือนตั้งใจ · ใบเก่าที่ออกก่อนมีคอลัมน์นี้จึงยังพิมพ์ถูก
- **คำเตือน "เอกสารตัวอย่างจากระบบสาธิต" ยังฮาร์ดโค้ดไว้ตลอด แก้จากหน้าตั้งค่าไม่ได้**
  เพราะเป็นคำเตือนด้านความถูกต้อง ไม่ใช่ข้อความการตลาดของร้าน

## 5. สถานีครัว (§24)

เพิ่ม/แก้ชื่อ/เรียงลำดับ/ปิดใช้งาน/ลบ · **ลบได้เฉพาะสถานีที่ไม่เคยถูกใช้เลย**
(นับ `OrderItem` และ `MenuItem` ก่อนเสมอ) ที่เหลือบังคับเป็น "ปิดใช้งาน" —
กติกาเดียวกับเมนูที่เคยถูกสั่งในโมดูล 04 เพราะ `OrderItem.stationId` ชี้มาที่มัน
และรายงาน "ครัวไหนช้า" ในบทที่ 15 อ่านจากตรงนั้น · รหัสถูกทำเป็นตัวใหญ่ให้เอง
· เปลี่ยนชื่อสถานีไม่กระทบตั๋วที่อยู่บนจอครัว เพราะ KDS กรองด้วย id ที่ snapshot ไว้

## 6. สองอย่างที่การวัดจอจับได้

1. **แถบล่างของจอหลังร้านออกแบบไว้ตอนมีสี่โมดูล ตอนนี้มีหก** — ที่ 390px เหลือ
   ช่องละ ~55px ป้าย "บันทึกการใช้งาน" ตัดเป็นสามบรรทัด → เพิ่มฟิลด์ `short`
   ให้แถบล่างใช้ป้ายสั้น ("บันทึก" · "ตัวเลือก") ส่วนแถบซ้ายของจอกว้างยังใช้ป้ายเต็ม
   **เพิ่มโมดูลที่เจ็ดเมื่อไหร่ต้องกลับมาคิดใหม่ว่าแถบล่างยังไหวไหม**
2. **สคริปต์วัดจอเองรายงานผิด** — มันหยิบ element **ตัวแรก** ที่มีข้อความนั้น ซึ่งคือ
   ลิงก์ในแถบซ้ายที่ถูกซ่อนบนจอแคบ แล้วสรุปว่า "ของที่ต้องเห็นถูกซ่อน" ทั้งที่หัวหน้าจอ
   แสดงอยู่ปกติ → แก้เป็น **"มองเห็นได้ที่ไหนสักที่ไหม"** (หา element ตัวแรกที่ขนาดไม่ใช่ 0)
   — เป็นบทเรียนเดียวกับที่บันทึกไว้สองครั้งก่อน: **เครื่องมือวัดที่ถามคำถามผิด
   จะให้คำตอบที่เชื่อไม่ได้ ทั้งตอนที่มันบอกว่าผ่านและตอนที่มันบอกว่าไม่ผ่าน**
