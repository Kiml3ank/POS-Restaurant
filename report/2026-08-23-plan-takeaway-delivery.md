# แผน — ช่องทางขายใหม่: ซื้อกลับหน้าร้าน (walk-in / drive-in) และไรเดอร์

เขียน 2026-08-23 ตามที่ผู้ใช้ขอ · **ยังไม่ได้ลงมือ** — เอกสารนี้คือแผน ไม่ใช่รายงาน
มี **คำถามที่ต้องตอบก่อนเริ่ม** รวมอยู่ในหัวข้อ 6 (ทำเลยไม่ได้ ต้องเลือกก่อน)

---

## 1. โจทย์

เพิ่มหน้าจอรับออร์เดอร์ให้สองช่องทางที่ **ไม่มีโต๊ะ**:

1. **ซื้อกลับหน้าร้าน** — ลูกค้าเดินมา/ขับมาที่หน้าร้าน สั่ง จ่าย รอรับ แล้วไป
2. **ไรเดอร์** — ออร์เดอร์มาจากแพลตฟอร์ม (Grab / LINE MAN / Shopee ฯลฯ)
   ร้านคีย์เข้าระบบเพื่อให้ครัวทำ แล้วไรเดอร์มารับ

---

## 2. สถานะของระบบตอนนี้ — สิ่งที่ต้องรู้ก่อนอ่านต่อ

| ของ | สถานะ |
|---|---|
| `enum OrderType { DINE_IN, TAKEAWAY }` | มีใน schema **แต่ไม่มีโค้ดที่ไหนอ่านหรือเขียนเลย** (grep แล้วเจอ 0 จุด) = schema ตายอยู่ |
| `Order.tableSessionId` | **nullable แล้ว** พร้อมคอมเมนต์ว่า "null ได้เมื่อเป็นออร์เดอร์กลับบ้าน" |
| `Payment.tableSessionId` | **บังคับ (ไม่ nullable)** ← **นี่คือตัวบล็อกจริง** |
| `getTableBill()` / `takePayment()` | ทุก query กรองด้วย `tableSessionId` |
| `Receipt` | ผูกกับ `Payment` ซึ่งผูกกับ `TableSession` |
| ส่วนลดพนักงาน (13a) | เก็บที่ `TableSession` |
| `addToCart()` | บังคับ `tableSessionId` |

**สรุป: สาย บิล → รับเงิน → ใบเสร็จ ทั้งเส้นถูกยึดไว้กับ `TableSession`**
ออร์เดอร์ที่ไม่มีโต๊ะจึงยังจ่ายเงินไม่ได้เลยในวันนี้ ไม่ว่าจะทำหน้าจอสวยแค่ไหน

## 3. การตัดสินใจที่ใหญ่ที่สุด — จะแก้ตัวบล็อกยังไง

### ทางเลือก A — ทำให้ทุกอย่าง "ไม่มี session ก็ได้"

`Payment.tableSessionId` เป็น nullable แล้วเพิ่มเส้นทางที่สองในทุกฟังก์ชัน

**ข้อเสียที่ทำให้ไม่แนะนำ:** ทุกจุดที่เขียนว่า `where: { tableSessionId: session.id }`
กลายเป็นสองสาขา (`billing.ts`, `payment.ts`, `receipt.ts`, `staff-meal.ts`,
`dev-reset-table`, smoke ทั้งแปดชุด) — และ **กฎที่ระบบพึ่งพาอยู่จะพังทันที**:
"หนึ่งรอบโต๊ะ = หนึ่งบิล" คือหลักที่ทำให้การคิดเซอร์วิสชาร์จ/VAT ครั้งเดียวถูกต้อง
(บทที่ 10) และเป็นตั๋วกันจ่ายซ้ำใน `takePayment()` (บทที่ 11) ถ้าไม่มี session
ต้องประดิษฐ์กลไกกันจ่ายซ้ำอีกชุดสำหรับเส้นทางที่สอง ซึ่งจะเพี้ยนออกจากกันแน่นอน

### ทางเลือก B — "รอบขาย" ที่ไม่ผูกโต๊ะจริง ✅ **แนะนำ**

ไม่แตะสาย บิล → รับเงิน → ใบเสร็จ เลยแม้แต่บรรทัดเดียว แต่ให้ช่องทางใหม่
**เปิด `TableSession` ของตัวเอง** บน "จุดขาย" ที่ไม่ใช่โต๊ะนั่ง

```
RestaurantTable += kind: DINE_IN | COUNTER | DELIVERY
```

- `COUNTER` = เคาน์เตอร์ซื้อกลับ · `DELIVERY` = ช่องรับออร์เดอร์แพลตฟอร์ม
- **ไม่ขึ้นในผังโต๊ะ** ของ `/pos` (กรอง `kind = DINE_IN`)
- ทุกอย่างท้ายน้ำใช้ได้ทันที: คิดบิล · รับเงิน · ใบเสร็จ · ส่วนลดพนักงาน ·
  กันจ่ายซ้ำ · `dev:reset-table` · smoke ทั้งแปดชุด **ไม่ต้องแก้อะไรเลย**

**⚠ กับดักที่ต้องแก้คู่กัน:** `openOrJoinTableSession()` ออกแบบให้ **เข้าร่วม**
รอบที่เปิดค้างอยู่ (สี่คนที่โต๊ะเดียวกันต้องได้บิลใบเดียว) — ถ้าใช้ตรง ๆ กับเคาน์เตอร์
**ลูกค้าซื้อกลับสองคนที่มาพร้อมกันจะได้บิลใบเดียวกัน** ซึ่งพังทันทีที่เปิดร้าน

→ ต้องเพิ่มกติกา: จุดขายที่ `kind !== DINE_IN` **สร้างรอบใหม่เสมอ ไม่เข้าร่วมของเดิม**
(เหตุผลเชิงความหมายชัดเจน: เคาน์เตอร์ไม่ใช่ที่ที่คนนั่งลงด้วยกัน)
แปลว่าจุดขายหนึ่งจุดมีรอบที่เปิดพร้อมกันได้หลายรอบ ซึ่งต่างจากโต๊ะจริง

**ผลที่ตามมา: ต้องมี "เลขคิว"** เพราะไม่มีชื่อโต๊ะให้เรียกลูกค้า —
ดูหัวข้อ 4.2

## 4. สิ่งที่ต้องสร้าง

### 4.1 Schema

```
RestaurantTable += kind SalePointKind @default(DINE_IN)   // DINE_IN | COUNTER | DELIVERY
TableSession    += queueNumber Int?        // เลขคิวต่อสาขาต่อวัน (เฉพาะ COUNTER/DELIVERY)
                 + customerName String?    // "คุณเอ" / ชื่อบนออร์เดอร์แพลตฟอร์ม
                 + customerPhone String?   // ซื้อกลับที่ให้โทรตามได้
                 + platform String?        // "GRAB" / "LINEMAN" / ... (เฉพาะ DELIVERY)
                 + platformOrderCode String?  // เลขออร์เดอร์ของแพลตฟอร์ม
Order.type       ← เริ่มเขียนค่าจริงสักที (DINE_IN / TAKEAWAY / DELIVERY)
```

`OrderType` ต้องเพิ่ม `DELIVERY` และ **ต้องมีโค้ดที่เขียนค่ามันจริง ๆ**
(ตอนนี้ทุกออร์เดอร์เป็น `DINE_IN` ตาม default เพราะไม่มีใครเซ็ต)

**`platformOrderCode` สำคัญกว่าที่คิด** — เป็นตัวเดียวที่ใช้กระทบยอดกับแพลตฟอร์ม
ตอนสิ้นเดือนได้ ถ้าไม่เก็บ ร้านจะเทียบไม่ได้ว่าแพลตฟอร์มโอนเงินมาครบไหม

### 4.2 เลขคิว — กติกาที่ต้องตัดสินให้จบก่อนเขียน

ใช้ท่าเดียวกับ `orderNumber` (`YYYYMMDD-NNNN` ต่อสาขาต่อวัน) **ไม่ใช่ท่าเดียวกับ
เลขใบเสร็จ** เพราะสองอย่างนี้มีข้อกำหนดคนละแบบ:

| | เลขใบเสร็จ (บทที่ 12) | เลขคิว |
|---|---|---|
| ต่อเนื่องห้ามขาด | **ใช่** (กฎหมาย) | ไม่ต้อง |
| รีเซ็ต | ไม่เคย | **ทุกวัน** |
| คนอ่านออกเสียง | ไม่ | **ใช่ — ต้องสั้น** |

→ เลขคิวเป็น 1, 2, 3… รีเซ็ตทุกวันตาม timezone สาขา · เรียก "คิว 12" ได้
**ห้ามเอา `DocumentCounter` มาใช้ซ้ำ** เพราะตัวนั้นห้ามรีเซ็ตตลอดกาล

### 4.3 หน้าจอ

| หน้า | ใคร | ทำอะไร |
|---|---|---|
| `/pos/counter` | แคชเชียร์ | เปิดบิลซื้อกลับใหม่ → สั่ง → คิดเงิน (เมนูเหมือนหน้าโต๊ะ ใช้ component เดิม) |
| `/pos/delivery` | แคชเชียร์ | คีย์ออร์เดอร์แพลตฟอร์ม: เลือกแพลตฟอร์ม + ใส่เลขออร์เดอร์ + สั่ง |
| `/pos` (ผังโต๊ะ) | ทุกคน | เพิ่มแถบ "ซื้อกลับ / ไรเดอร์" ที่แสดงคิวที่ยังไม่ปิด |
| KDS | ครัว | ตั๋วต้องขึ้น **ช่องทาง + เลขคิว** เด่นกว่าชื่อโต๊ะ |

**ใช้ component เดิมทั้งหมด** — `/pos/table/[tableId]` มีทั้งเมนูและตะกร้าอยู่จอเดียว
อยู่แล้ว หน้าใหม่ควรเป็น **เส้นทางบาง ๆ ที่ resolve จุดขายแล้ว render ตัวเดิม**
ไม่ใช่หน้าจอชุดที่สอง (ท่าเดียวกับ `receipt-document.tsx` ในบทที่ 12)

### 4.4 KDS — จุดที่พลาดแล้วเสียหายจริง

ตั๋วบนจอครัวตอนนี้บอก "โต๊ะ A3" ออร์เดอร์ซื้อกลับจะไม่มีอะไรให้บอก
→ ต้องขึ้น **"ซื้อกลับ · คิว 12"** หรือ **"GRAB · #A7K2"** ด้วยน้ำหนักเท่าชื่อโต๊ะ

และ **ลำดับความเร่งด่วนต่างกันจริง**: ไรเดอร์ยืนรออยู่และมีเวลาจับ ส่วนโต๊ะที่นั่งอยู่
รอได้นานกว่า — แต่ **ยังไม่ต้องทำการเรียงลำดับอัตโนมัติในก้อนนี้** แค่ให้ครัวเห็น
ช่องทางชัด ๆ ก่อน แล้วค่อยดูว่าร้านอยากให้เรียงยังไงจากการใช้จริง

## 5. เรื่องเงินของไรเดอร์ — ต่างจากซื้อกลับคนละเรื่อง

**ซื้อกลับ** = ลูกค้าจ่ายที่ร้าน เงินสด/QR → ใช้ `takePayment()` เดิมได้ทั้งดุ้น

**ไรเดอร์ = ร้านไม่ได้รับเงินจากคนที่มายืนอยู่** ลูกค้าจ่ายให้แพลตฟอร์มไปแล้ว
แพลตฟอร์มหักค่าคอมมิชชัน (ปกติ 30-35%) แล้วโอนให้ร้านทีหลังเป็นก้อน

ผลที่ตามมาที่ต้องออกแบบ ไม่ใช่แค่เพิ่มปุ่ม:

1. **ต้องมีวิธีรับเงินแบบ "ไม่ได้รับเงินสด"** — `PaymentMethod` เพิ่ม `PLATFORM`
   หรือคล้ายกัน · ยอด `receivedAmount`/`changeAmount` เป็น null เหมือน QR
2. **ยอดที่บันทึกคือยอดเต็มหรือยอดหลังหักคอม?** → **ต้องเป็นยอดเต็ม**
   เพราะนั่นคือราคาที่ขายจริงและเป็นฐาน VAT · ค่าคอมเป็น **รายจ่าย** คนละเรื่อง
   (โมดูล Expenses ที่ยังไม่มี — spec §16) **ห้ามเอาไปลบออกจากยอดขาย**
   ไม่งั้นรายงานยอดขายกับใบกำกับภาษีจะไม่ตรงกัน
3. **ใบเสร็จ** — ปกติไม่ได้ให้ไรเดอร์ (แพลตฟอร์มออกให้ลูกค้าเอง) แต่ระบบยังออกใบ
   อัตโนมัติอยู่ (บทที่ 12 ออกใบใน transaction ของการรับเงินเสมอ)
   → **ต้องตัดสินใจ**: ออกใบให้ทุกออร์เดอร์แพลตฟอร์มเหมือนเดิม (เลขเดินต่อเนื่อง
   ครบถ้วน ตรวจสอบง่าย แต่มีใบที่ไม่มีใครรับ) หรือแยกชุดเอกสาร — ดูคำถามข้อ 6.3
4. **VAT ของออร์เดอร์แพลตฟอร์ม** เป็นเรื่องที่ **ต้องถามผู้สอบบัญชี** ไม่ใช่เดาเอง
   (ใครเป็นผู้ขายในทางภาษี ร้านหรือแพลตฟอร์ม — ต่างสัญญากันคนละแบบ)

## 6. ❓ คำถามที่ต้องตอบก่อนเริ่มเขียนโค้ด

### 6.1 ใครเป็นคนกดสั่งของ "ซื้อกลับหน้าร้าน"

- **(ก) แคชเชียร์คีย์ให้** — เหมือนสั่งแทนลูกค้าที่โต๊ะ ใช้ของเดิมได้เกือบหมด
- **(ข) ลูกค้าสแกน QR ที่เคาน์เตอร์สั่งเอง** — ต้องมี QR ที่ไม่ผูกโต๊ะ +
  แก้ `proxy.ts` + คิดเรื่องคนสองคนสแกน QR ใบเดียวกันพร้อมกัน (ต้องได้คนละบิล)
- **(ค) ทั้งสอง**

ข้อนี้เปลี่ยนขนาดงานมากที่สุด — (ก) เล็กกว่า (ข) หลายเท่า

### 6.2 ไรเดอร์ — คีย์เองหรือรับอัตโนมัติ

- **(ก) แคชเชียร์คีย์ตามที่เห็นบนแท็บเล็ตของแพลตฟอร์ม** (ทำได้เลย)
- **(ข) ต่อ API ของแพลตฟอร์ม** — คนละขนาดงาน ต้องสมัคร partner แต่ละเจ้า
  แต่ละเจ้ามี API คนละแบบ และหลายเจ้าไม่เปิดให้ร้านเล็ก

แผนนี้เขียนบนสมมติฐาน **(ก)**

### 6.3 ออร์เดอร์แพลตฟอร์มต้องออกใบเสร็จไหม

ตอนนี้ระบบออกใบให้ทุกการรับเงินโดยอัตโนมัติใน transaction เดียวกัน (บทที่ 12)
ถ้าไม่อยากให้ออก ต้องแก้ตรงนั้น ซึ่งกระทบสมบัติ "ไม่มีบิลที่จ่ายแล้วไม่มีเอกสาร"
ที่ตั้งใจทำไว้ — **แนะนำให้ออกเหมือนเดิม** แล้วแค่ไม่พิมพ์

### 6.4 จ่ายก่อนหรือหลังทำ

ซื้อกลับส่วนใหญ่จ่ายก่อน แต่ระบบตอนนี้ออกแบบให้ **สั่ง → ครัวทำ → จ่ายทีหลัง**
(จ่ายก่อนได้อยู่แล้วเพราะ `takePayment` ไม่บังคับว่าของต้องเสิร์ฟครบ แค่เตือน)
→ ต้องรู้ว่าอยากให้หน้าจอ **บังคับลำดับ** หรือปล่อยอิสระเหมือนเดิม

### 6.5 ค่าส่ง / ค่ากล่อง

ซื้อกลับหลายร้านคิดค่ากล่อง · ไรเดอร์มีค่าส่งที่แพลตฟอร์มเก็บ (ไม่ใช่รายได้ร้าน)
→ ถ้าต้องมีค่ากล่อง มันคือ **สินค้าอีกชิ้นในบิล** ไม่ใช่ค่าธรรมเนียมพิเศษ
(ง่ายกว่ามากและไม่ต้องแตะสูตรคิดเงิน) — ยืนยันว่ารับแนวนี้ได้ไหม

### 6.6 เซอร์วิสชาร์จของออร์เดอร์ที่ไม่ได้นั่งกิน

สาขานี้ตั้ง `serviceChargeBp = 1000` (10%) **ซึ่งจะถูกคิดกับซื้อกลับด้วยถ้าไม่ทำอะไร**
ร้านส่วนใหญ่ **ไม่คิด** เซอร์วิสชาร์จกับของกลับบ้าน เพราะไม่มีการบริการที่โต๊ะ
→ ต้องตัดสินใจว่าจะให้อัตราขึ้นกับ **ช่องทาง** ไหม (เป็นการเปลี่ยนที่กระทบ
`calculateBill()` ซึ่งเป็นหัวใจของบทที่ 10 จึงต้องตั้งใจทำ ไม่ใช่แถม)

**ข้อนี้คือข้อที่ถ้าลืม ลูกค้าจะโดนเก็บเงินเกินทุกใบตั้งแต่วันแรก**

| 2 | เซอร์วิสชาร์จตามช่องทาง (ข้อ 6.6) | ต้องมาก่อนเปิดใช้จริง ไม่งั้นเก็บเงินเกิน |
| 3 | `/pos/counter` + แถบคิวในผังโต๊ะ | ช่องทางที่ง่ายกว่าและใช้บ่อยกว่า |
| 4 | KDS แสดงช่องทาง + เลขคิว | ครัวต้องเห็นก่อนที่ออร์เดอร์จริงจะเข้ามา |
| 5 | `/pos/delivery` + `PaymentMethod.PLATFORM` + `platformOrderCode` | ต้องรอข้อ 1-4 เสถียรก่อน |
| 6 | รายงานแยกช่องทาง | ไปรวมกับบทที่ 15 |

**ข้อ 1-4 = ซื้อกลับใช้งานได้จริง** · ข้อ 5 = ไรเดอร์

## 8. สิ่งที่แผนนี้ **ไม่** ครอบ

- **ส่งเองโดยพนักงานร้าน** (ที่อยู่ลูกค้า · ค่าส่ง · สถานะจัดส่ง · คนขับ) —
  เป็นโมดูล Delivery เต็มรูปตาม spec §10 ซึ่งใหญ่กว่านี้มาก แผนนี้ครอบแค่
  **ไรเดอร์ของแพลตฟอร์มมารับที่ร้าน**
- **ต่อ API แพลตฟอร์ม** (ข้อ 6.2ข)
- **บัญชีลูกค้า/แต้มสะสม** — spec §11 คนละโมดูล
- **ค่าคอมมิชชันแพลตฟอร์มเป็นรายจ่าย** — ต้องมีโมดูล Expenses ก่อน (spec §16)
